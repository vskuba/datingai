# Tool Rules — автообнаруживаемые инструменты для LLM

> Инструмент — обычная функция в специальной ветке кода. Её **докстринг — это контракт для
> LLM**, а не комментарий для человека. Ошибки возвращаются, а не выбрасываются.

## 1. Требования к функции

1. **Место** — только в ветке инструментов (`<root>/tool/**`). Всё, что туда положено,
   становится инструментом автоматически; обычную бизнес-логику там держать нельзя.
2. **Асинхронная** — движок вызывает инструменты в общем цикле событий.
3. **Имя уникально глобально**, а не внутри файла или категории (см. раздел 4).
4. **Аннотации типов у всех параметров** — по ним строится схема, которую видит LLM.
   Параметр без аннотации превращается в «строку неизвестного назначения».
5. **Значения по умолчанию** у всех необязательных параметров.
6. **Возвращает `dict`** — всегда словарь, даже если результат одно значение.
7. **Не выбрасывает исключения наружу.** Ошибка — часть результата:
   ```python
   return {"success": False, "error": "понятное описание"}
   ```
   Причина: исключение обрывает выполнение сценария, а LLM должна иметь возможность
   прочитать ошибку и попробовать иначе.
8. **Идемпотентность там, где возможно.** LLM повторяет вызовы: при таймауте, при
   непонятном ответе, просто «на всякий случай».
9. **Никаких побочных эффектов, не описанных в докстринге.** Если функция что-то удаляет
   или отправляет наружу — это первая строка описания.

## 2. Докстринг — контракт

Докстринг попадает в промпт. Он одновременно документация и спецификация:

```python
async def <domain>_<action>(target: str, limit: int = 10) -> dict:
    """
    Одна строка: что инструмент делает и когда его выбирать.

    Args:
        target: что обрабатываем — в терминах, понятных без чтения кода
        limit: сколько элементов вернуть максимум (по умолчанию 10)

    Returns:
        success: удалось ли выполнить
        items: найденные элементы
        error: описание ошибки, если success = false
    """
```

- **Первая строка — критерий выбора.** LLM выбирает инструмент по ней. «Обрабатывает
  данные» не помогает выбрать; «Ищет пользователя по email» помогает.
- **`Args:` — не пересказ имени параметра**, а смысл и допустимые значения.
- **`Returns:` разбирается в перечень выходных ключей** — то, что там перечислено,
  становится доступным дальше в сценарии. Ключ, которого нет в докстринге, невидим,
  даже если функция его возвращает.
- Описывать **ограничения**: лимиты, форматы, что будет при отсутствии данных.

## 3. Автообнаружение

Типичный механизм: обход файлов ветки инструментов, разбор синтаксического дерева
(без импорта — импорт исполняет код и требует всех зависимостей), извлечение публичных
функций, их сигнатур и докстрингов, синхронизация в реестр (таблицу БД).

Практические следствия:

- реестр — **производная от кода**, его не правят руками (правки затрутся)
- реестр в seed не попадает (см. `backup_rules.md`)
- удалённая из кода функция должна **исчезать или помечаться неактивной** при синхронизации,
  иначе LLM продолжает вызывать несуществующее
- синхронизация запускается при старте и/или вручную; после правки инструмента её надо
  выполнить, иначе изменения не видны движку

## 4. Уникальность имени

> ⚠️ Если имя инструмента хранится в колонке с уникальным индексом и ограничением длины,
> **два инструмента с совпадающим префиксом схлопнутся** — и синхронизация может
> обрезать/перезаписать записи. Симптом непропорционально страшный: часть реестра
> исчезает.

Правило: имена короче лимита колонки и различаются в начале, а не в конце.
Правило префикса из `code_rules.md` работает и здесь — оно же и даёт различимость.

## 5. Приведение типов

Параметры приходят из LLM и из определения сценария **строками**. Движок приводит их к
аннотированным типам. Отсюда:

- `bool` из строки — сравнение с набором истинных значений, а не `bool("false")`
  (непустая строка всегда истинна)
- пустая строка для числа — это «не задано», а не `0`
- **проверка «значение задано» через «истинность» ломается на `0`, `""`, `False`, `[]`.**
  Различать «не передано» и «передано пустым» нужно явно (`is None`)
- сложные структуры передавать как JSON-строку с явным разбором внутри функции

## 6. Чек-лист нового инструмента

1. Файл — в ветке инструментов, имя по правилу префикса.
2. Функция асинхронная, все параметры аннотированы, необязательные — с дефолтами.
3. Докстринг: первая строка = критерий выбора; `Args:` со смыслом; `Returns:` со всеми
   ключами, которые нужны дальше.
4. Возврат — `dict`; ошибки — `{"success": False, "error": ...}` без исключений.
5. Проведена синхронизация реестра; инструмент появился и параметры разобраны верно.
6. Вызов проверен вручную с валидным и с заведомо плохим входом.
7. Опасные действия (удаление, отправка наружу, трата денег) — явно названы в докстринге
   и по возможности требуют подтверждения.

## Грабли

1. **Бизнес-логика в ветке инструментов** — становится инструментом и предлагается LLM
2. **Ключ не описан в `Returns:`** — недоступен в сценарии, «инструмент ничего не вернул»
3. **Исключение вместо `{"success": False}`** — обрыв сценария вместо обработки
4. **Забыта синхронизация** — правка не видна движку
5. **Коллизия имён** — часть реестра пропадает
6. **Проверка «задано» через истинность** — `0` и `""` считаются отсутствующими
7. **Размытая первая строка докстринга** — LLM выбирает не тот инструмент
