# Вход в панель

## 1. Два состояния и ни одного больше

Прав здесь ровно два: вошёл или нет. Ролевой матрицы нет намеренно — весь проект
про одну вещь, анкеты на сайтах знакомств, и делить его на «смотреть» и «править»
значило бы завести бухгалтерию ради одной страницы.

Понадобится разделение — оно появится тогда, когда появится второй род работы.
Пока его нет, лишний слой прав только создаёт иллюзию защищённости.

## 2. Чем представляются

| Способ | Кто им ходит | Где проверяется |
|--------|--------------|-----------------|
| сессионная кука `dating_session` | человек со страницы | `SessionMiddleware` + `auth_required` |
| `Authorization: Bearer <token>` | скрипты, проверки | `auth_token_user` по таблице `user_access_token` |
| `X-API-KEY: <token>` | интеграции | там же |

Два заголовка, потому что `Bearer` общепринят, а `X-API-KEY` привычен
интеграциям. Голый токен без слова `Bearer` тоже принимается: так его шлют из
curl чаще, чем по спецификации, и отвергать за это жестоко.

Проверка живёт в одной функции (`auth_required`), поэтому новый способ
представиться появляется сразу во всех точках, а не в тех, куда его не забыли
добавить.

## 3. Middleware: редирект человеку, 401 скрипту

`main_uvicorn_auth_middleware` различает не пути, а тип ответа, который ждут:

* браузер (`Accept: text/html`) уводится на `/login?next=…`;
* всем остальным отдаётся `401` с `{"detail": "нужен вход"}`.

Редирект на HTML-форму сказал бы клиенту API «всё хорошо, вот вам страница
входа», и он бы разбирал её как ответ.

Открыто без входа: `/login`, `/auth/login`, `/static`, `/health` и документация
API. Список короткий и явный — всё остальное закрыто по умолчанию, поэтому забыть
закрыть новую страницу нельзя.

## 4. Пароли

`bcrypt`, открытый пароль не хранится нигде. Сравнение идёт по хешу **всегда**,
даже когда логина нет в базе: для несуществующего пользователя берётся
хеш-заглушка. Иначе время ответа выдавало бы, существует ли такой логин.

Наружу причина отказа не уходит: «нет такого пользователя» и «неверный пароль» —
разные ответы только для того, кто перебирает логины.

## 5. Первый пользователь

Заводится на старте и **только если таблица пуста** — из `ADMIN_USERNAME` и
`ADMIN_PASSWORD`. Не «создать или обновить»: иначе правка пароля в `.env` молча
меняла бы его у живого пользователя, а забытый в образце `change-me` возвращался
бы после каждого перезапуска.

Вместе с ним заводится токен доступа: без него первую же проверку API пришлось бы
делать куками из браузера, а это не тот способ, которым живут скрипты.

## 6. Учётка для обращения к RhapsodyAi — это другое

Не путать: `RHAPSODY_TOKEN` — токен **нашей** учётки **в соседнем проекте**. Он
не даёт доступа сюда и не проверяется здешним `auth_required`. Права этой учётки
и её назначение — в `rhapsody_api.md`, раздел 2.
