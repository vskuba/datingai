# Схема базы

## 1. Где лежит структура

Структура — это `migrations/`: начальная схема
(`20260101000000_initial_schema.sql`, заморожена) плюс файлы изменений с меткой
времени в имени. Накатываются на старте сервера (`mysql_migration_up`), по
алфавиту имён, каждый ровно один раз.

Применённый файл не правят — правка не выполнится ни на проде, ни на локальной
базе с данными. Изменение таблицы — новый файл рядом; порядок и грабли —
`migration.md`.

Быстрый ответ на «как таблица выглядит сейчас» даёт база: `SHOW CREATE TABLE`
или phpMyAdmin. Таблица ниже — про смысл, а не про точный DDL.

## 2. Что в базе есть

| Таблица | Что хранит |
|---------|------------|
| `user` | люди, входящие в панель; `role` — `dating` или `admin` (см. `auth.md`) |
| `user_access_token` | токены для скриптов; у пользователя их может быть несколько |
| `profile` | учётки анкет: логин, пароль, вход, адрес сокета, статус |
| `message` | переписка: входящие и исходящие |
| `log` | журнал работы по учётке — что делали и чем кончилось |
| `contact` | собеседницы: те, с кем есть переписка или кого показал чат |
| `setting` | настройки панели: ключ → значение (страница «Настройки → Значения») |
| `scenario_run` | прогоны сценариев: что просили у соседа, чем кончилось, сколько заняло |
| `site` | сайты: снимок списка соседа (имя, адрес, метки) и наши настройки к нему |
| `mail` | шаблоны писем рассылки: текст с переменными, по сайту |
| `mail_var` | реестр переменных сайта: какие имена вообще бывают |
| `profile_var` | значения переменных у анкеты: чем их подставлять |
| `mailing` | журнал рассылки: что и кому ушло, с отрендеренным текстом |
| `companion` | собеседники сайта: карточка человека, которому пишут (⚠ `priority` — кому писать первым, порядок в наборе пула, а не отбор) |
| `favorite` | избранные: кого мы добавили девушке в звёздочки и чем это кончилось (⚠ по **анкете**, а не по сайту) |
| `invite` | пул инвайтов: первая реплика в чат тому, с кем разговора не было (⚠ шаблона нет — текст сочиняет агент) |
| `favorite_mail` | пул писем избранным: возобновление затихшего разговора (⚠ уникального ключа на пару **нет** — одному человеку пишут много раз; частоту держат настройки, а не схема) |
| `error` | что сломано **сейчас**: строка на источник отказа со счётчиком повторов |

Порядок **удаления** — от зависимых к главным: `contact`, `log`,
`message`, `scenario_run`, `profile`, `site`, `setting`,
`user_access_token`, `user`; создание идёт обратным. Иначе внешние ключи не дадут уронить таблицу, и накат встанет на
первом же `DROP`.
Всё, что связано с анкетой, уходит вместе с ней (`ON DELETE CASCADE`): карточку
удаляют, чтобы её не было, а не чтобы её переписка осталась сиротой.

## 3. Чего в базе нет и почему

Сайтов-закладок, сценариев браузера, агентов, workflow и фактов. Это хозяйство
RhapsodyAi, и вторая копия разошлась бы с первой в первый же день.

**Снимков собеседников с сайта** (избранные, кто в сети, диалоги) тоже нет, и это
отдельное решение: они про «кто там прямо сейчас», а не данные. Живут неделю в
Redis под ключом `dating:people:{profile_id}:{kind}` — срок Redis считает сам,
чистить некому и нечего, а потеря при сбросе не стоит ничего: следующий заход
снимет заново (`api.md`, §3.3).

Отсюда особенность: **`dating_profile.site_id` без внешнего ключа**. Сайт живёт у
соседа, проверить его движком базы невозможно — проверяет API-клиент
(`rhapsody_api_site_get`), и на несуществующий сайт ручка отвечает 422.

## 4. Поля, смысл которых неочевиден

**`dating_profile.storage_state`** — снятый вход (cookie и localStorage). С ним
присутствие держит обычный HTTP-клиент, без вкладки Chromium: замер на живом
сайте — вкладка ~143 МБ, клиент с cookie единицы килобайт.

**`dating_profile.ws_url`** — адрес чат-сокета с токенами сессии. В разметке его нет,
его собирает JS страницы, поэтому снимается браузером один раз. После нового
входа прежний адрес мёртв.

**`dating_profile.role`** (`lady` / `man`) — от него зависит почти всё поведение:
мужской и женский кабинеты сайта это разные приложения, у них разные сценарии, и
агент девушке заводится своим workflow. Не «пол анкеты», а «каким кабинетом
пользоваться».

**`dating_site.site_id`** — номер у соседа, **без внешнего ключа**: указывает в
чужую базу, движком не проверить. То же, что у `dating_profile.site_id` (§3).

⚠ **`dating_site.name`, `url`, `tags` — снимок ответа соседа, а не свой список.**
Прежде их здесь не было намеренно; появились они за конкретную цену: селект сайта
стоит в шапке каждой страницы раздела, и пока список брали у соседа при каждом
открытии, его недоступность гасила панель целиком.

* было: копии нет, разойтись не с чем, но лежащий сосед гасит всю панель;
* стало: копия есть и может разойтись — ценой пустого селекта.

Расхождение лечится сверкой: `synced_at` — когда снимок сверяли, `is_gone` — у
соседа такой закладки больше нет. Ушедшие **метятся, а не удаляются**: вместе со
строкой ушли бы наши настройки этого сайта, а закладку могли убрать по ошибке.

Строка теперь появляется двумя путями: сверка заводит её на каждый сайт соседа, а
сохранение настройки — на тот, который настраивают.

**`dating_site.settings`** — JSON, а не колонка на настройку: настройки сайта
только заводятся, и какие понадобятся, сейчас не знает никто; колонка под каждую
означала бы миграцию на каждую.

⚠ **`dating_site.mailing_schedule` и `mailing_schedule_on` — свои колонки, и в
`settings` им нельзя.** Расписание массовой рассылки (когда с сайта уходят письма
тем, кто в сети) хранится рядом с настройками, но не среди них, потому что
`PUT /api/dating/site/{id}` переписывает набор **целиком**: страница «Сайты» шлёт
то, что на ней, а этого ключа она не знает — первое же сохранение соседней
настройки стёрло бы расписание молча. Заодно расписание и не «ключ → значение из
набора», ради которых `settings` заведены, а структура — список смен.

Смены те же, что в `dating_profile.schedule`, и разбирает их тот же
`dating_schedule.py`. Уровень разный: там «когда анкете быть в сети» (про учётку),
здесь «когда уходит рассылка» (про сайт, один ответ на все его анкеты).

## Письма: три таблицы и почему их три

**`mail`** — шаблоны (`site_id`, `name`, `body`, `enabled`). Текст с
переменными вида `[[firstName]]`; название — для списка в панели, на сайт не
уходит.

**`mail_var`** — реестр переменных сайта (`site_id`, `name`, `source`,
`title`, `default_value`). Имя уникально **внутри сайта**: письмо ссылается на
переменную по имени, и две одноимённые сделали бы ссылку неоднозначной.

⚠ **Части имени собеседника — выводимые, и колонок у них нет.**
`companion_first_name` и `companion_last_name` разбираются из `name` карточки по
первому пробелу (`api.md`, §3.7). Заведи мы под них колонки, они разошлись бы с
именем в первую же правку — тот же довод, по которому у `companion`-переменных
нет своего хранилища вовсе.

⚠ **`source` (`profile` / `companion` / `live`) решает, где живёт значение.**
`profile` (`girl_name`) лежит в `profile_var`. `companion`
(`companion_name`) лежит в карточке получателя и **читается** при отправке. `live`
(`question_to_companion`) не лежит нигде: **вычисляется** агентом при отправке, под
каждого получателя свой.

Не три таблицы, потому что для письма разницы нет — все пишутся `[[имя]]`,
проверяются по реестру и одинаково ломают рассылку, когда их нечем подставить.
Разный только способ добыть значение.

**`profile_var`** — значения у анкеты (`profile_id`, `name`, `value`,
`filled_by`). Уникальна пара «анкета + имя»: агент вернёт значение второй раз — оно
обновится, а не задвоится.

⚠ **Значение живёт у анкеты, а не у пары «анкета — адресат».** Переменные
описывают саму анкету, и значение одно, кому бы она ни писала. Держи мы их на пару,
агента пришлось бы звать на каждого адресата — сотни вызовов вместо одного.

⚠ **Значения строками, а не JSON-колонкой в `profile`.** Их спрашивают по
имени, проверяют перед каждой отправкой и наполняют по одной; JSON пришлось бы
разбирать целиком ради одного ключа, а отбор «у кого пусто» стал бы перебором в
Python. Это обратный случай расписанию (`dating_profile.schedule`), которое читают
и заменяют целиком.

⚠ **`dating_profile_var.name` дублирует имя, а не ссылается на `dating_mail_var.id`.**
По имени идёт вся работа: письмо пишет `[[firstName]]`, агент возвращает
`firstName`, страница показывает `firstName`. Ссылка номером означала бы join на
каждую проверку письма ради строки, которая и так под рукой. Плата — **уборка при
удалении переменной лежит на коде**, а не на внешнем ключе: `CASCADE` тут
невозможен, базе не из чего понять, что строка со значением относится к удаляемой
строке реестра (`api.md`, §3.7).

**`companion`** — карточка человека, которому пишут (`site_id`, `uid`,
`name`, `photo`, `age`, `city`, `country`, `email`, `about`, `about_state`).

⚠ **Наполняется по требованию, а не списком.** Людей в сети сто с лишним, на
сайте тысячи; строка появляется, когда о человеке спросили. `about_state`
различает «не собирали» и «сходили, там пусто» — одним пустым полем их не
отличить, а решения они требуют разных.

⚠ **Не то же, что `contact`.** Там собеседницы конкретной анкеты, с
которыми уже есть переписка. Здесь — люди сайта, которым рассылка пишет впервые;
и принадлежат они сайту, а не анкете: человек один, и то, что о нём известно, не
зависит от того, какая учётка на него смотрит.

**`invite`** — пул первых реплик в чат (`site_id`, `profile_id`, `uid`,
`name`, `photo`, `body`, `status`, `error`, `sent_at`). Ключ `(profile_id, uid)`.

⚠ **Своя таблица, а не второй жанр в `mailing`.** У письма есть шаблон
(`mail_id`), и на нём держится ключ пула: «одна анкета не пришлёт один и тот же
шаблон дважды». У инвайта шаблона нет вовсе — текст сочиняет агент под конкретного
человека, — и правило другое: **одна анкета зовёт одного человека один раз**. Ключ
с шаблоном такого не выражает, а `mail_id NULL` сделал бы его неработающим (в MySQL
NULL не равен NULL — на этом уже спотыкался журнал рассылки).

⚠ **`name` хранится рядом с `uid`.** Имя приходит из снимка ленты, а тот живёт
неделю; карточка `companion` есть не у всех. Без имени в строке пул через
месяц читался бы как список номеров — а имя ещё и стоит внутри самого текста, и
расхождение между ними было бы видно человеку.

⚠ **Правило пула строже ключа.** В базе — пара, при наборе — человек: два
приветствия от двух наших девушек одному мужчине выдают агентство (`api.md`, §3.9).
Ключ отвечает на «что допустимо в истории», код набора — на «как набирается пул».

**`favorite`** — кого мы добавили девушке в избранные (`site_id`,
`profile_id`, `uid`, `state`, `error`, `tries`, `reason`). Ключ
`(profile_id, uid)`.

⚠ **По анкете, а не по сайту — в отличие от соседней `companion`.**
Избранные у каждой девушки свои: один и тот же мужчина у Дианы в звёздочках, а у
Елены нет, и это не расхождение сведений, а два разных факта. Держи мы признак в
карточке собеседника (одна на сайт), добавление под одной анкетой означало бы
«добавлено» для всех тринадцати.

⚠ **Истина не здесь.** Кто у девушки в избранных, знает сайт, и круг сверяется с
его списком (`GET /users/my-favorites`), а не с этой таблицей. Таблица отвечает на
другой вопрос — **что мы пробовали и чем это кончилось**: список говорит «его там
нет», но не говорит, ходили ли мы за ним трижды и падали ли на входе (`api.md`,
§3.7.6).

⚠ **`state` различает два «он там есть»**: `done` — звёздочку нажали мы, `already` —
он был там до нас. Кругу разницы нет, оба значат «больше не ходить»; человеку есть —
по первому видно работу панели, по второму то, что было и так.

**`mailing`** — журнал (`site_id`, `profile_id`, `mail_id`, `uid`, `name`,
`body`). Ждёт круга рассылки: писать в него некому, пока письма не уходят.

⚠ **Отрендеренный текст хранится целиком, а не ссылкой на шаблон.** Шаблон правят:
сегодня в нём одно, завтра другое. Журнал же отвечает на вопрос «что человек
получил» — и ответ не должен меняться задним числом.

⚠ **Уникальный ключ `(profile_id, uid, mail_id)`** — это и есть «без дубликатов»:
одна анкета не пришлёт одному человеку один и тот же текст дважды. Другой шаблон
ему же можно (следующее письмо в переписке), тот же шаблон от другой анкеты — тоже.
Ключ в базе, а не проверка в коде: рассылка пойдёт кругом воркера, и проверка между
чтением и записью — это гонка.

⚠ **`mail_id` — `ON DELETE SET NULL`, а не `CASCADE`**: шаблон удалят, а журнал
останется. Отсюда следствие, которое стоит помнить: у строк с погибшим шаблоном
уникальный ключ перестаёт работать (в MySQL NULL не равен NULL). Это осознанно —
шаблона больше нет, и «то же самое письмо» стало неопределимым.

⚠ **`idx_dating_message_time` (`profile_id`, `sender_uid`, `created_at`, `id`)** —
индекс диалога **по времени**, помимо прежнего по `id`.

Карточка чата раскладывает собеседников по свежести последней реплики, и свежесть
считала по `MAX(id)`: автоинкремент совпадал с порядком событий, пока писал один
сокет. Импорт переписки из панели агентства (`dating.md`, §5.8) приносит историю за
неделю и кладёт её сегодня — **после** всего, что сокет успел поймать: в диалоге с
обоими источниками наибольший `id` оказывался у недельной давности реплики. Диалоги
сортировались наоборот, а значок «нужен ответ» загорался по старому сообщению.

Сортировать пачку при вставке недостаточно: внутри пачки порядок поправить можно, но
сама пачка ложится позже свежих сообщений сокета.

Цена измерена (21 762 реплики, 400 диалогов): `MAX(id)` — 9 мс и неверно;
`ROW_NUMBER()` по времени — 121 мс (и 118 даже с этим индексом — MySQL всё равно
сортирует); `MAX(created_at)` с ним — **29 мс** и верно.

Прежний индекс по `id` остаётся: он покрывает счёт реплик и дешевле на чтение.

**`dating_message.answer_silent_at`** — когда агент решил не отвечать на это
сообщение; `NULL` — такого решения не было (`dating.md`, §5.9.3). ⚠ Отдельно от
`is_answered`: тот означает «мы отправили ответ», и метить им молчание значило бы
врать в данных.

**`dating_profile.password_source`** — `site` или `own`: общий агентский пароль
сайта или свой у этой анкеты (`dating.md`, §5.12). ⚠ Умолчание `site`: своего пароля
не было ни у одной из 64 живых анкет, и `own` остановило бы разом всё.

**`dating_profile.schedule`** — смены суток, `[{"from":"07:00","to":"11:00"}]`
(`dating.md`, §5.9.4). `NULL` и пустой список значат «ведут руками», а не «всегда в
сети». JSON-колонкой, потому что смены читают только целиком.

**`dating_profile.can_work` и `work_reason`** — может ли панель сейчас работать с
анкетой и почему нет (`dating.md`, §5.10). ⚠ Не то же, что `enabled` (ведём ли) и
`status` (в сети ли): три признака про разное. Умолчание `0` — «готова» это вывод из
обстоятельств, а не состояние по умолчанию.

**`dating_profile.mailing_on`** — слать ли от анкеты рассылку писем. Колонку читает
**отбор списка** на «Профилях»: вкладка «Письма рассылка» показывает только анкеты
с этим флагом. ⚠ **А вот исполнителя у него нет:** круга рассылки в проекте не
существует, и поставленная галочка пока никому не поручает писать письма. Не ищите
его — его напишет отдельная задача, она же заведёт индекс.

⚠ Умолчание `0`, в отличие от `auto_answer` (`1`): показать включённой галочку у
функции, которой нет, значит соврать. Третий флаг ведения анкеты рядом с `enabled`
(ведём ли) и `auto_answer` (отвечает ли агент в чате) — все три про разное.

**`dating_message.source`** — `socket`, `http`, `panel` или `scenario`: живой
вебсокет, ручка чата самого сайта, журнал панели агентства (`dating.md`, §5.8) или
отправка сценарием у соседа (`dating.md`, §5.9). ⚠ **Не украшение, а два условия
сразу.**

⚠ **Значение `http` добавлено позже остальных, и это стоило разбора.** Столбец
знал три пути, а в коде их было четыре: HTTP-путь просто никем не был настроен.
В день, когда LadaDate перевели на его ручку `/chat-send`, каждое исходящее стало
писаться как `socket` — у сайта, у которого сокета нет вовсе. Мораль в том, что
столбец надо учить новому значению, а не подгонять путь под старое: третий вопрос
разбора («чем шло») отвечается тремя разными местами, куда идти смотреть.

Первое: **разные пространства номеров.** У сокета `message_uid` это ULID кадра, у
панели свой числовой номер; номера панели пишутся с приставкой (`panel:36594474`),
но в запросе приставку не напишешь, а `source = 'panel'` напишешь.

Второе, важнее: **импорт не должен запускать автоответ пачкой.** Автоответчик берёт
последнее неотвеченное входящее по собеседнику, и привезённая за неделю история для
него неотличима от свежей почты.

⚠ Прежде отбор исключал `source = 'panel'` целиком — это было верно, пока импорт шёл
кнопкой. Теперь у сайта без сокета панель единственный источник входящих, и запрет
означал бы «не отвечать вовсе». Вместо него — **порог по возрасту**: привезённое
отвечается, если пришло не позже суток (`dating.md`, §5.9.2). Столбец нужен и для
этого: без него «привезённое» от «пойманного сокетом» не отличить.

Умолчание `socket`, потому что все 25 тысяч прежних строк именно оттуда: умолчание
`panel` соврало бы про каждую, а `NULL` заставил бы каждый запрос помнить про
третье состояние, которого не бывает.

**`dating_error.source` + `site_id`** — ⚠ **уникальная пара, и в этом весь смысл
таблицы.** Она отвечает на вопрос «что сломано сейчас», а не «что ломалось»:
лежащий сосед даёт отказ на каждый показ страницы, и строка на каждый залила бы
таблицу тысячей одинаковых записей за час. Вместо этого растёт `hits`, а `first_at`
показывает, идёт это час или неделю. Удачная работа строку **стирает**.

**`setting.node_id`** — ⚠ **лишняя колонка, и это намеренно.** Узлов в этом проекте
нет и не планируется (узлы — хозяйство RhapsodyAi, где одна настройка бывает разной
на разных машинах). Держится потому, что её читает и пишет общий модуль
`py_modules/setting_/setting_.py` — один файл на оба проекта; убери колонку, и
`setting_get` упадёт на первом вызове. Внешнего ключа нет — ссылаться не на что,
значение всегда `NULL`.

**`dating_scenario_run.profile_id`** — NULL там, где анкеты нет: импорт и выгрузка
идут по сайту целиком. Внешний ключ с `SET NULL`, а не `CASCADE`, и это разница по
смыслу: удалили анкету — прогон остаётся. Он про то, что делали с сайтом, и вопрос
«почему импорт тогда развалился» переживает саму анкету.

**`dating_scenario_run.scenario_name`** — имя рядом с номером, а не вместо него: у
соседа сценарий могут переименовать или удалить, и тогда номер перестанет что-либо
значить. Имя — то, по чему прогон узнают через месяц.

**`dating_scenario_run.status`** — `sent`, `ok` или `error`. ⚠ **`sent` значит
«запрос ушёл, ответа ещё нет»**: строка пишется до прогона, а после него рядом
ложится вторая, с исходом. Строка `sent` без пары — зависший прогон, ради этого
случая отметка и заводилась.

**`dating_scenario_run.ms`** — сколько занял прогон. Ради него журнал наполовину и
заводится: «вход стал идти вдвое дольше» видно только рядом лежащими замерами.
**`step_no = 0` у отказа** значит не «встал на первом шаге», а «не начинался»: сосед
не ответил, вкладка не открывалась.

**`setting.user_id`** — настройка одного человека; страница «Значения» такие не
показывает, она про общие. **`setting.dynamic = 1`** — поставлено кодом, а не
человеком: это состояние, а не настройка, и править его руками нечего. Страница
прячет и такие.

**`dating_message.message_uid`** — идентификатор сайта. По нему же ловятся
повторы: сокет переподключается, и сайт шлёт неподтверждённое заново.

**`dating_message.answer_tried_at`** — когда агента спрашивали про это сообщение.
Отдельно от `is_answered`, потому что агент имеет право промолчать: пометить такое
«отвеченным» — обмануть оператора, а спрашивать заново каждую минуту — сжигать
деньги на LLM.

**`dating_profile.auto_answer_only`** — кому отвечать автоматически. Пусто — всем.
Ограничение нужно, потому что каждый ответ стоит денег дважды: прогон LLM и
платное сообщение на сайте. У анкеты с сотнями диалогов «отвечать всем» — это
рассылка, а не разговор.

**Автовосстановление входа** (`src/dating/dating_revive*.py`, подробности —
`dating.md`, §5.7) держит своё состояние в пяти полях:

| Поле | Смысл |
|---|---|
| `keep_online` | анкета под присмотром автомата; ставит успешный вход, снимает «Отключить» |
| `logged_in_at` | когда вход снят последний раз — от него считается профилактика |
| `relogin_since` | **тревога** — анкеты нет в сети; `NULL` — тревоги нет |
| `relogin_tries` | **откат** — сколько попыток сделано в текущей лестнице |
| `relogin_next_at` | **откат** — срок следующей попытки; `NULL` при сдаче |

`relogin_since` и пара `relogin_tries`/`relogin_next_at` — разные поля, а не одно,
потому и признак у них разный: тревогу видно по опросу прямо сейчас, а неудачу
входа — только по тому, что `logged_in_at` не подвинулся. Слить их значило бы либо
объявлять сдачу анкете, которая всё это время отвечала на сайте, либо звать
браузер соседа раз в минуту после каждой минутной отлёжки сайта.

## 5. Индексы, которые нужны не «на всякий случай»

**`dating_message (profile_id, sender_uid, id)`** (`idx_dating_message_dialog`) — по
нему живёт карточка анкеты. Оба её запроса без него вырождаются в перебор:
группировка переписки по собеседнице идёт через временную таблицу на все реплики
анкеты, а «последние десять реплик одной собеседницы» читаются обратным проходом по
первичному ключу. Замер на анкете с 400 диалогами и 22 тысячами реплик: 183 мс и
5.9 мс на каждый из пятидесяти показанных диалогов против 12 мс и 0.07 мс с
индексом. Порядок полей именно такой: `profile_id` и `sender_uid` берутся равенством,
`id` остаётся отсортированным — по нему и свежесть диалога (`MAX(id)`), и десяток
последних реплик без сортировки.

**`dating_message (profile_id, id)`** (`idx_dating_message_profile`) оставлен рядом: по
нему идёт переписка анкеты целиком, без разбора на диалоги.

Индекс догонялся до живой базы вручную — так делали, пока схему держал один файл.
Сейчас такой индекс завёлся бы обычной миграцией с меткой времени и до прода
доехал бы сам (`migration.md`, §1); тот файл туда и переехал —
`migrations/20260819144000_dating_message_dialog.sql` (`migration.md`, §2.3).
