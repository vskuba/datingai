# Работа с сайтом знакомств

Предметная часть: как устроен сайт, чем он отвечает и почему код выглядит так, а
не иначе. Знание добыто на живой установке — сохранено целиком, включая грабли.

**Что изменилось после переезда из RhapsodyAi.** Сам сайт и логика работы с ним
остались прежними; изменилось, откуда берётся браузер и агент:

| Было (внутри RhapsodyAi) | Стало (DatingAi) |
|--------------------------|------------------|
| `SELECT ... FROM browser_site` | `rhapsody_api_site_get(site_id)` |
| `SELECT ... FROM browser_scenario` | `rhapsody_api_scenario_find(...)` |
| `browser_scenario_run_one(...)` | `rhapsody_api_scenario_run(...)` |
| `browser_upstream_request(...)` | `rhapsody_api_session_*`, `rhapsody_api_ws_capture` |
| вставка строки в таблицу `agent` | `rhapsody_api_agent_create(...)` |
| `/chat/ask` своего сервера | `rhapsody_api_chat_ask(...)` соседа |

Названия настроек сайта (`presence`, сценарии по ролям) не изменились: они как
лежали в закладке сайта у соседа, так и лежат — просто приходят по HTTP.
Контракт — `rhapsody_api.md`.

## 1. Почему не браузер на каждую анкету

Замер на живом сайте: вкладка Chromium со страницей чата стоит **~143 МБ**, HTTP-клиент
с сохранёнными cookie — **единицы килобайт**. Двести анкет в первом виде это 29 ГБ,
во втором — 2,3 МБ. Поэтому разделение жёсткое:

| Что | Чем | Как часто |
|-----|-----|-----------|
| вход, чтение анкеты | браузер (сценарий) | раз в сутки, пока жив `storage_state` |
| присутствие, счётчики | HTTP с cookie | раз в 15 секунд |
| входящие сообщения | вебсокет из Python | пока держим соединение |

Адрес чат-сокета собирает JS страницы, в разметке его нет — он снимается браузером
один раз (`/browser/ws/capture`) и живёт в `dating_girl.ws_url`.

## 2. Настройка сайта: `browser_site.presence`

Что дёргать — настройка, а не код: у каждого сайта свои ручки, и вписывать их в
Python значило бы править код ради нового сайта.

```json
{
  "base": "https://goldenbride.net",
  "headers": {"Referer": "https://goldenbride.net/chat"},
  "heartbeat": {"path": "…", "body": "mode=setAuthUserOnline"},
  "status": [
    {"path": "…/chat/v26", "body": "mode=update_v2", "auth_field": "auth"},
    {"path": "/ladymodule/services/rpc", "body": "7|0|10|…", "ok_mark": "//OK",
     "headers": {"Content-Type": "text/x-gwt-rpc; charset=UTF-8"}}
  ],
  "unread": {"path": "…?requestType=LetterStats", "method": "GET", "field": "unreadMail"},
  "chat_url": "https://goldenbride.net/chat#!CHAT",
  "chat_ws_mark": "Red5Chat",
  "profile": {"path": "…?requestType=ManStats", "method": "GET", "field": "user"},
  "profile_scenario": "анкета девушки",
  "contacts": {"path": "…/chat/v27", "body": "mode=get_result_v2"},
  "send": {"transport": "ws", "frame": {…}, "ack": {…}}
}
```

**`status` — список, а не одна ручка.** На Goldenbride мужская анкета отвечает
JSON-ручкой, а женская живёт в другом модуле (`/ladymodule`, GWT-RPC) и на мужскую
отвечает `401`. Перебор идёт до первой удачной проверки; подошла любая — вход жив.

Как понять, что вход жив, задаётся тут же: `auth_field` — поле JSON, `ok_mark` —
метка в тексте (ответ GWT не JSON вовсе), ничего из двух — сойдёт код `200`.

## 3. Анкета: JSON у мужской, страница у женской

`presence.profile` — HTTP-ручка. Она есть у мужской учётки (`ManStats`), у женской
её **нет**: кабинет девушки собран на GWT-RPC и отдаёт бинарный поток. Проверено —
`LadyStats` и соседние имена возвращают `{"success":true}` без единого поля.

Поэтому анкета девушки читается **со страницы**, сценарием
(`presence.profile_scenario` → имя сценария в `browser_scenario` этого сайта).
Шаги `extract` складывают значения по именам, а имена совпадают с полями карточки:
`name`, `city`, `about`, `photo`, `age`, `id`. Новое поле в карточке — новый шаг в
сценарии, а не правка Python (`src/dating/dating_profile_page.py`).

Читается это редко: анкета меняется раз в месяцы, а браузер дорог. Поэтому чтение
прицеплено к входу и к проверке — там сессия уже открыта.

## 3.1 Мужской кабинет: чем он отличается

Мужской кабинет — приложение на React, женский — GWT, и различия не косметические:

| | женская анкета | мужская |
|---|---|---|
| анкета | со страницы сценарием | JSON-ручка `ManStats` |
| признак входа в чат | `.account-wrap-new` | кнопка `live chat` |
| перенос входа в новую вкладку | работает | **нет**: восстановленная из `storage_state` сессия показывает «sign in» |

Отсюда два правила. Первое: сокет мужской анкеты снимается **только в живой
сессии входа** — открыть чат по сохранённым cookie не выйдет. Второе: сценарий
входа заканчивается двумя необязательными ожиданиями (по признаку каждой роли) —
без этого перехват шёл раньше, чем вход завершался, и возвращал пусто.

## 4. Порядок входа

1. Гасим прежние сессии этой анкеты. Сайт держит **одну сессию на учётку**: второй
   вход выбрасывает первый, и две живые вкладки кончались тем, что обе теряли вход.
2. Сценарий входа — тот, что ждёт и логин, и пароль (`secrets`, мимо базы и журнала).
3. Сценарий анкеты. Он ждёт появления кабинета — то есть настоящего конца входа.
4. **Только теперь** снимаем `storage_state`. Нажатие кнопки «войти» ещё не сессия:
   снятое сразу после него состояние приходило без cookie сайта, и опрос честно
   отвечал «сайт не признал вход».
5. **Спрашиваем сайт, признал ли он вход** — опросом присутствия. Сценарий этого
   не скажет: его последние шаги (ожидания кабинета) обязаны быть необязательными,
   потому что кабинет у мужской и женской анкеты разный, и провалиться сценарий не
   может никогда. На неверном пароле он отчитывался успехом: сайт показывал «Bad
   credentials», карточка получала бесполезное состояние и выглядела рабочей до
   первой попытки что-нибудь отправить. Опрос годится обеим ролям — в отличие от
   чтения анкеты, сценарий которой заведён только для женской.
   Не признал — стираем `storage_state` и адрес сокета: держать cookie, по которым
   сайт не пускает, значит показывать в карточке вход, которого нет.
6. Снимаем **новый адрес чат-сокета** — в этой же вкладке. Токены в прежнем
   привязаны к прежней сессии, и после входа он мёртв. Без этого шага держатель
   вечно висел на мёртвом адресе: соединение выглядело живым, ошибок не было, а
   сообщения уходили в «пропущенные».

Пароль в `dating_girl.password` — не украшение: без него вход не пройдёт, а рабочая
сессия живёт лишь до истечения cookie. Учётка, заведённая с паролем-заглушкой,
работает, пока кто-то однажды вошёл руками, и умирает молча вместе с cookie.
Проверить пароль, не трогая базу, можно ответом сервиса входа: пустой ответ —
принят, `Bad credentials` — нет (тот же ответ и на несуществующий номер).

```bash
curl -s -X POST https://goldenbride.net/goldenbride/services/login \
  -H 'Content-Type: application/x-www-form-urlencoded; charset=UTF-8' \
  --data 'username=<номер>&userpass=<пароль>&doremember=true&requestType=login'
```

## 5. Чат: чтение и отправка

Входящие приходят кадрами `receivePrivateMessage` (тело — JSON внутри JSON).
Каждое подтверждается кадром `confirmFromClient`, иначе сайт пришлёт его снова;
повторы всё равно ловит уникальный ключ по `message_uid`.

Сервер здоровается первым (`connectFromServer`) и до этого кадра присланное
клиентом игнорирует. После приветствия страница спрашивает `getHistoryByContactIds`
и `getChatInfo` — то же делает и слушатель.

**Сообщение, пришедшее без живого соединения, в чат не возвращается.** Оно уходит
в раздел «Missed chat» кабинета — проверено: письмо мужчины дошло до сайта и
легло туда, а очередь чата осталась пустой (`notSendMessages: []`). Значит живой
приём возможен только пока сокет держат: HTTP-присутствие даёт «на сайте», но не
«в чате».

Поэтому сокеты держит воркер — см. §5.1. Прочитать пропущенное можно сценарием
«пропущенные сообщения (девушка)».

## 5.1 Воркер: постоянное присутствие в чате

`worker_dating` (очередь `dating`, `src/worker/dating/chat_worker.py`) держит
вебсокеты всех учёток со снятым входом. Одна смена — 6 часов, дальше job
завершается и его ставит заново тик `src/cronjob/dating_chat.py`; при старте
uvicorn смену поднимает `chat_worker_recover()`. От двух держателей на одну
анкету защищает single-flight: два соединения сайт вышибает оба.

Список учёток перечитывается раз в минуту прямо в смене — заведённая анкета не
ждёт следующей. Обрыв соединения обычен: пауза растёт с 5 до 60 секунд, а после
трёх неудач подряд адрес сокета переснимается браузером (не чаще раза в 10 минут —
каждый перехват это открытая вкладка).

Входящее пишется в `dating_message` и **сразу строкой в журнал** — от кого и
обрезанный текст. На карточке учётки счётчик непрочитанных пульсирует красным,
пока карточку не открыли: открытие помечает сообщения прочитанными
(`POST /api/dating/girl/{id}/read`).

Проверено на живой учётке: за час смена приняла и записала 711 сообщений.

**Молчащий сокет считается мёртвым.** Сайт сам шлёт `ping` каждые 15-20 секунд,
поэтому полторы минуты без единого кадра — это не затишье в чате, а оборванное
соединение, которого никто не оборвал. Живое наблюдение: соединение проработало
час, потом сайт перестал слать что-либо, разрыва не случилось, и учётка восемь
часов выглядела работающей, не принимая ничего. Теперь такое соединение
переподключается, а после трёх неудач подряд адрес переснимается.

**Смена следит и за адресом сокета, а не только за составом учёток.** Новый вход
выдаёт новый адрес; держатель, не заметив подмены, висел бы на прежнем — и снова
без единой ошибки.

Событие Cronicle — страховка, а не основной путь: обычная смена сама ставит
следующую. Тик нужен на случай, когда смена до этого не дошла (падение, убитый
контейнер):

```
POST /cronjob {"cronjob_path":"src/cronjob/dating_chat.py","timeout":60}   # раз в 5 минут
```

Ключ смены живёт 150 секунд и продлевается изнутри job'а. Иначе жёстко убитый
воркер запирал бы чат на все шесть часов: `finally` в таком случае не выполняется,
и снять ключ некому — проверено на себе.

## 5.3 Ошибки

Всё, что ломается на стороне дейтинга, идёт в общий журнал ошибок с источником
`dating` — вкладка «Ошибки» на `/admin/browser`: вход, чтение анкеты, перехват
адреса сокета, проверка, отключение, поломка чата в смене.

Опрос присутствия — исключение: он идёт раз в 15 секунд, и сотня учёток залила бы
вкладку одним и тем же за минуту. Поэтому в журнал пишется только **переход** в
нерабочее состояние, а текущее и так видно на карточке.

Отправка идёт **тем же сокетом** — HTTP-ручки отправки у сайта нет:

```json
{"toId": "…", "content": "…", "method": "sendPrivateMessage", "messageIdForConfirm": "…"}
```

Транспорт задаётся настройкой (`send.transport`: `ws` или `http`), шаблон кадра —
`send.frame` с подстановками `{{to}}`, `{{text}}`, `{{uid}}`.

**Соединение обязано согласовать подпротокол `chat`.** Браузер делает это
заголовком `Sec-WebSocket-Protocol`, и сервер отвечает тем же. Без подпротокола
сокет устанавливается, входящие приходят — а всё, что шлёт клиент, сервер
игнорирует **молча**: ни ответа, ни ошибки. Из-за одного этого заголовка все
отправки уходили в никуда, тогда как те же кадры со страницы доходили; на поиск
ушёл день, потому что ошибка не выглядела ошибкой.

Проверка простая: отправьте `getHistoryByContactIds` — с подпротоколом сервер
ответит `notSendMessages`, без него промолчит.

**Доставку подтверждает сервер.** На принятое сообщение он шлёт два кадра:
`confirmFromClient` (эхо) и `confirmFromServer` — вот он и есть подтверждение.
Останавливаться на первом значит принять эхо за доставку.

**Собеседника нет в чате — это состояние, а не ошибка.** Сайт отвечает
`offlineUser`; автоответ такое сообщение не помечает отвеченным и не пишет в
ошибки — собеседник вернётся, и ответ уйдёт тогда. В чате говорят с тем, кто в
чате: пока адресат не в нём, сообщение не принимается вовсе.

**Отказ сайт называет словами.** Методы разные (`limit`, `limitSecond`, …), но
текст общий — `Message not delivered` и причина: «Unacceptable words: …» от
фильтра содержимого (кириллица не проходит) или «You can send a second message
after 1 minute» от ограничения частоты. Узнаём по фразе, а не по перечню методов.

Порядок обязателен: дождаться приветствия сервера → открыть диалог
(`getHistoryByContactIds` с `content: "<uid>,"` — именно в `content`) →
`startTyping`/`stopTyping` → само сообщение с идентификатором-ULID.

Собеседников можно искать по номеру: в чате есть панель `MEN ONLINE` с поиском
`Search by Name, City, Id` — сценарий «найти собеседника в чате (общий)` этим и
пользуется.

## 5.2 Сценарии сайта: роль в названии

Мужской и женский кабинеты — это разные приложения на одном домене (React против
GWT), и половина сценариев для них не совпадает. Чтобы не выяснять это заново
каждый раз, роль пишется прямо в названии:

| Сценарий | Для кого |
|----------|----------|
| `вход (общий)` | форма входа одна на обе роли |
| `анкета (девушка)` | кабинет `/lady`, читается `presence.profile_scenario` |
| `открыть чат (девушка)` | вход в чат из женского кабинета |
| `пропущенные сообщения (девушка)` | раздел «Missed chat» |
| `найти собеседника в чате (общий)` | поиск по имени/городу/номеру в чате |
| `выбрать, кто написал мне (общий)` | открыть диалог из списка |
| `выход (мужчина)` | меню профиля мужского кабинета |

Новый момент работы — новый сценарий с ролью в имени, а не разовые шаги руками:
иначе то же самое приходится выяснять во второй раз.

Роль лежит у учётки (`dating_girl.role`: `lady` | `man`), а связка «роль → сценарий»
в настройке сайта. Строка означает «на все роли», объект — по ролям:

```json
"logout_scenario": {"lady": "выход (девушка)", "man": "выход (мужчина)"},
"profile_scenario": {"lady": "анкета (девушка)"}
```

Ключ `default` закрывает роли, которые не перечислили. Нет ни роли, ни `default` —
вызывающий скажет об этом сразу, а не потратит минуту на чужой сценарий, падающий
по таймауту. Ровно это и было: мужской учётке достался женский сценарий выхода и
честно упал через 62 секунды, а страница всё это время молчала.

## 5.3.1 Как это показано на странице

Диалогов у живой анкеты сотни, поэтому свёрнутый вид — основной. В строке ровно то,
по чему выбирают, что открыть: имя, время последней реплики, сама реплика кратко и
метка «нужен ответ». Открыт один диалог за раз; выбор переживает перерисовку
(страница обновляется каждые 15 секунд) и хранится в `localStorage`.

«Нужен ответ» — последнее слово осталось за собеседником (`needs_answer` в
`/api/dating/girl/{id}/profile`). Метка мигает: это единственная строка в панели,
означающая несделанную работу.

Переписка отдаётся последними десятью репликами **обеих сторон** в порядке
разговора. Раньше выбирались последние по номеру строки, а строки писались
«сначала все её, потом все наши» — в карточке оказывались одни наши.

Ширину колонки и высоту журнала тянут разделителями; обе величины — переменные
сетки (`--col`, `--log`) и запоминаются в `localStorage`.

Панель обновляется сама раз в 15 секунд — вместе со списком анкет и журналом.
Работу ведут воркеры в фоне, и требовать перезагрузки страницы, чтобы увидеть
свежий ответ, значит показывать вчерашнюю картину. Прокрутка и открытый диалог при
этом сохраняются: иначе чтение переписки сбрасывалось бы каждый круг.

**Список собеседников строится от переписки, а не от `dating_contact`.** В ту
таблицу попадают только те, кого сайт отдал списком «кто онлайн» (двести штук), и
диалог с человеком вне этого списка в панель не попадал вовсе — счётчик показывал
549, а баров было 59.

## 5.4 Отключение учётки

Кнопка «Отключить» (`POST /api/dating/girl/{id}/disconnect`): выход на сайте
сценарием `presence.logout_scenario`, закрытие всех вкладок этой анкеты, стирание
`storage_state` и `ws_url`. Переписка, журнал и анкета остаются — это «не веди её»,
а не «забудь». Вернуть в работу — кнопкой «Войти».

**Снятый вход и есть выключатель**: и держатель сокетов, и опрос присутствия берут
учётки с непустым `storage_state`. Отдельный столбец «включена» дал бы два
источника истины об одном и том же, и они бы разошлись.

Порядок обязателен: сначала выход на сайте, потом стирание состояния — наоборот
выходить будет нечем. Выход на сайте необязателен и провалом не считается: сайт
может не ответить, а отключить учётку надо именно тогда.

Сокет закрывается на ближайшей сверке смены, то есть в течение минуты.

## 5.5 Автовосстановление входа

Вход на сайт живёт около суток. Раньше его протухание не замечал никто: полный
опрос делала только открытая страница, а держатель шлёт голый heartbeat, который на
мёртвых cookie молча возвращает `False`. Анкета уходила из сети, сообщения ложились
в «Missed chat» безвозвратно, и узнавал об этом человек — когда открывал панель.

Теперь смена держателя раз в минуту опрашивает анкеты с пометкой `keep_online` и
сама чинит то, что выпало (`src/dating/dating_revive.py`: круг — `dating_revive_round`,
решение по одной анкете — `dating_revive_plan`).

Три поля `dating_girl` делят между собой две разные заботы, и путать их нельзя:

| Поле | Что означает |
|---|---|
| `relogin_since` | **тревога** — анкеты нет в сети. Мигает значком на карточке, через сутки становится «сдались». |
| `relogin_tries` + `relogin_next_at` | **откат** — не входить браузером чаще лестницы, повод (плановый вход или протухание) неважен. |

Тревогу гасит любое «в сети» в опросе — всегда, независимо от возраста входа.
Откат такое гашение переживает и сбрасывается только успешным входом: анкета
может отвечать на сайте по старым cookie, а обновить вход браузером не выходит
(капча, временная блокировка) — мигать тревогой тут незачем, человека дёргать не
о чем, но входить раз в минуту всё равно нельзя: вкладка Chromium у соседа не
бесплатная.

По той же причине **лестница начинается заново не по погасшей тревоге, а по
исчерпанности отката**: живой, ещё не наступивший срок попытки уважается, даже
если тревога успела погаснуть и зажечься снова. Иначе мигающий сайт (лёг →
встал на минуту → снова лёг) выбрасывал бы паузу, и входы шли бы чаще лестницы.

| Что увидели | Что делаем |
|---|---|
| в сети | тревога гаснет всегда; вход старше 20 часов — плановый вход, тревогу не зажигаем |
| не в сети, тревоги ещё нет | зажигаем тревогу; если срок отката ещё не истёк — ждём его, иначе лестница с начала |
| не в сети, тревога есть, срок отката не настал | ничего, ждём |
| не в сети, тревога есть, срок отката настал | входим браузером, откат — на следующую ступень |
| тревоге больше суток | сдача: попытки прекращаются, объявляется один раз |

Лестница пауз: **1, 5, 15, 45, 90 минут, дальше каждые два часа**. Успешный вход
обнуляет и тревогу, и откат.

Неудачный **плановый** вход (профилактика по сроку) тревогу не зажигает — анкета
и так отвечает, звать человека не о чем, — но двигает откат по той же лестнице:
без этого неудачная профилактика (сменили пароль, капча) ломилась бы в браузер
соседа раз в минуту.

Сдача объявляется **ровно один раз** — на том круге, что заметил переход, а не
на каждом последующем: иначе за сутки во вкладку «Ошибки» соседа набежали бы
полторы тысячи одинаковых строк.

`keep_online` ставит успешный вход, снимает «Отключить». Отдельным полем, а не
`storage_state IS NOT NULL`: неудачная проверка входа состояние стирает, и анкета
выпадала бы из-под присмотра ровно тогда, когда её надо чинить.

Входы идут по одному: каждый открывает вкладку Chromium у соседа. Смена в установке
одна, поэтому семафора в процессе достаточно.

Побочно чинится давний перекос: `status`, `unread` и `last_error` больше не зависят
от того, открыл ли кто-то страницу.

## 6. Кнопка «Проверка»

`POST /api/dating/girl/{id}/check` — полная проверка одной анкеты: вход → чат →
чтение → пробная отправка → закрытие. Каждый шаг пишет строку в `dating_log`, и по
журналу видно, где встало, без чтения кода. Первый упавший шаг останавливает
проверку — то же правило, что у шагов сценария и звеньев цепочки.

## 6.1 Агент анкеты

Отвечать в чате будет агент, а не человек, поэтому у каждой анкеты свой. Заводится
он сам — **последним** шагом «Проверки», и порядок здесь обязателен:

```
учётка (логин, пароль) → вход на сайт → чтение анкеты → биография → агент
```

Последним, потому что делает агента не запись в таблицу, а workflow
`dating_girl_create` через `POST /agent/create`, и на входе ему нужна биография:
из неё он добывает факты. Позвать его раньше чтения анкеты нечем.

| Что | Откуда |
|-----|--------|
| `name` | латиницей из имени анкеты + номер: `natalia_1430119` |
| узел | `Dating` |
| workflow агента | `dating_talk` |
| чем заводится | `dating_girl_create` — по роли (`DATING_AGENT_WORKFLOW_CREATE`) |
| `girl_bio` | имя, возраст, город и «о себе» из анкеты, склеенные в рассказ |
| `workflow_variable` | `{"girl_id": "<имя агента>"}` |

**Биография собирается из полей, а не берётся одним «о себе».** Сайт держит имя,
возраст и город отдельно, а в «о себе» пишут прозу вроде «я ценю честность» — из
неё одной проверяемых фактов не выйдет. Замер на живой анкете: 511 знаков
биографии → 25 фактов, 16 секунд.

**`girl_id` обязателен.** Коллекция `dating_girl` одна на всех, девушки в ней
разделены полем `document_id`, и фильтр собирается из `girl_id`. Без него агент не
может ни отложить придуманный на ходу факт, ни найти свой: он выйдет вторым сортом
— без фактов и с промптом из «о себе» вместо шаблона узла. Так и было, пока агент
заводился простой вставкой в таблицу.

**Факты принадлежат анкете, а не пользователю.** Фильтр — только
`{"document_id": "%girl_id%"}`. Раньше в нём стоял ещё и `user_id`, и это делало
девушку разной для разных учёток: факты, отложенные в разговоре под одним
пользователем, в разговоре под другим не находились, и анкета 43 лет из Харькова
отвечала «25, Kyiv» — по `girl_bio_example` узла. Разделения `user_id` при этом не
добавлял: `girl_id` — имя агента, уникальное на всю установку.

Поле `user_id` у факта осталось: оно говорит, кто факт создал. Но фильтровать по
нему нельзя — девушка одна, и помнить себя она должна одинаково, кто бы ни говорил
через неё: человек кнопкой «Ответить» или фоновый автоответ по `dating_auto_token`.
То же касается фактов о собеседнике и о разговоре — там разделение уже несёт
`document_id` (`%companion_name%` и `%girl_id%_%companion_name%`).

Роль решает, чем заводить: `dating_girl_create` лепит именно девушку. У мужской
анкеты своего workflow создания нет, для неё остаётся простая запись — агент без
фактов, и журнал говорит об этом прямо.

Номер в имени не украшение: имена на сайте повторяются десятками, а имя агента
уникально на всю установку. Кириллица переводится в латиницу — `наталья_1430119`
читается хуже и ломается в путях.

Существование проверяется **по имени**, а не по хранимой ссылке: агента могли
удалить или переименовать в админке, и единственный надёжный признак — есть ли он
сейчас. Повторная «Проверка» ничего не дублирует.

Снаружи то же самое делает `POST /agent/create` — по именам узла и workflow, а не
по номерам: номера разные на стенде и на проде, и клиенту их взять неоткуда.
Обязательное поле одно — `girl_bio` (см. `workflow.md`).

**Факты девушки ищутся по `document_id`.** Коллекция `dating_girl` общая на всех
анкеты пользователя, и без этого фильтра поиск отдавал факты чужой девушки — у
новой анкеты появлялся кот предыдущей. Фильтр живёт в шаге «Переменные»
workflow `dating_talk`.

## 6.2 Автоответ — основной путь

Анкета отвечает сама, пока подключена: смена держателя (`dating_chat_hold`) раз в
минуту обходит анкеты с `dating_girl.auto_answer = 1` и отвечает тем, чьё
сообщение осталось без ответа. Кнопка «Ответить» осталась запасным путём —
«сделай сейчас и при мне».

Переключатель — чекбокс в карточке, включён по умолчанию: анкету заводят, чтобы
она разговаривала. Включение сразу разбирает накопившееся, а не ждёт круга.

Токен для обращения к агенту — настройка `dating_auto_token` (значение —
`user_access_token` служебной учётки `dating_service`, у неё есть `dating:create`).
Тот же пользователь, что заводит анкеты руками через API, отвечает и фоном: две
разные учётки здесь означали бы две разные истории действий в журнале. Без токена автоответ
не работает: у воркера нет ни сессии, ни заголовков запроса, а заводить
«системного пользователя» мимо проверки прав значило бы открыть вторую,
непроверяемую дорогу к агенту.

Раз в минуту, а не чаще — ограничение сайта: «You can send a second message after
1 minute».

**Кому отвечать** — `dating_girl.auto_answer_only`: номера через запятую, пусто —
всем. Это не тонкая настройка, а защита кошелька: каждый ответ стоит и прогона
LLM, и платного сообщения. Проверено на живой учётке — включённый без ограничения
автоответ за четыре минуты написал шести собеседницам из шестисот.

**Роли не равны.** Разговор ведёт мужская анкета: она пишет первой и возвращается
после тишины дольше трёх минут. Женская только отвечает. Иначе разговор умирает на
первом же намеренном молчании агента: для собеседника оно выглядит как «не
ответила», и ждать от него следующего шага не приходится.

Проверено живым разговором двух своих анкет: восемь реплик подряд без вмешательства,
включая круг, где Наталья промолчала, а Семен через паузу написал снова.

Ожидание ответа движка автоответ поднимает до `chat_timeout: 240` вместо
умолчания в 60 секунд: живой workflow с несколькими шагами в минуту не
укладывается, и ответы срывались раз за разом. Перед экраном здесь никто не
сидит, поэтому ждать можно столько, сколько работа честно занимает.

Проверено замкнутым кругом внутри системы: обе анкеты (мужская и женская) заведены
на странице, мужчина шлёт через `POST /api/dating/girl/{id}/send`, женщина отвечает
сама, и её ответ приходит мужчине в его же `dating_message`.

## 6.3 Ответ собеседнику

Кнопка «Ответить» (`POST /api/dating/girl/{id}/answer`): взять неотвеченное,
спросить агента через `/chat/ask` и отправить сказанное в чат. Что именно
сказать, решает workflow агента — этот путь только доставка.

Ждут ответа те диалоги, где **последняя** реплика входящая и не помечена
отвеченной. Именно последняя, а не каждая: ответ закрывает переписку целиком.

**Пустой ответ — решение, а не сбой.** Агент может намеренно промолчать; тогда
сообщение помечается отвеченным, в чат не уходит ничего, и в итоге видно
`промолчал N`. Без этого анкета вечно висела бы в «нужен ответ» из-за реплики, на
которую отвечать нечем.

Права берутся у того, кто нажал: внутренний вызов идёт с заголовком авторизации
исходного запроса, а не со служебным токеном, который пришлось бы где-то хранить.

## 7. Таблицы

| Таблица | Что в ней |
|---------|-----------|
| `dating_girl` | учётка: логин, пароль, `role`, `storage_state`, `ws_url`, `status`, `profile` |
| `dating_message` | переписка; `direction` in/out, `is_answered`, `message_uid` |
| `dating_contact` | собеседницы: имя, фото, возраст, город, онлайн |
| `dating_log` | журнал по учётке: что делали и чем кончилось |

Пароль наружу не отдаётся никогда: в списке приходит только `has_password`.

**Журнал не копит повторы.** `dating_log_write` сравнивает текст с самой свежей
строкой этой учётки, и при совпадении прежняя удаляется, а новая встаёт с текущим
временем. Так «Неотвеченных сообщений нет» — одна строка со временем последней
проверки, а не столбец на весь экран: держатель сокетов ходит по кругу раз в
минуту, и за таким столбцом не видно настоящих событий. Сравнивается только текст;
`level` берётся у новой строки.

## Грабли

- **Второй браузер гасит первый.** Любое открытие страницы этой учётки где-то ещё
  (в том числе отладочный скрипт) обрывает живую сессию, и опрос начинает отвечать
  «сессия завершена». Одна анкета — одна вкладка.
- **Женские cookie не работают с мужскими ручками.** `401 Access denied` на
  `userApiV2` под женской учёткой — это не протухший вход, а другая половина сайта.
- **`profile` в `presence` требует своего поля.** Если `field` задан, а его в ответе
  нет — анкета не пишется. Иначе отказ (`{"error":…}`) прошёл бы как анкета и затёр
  бы ту, что прочитана со страницы кабинета.
- **Молчание сокета выглядит как исправная работа.** Ни ошибки, ни разрыва, ни
  единой строки в логе — учётка «онлайн», сообщений нет. Единственный признак —
  отсутствие даже серверных `ping`.
- **Без подпротокола `chat` приём работает, а отправка нет.** Самая дорогая
  ловушка этого сайта: половина связи исправна, вторая молчит без единого
  признака. Если сообщения «уходят», но их никто не получает — первым делом
  сверьте заголовки рукопожатия с браузерными (CDP-событие
  `Network.webSocketWillSendHandshakeRequest`).
- **`isMan` — не «наше эхо».** Поле говорит, мужчина ли написал. У женской анкеты
  входящие от мужчин помечены `isMan: true`, и фильтр «своё эхо» по этому полю
  глушил ровно те сообщения, ради которых всё и затевалось. Отличать своё надо по
  отправителю, а не по полу.
- **Пропущенное отдаётся только по запросу с номерами собеседников.** С пустым
  `content` сервер отвечает `notSendMessages: []`, будто ничего и не было; те же
  сообщения приходят, стоит перечислить собеседников через запятую.
- **Лишний уход со страницы ломает мужской кабинет.** Он держит вход в памяти
  страницы: заход на главную или `about:blank` перемонтирует приложение, и чат
  после этого не открывается вовсе. Поэтому перехват уходит со страницы, только
  если уже стоит на целевой (иначе событие подключения не возникнет).
- **Оставленная вкладка браузера ворует чат.** Сайт отдаёт сообщение одному
  соединению, и открытая страница чата — тоже соединение. Поэтому вход и чтение
  диалогов гасят вкладку за собой; чужие вкладки (в том числе у человека за
  экраном) дают тот же эффект.
- **`ok` у отправки — не «доставлено».** Пока не пришёл `confirmFromServer`,
  сообщения нет ни у кого. Отсутствие ошибки ничего не значит.
- **Отладочный вход через браузер убивает живой сокет.** Любой сторонний заход под
  учёткой обесценивает её `ws_url`, и держатель до полутора минут не знает об этом.
  Поэтому диагностику ведут либо через API входа (он адрес обновит), либо приняв,
  что чат на это время потерян.
- **Перезапуск `worker_dating` роняет смену, а ключ переживает её.** До
  переподключения проходит до двух с половиной минут (срок ключа) — если тика
  Cronicle нет, поднимать смену придётся руками.
