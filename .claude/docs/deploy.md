# Деплой на прод

## 1. Где живёт

Один сервер Oracle Cloud, тот же, что у RhapsodyAi (`ssh rhapsody-prod`), каталог
`~/datingai`. Прокси тоже его, а вот **имя своё**:

| Имя | Проект |
|-----|--------|
| `92.5.17.195.sslip.io` | RhapsodyAi |
| **`dating.92.5.17.195.sslip.io`** | **DatingAi** |
| `blog.92.5.17.195.sslip.io` | BlogAi |

Сертификат Let's Encrypt выпускается сам: sslip.io резолвит любое имя вида
`<что-угодно>.92.5.17.195.sslip.io` в тот же адрес, и отдельный домен покупать не
надо.

**Раньше домен был общим и делился по URI** — панель жила под `/dating`, а
`BASE_PATH` дописывал префикс в разметку. Со своим именем этого не нужно: панель
видна от корня, `BASE_PATH` пуст, и «локально в корне, на проде под префиксом»
как источника расхождений больше нет.

Старый адрес не умер: `92.5.17.195.sslip.io/dating*` отвечает постоянным
редиректом на новое имя — сохранённые закладки работают.

## 2. Чем прод отличается от локальной установки

Сервисов пять на обеих сторонах, и это новость: движки на проде **свои** с 26
августа. Раньше MySQL и Redis брались у соседа ради экономии памяти, и цену этой
экономии узнали 25 августа — сосед пересоздал свой MySQL, база `dating` и её
пользователь исчезли вместе с ним, прод три дня отвечал «Access denied» на каждый
вход. Заводились они там руками, один раз, поэтому пересоздание уносило их без
следа; `/health` при этом отвечал 200, и снаружи панель выглядела живой.

| | локально | прод |
|---|---|---|
| MySQL | свой `dating_mysql`, порт на хост (`MYSQL_PORT_HOST`) | свой `dating_mysql`, наружу не смотрит |
| Redis | свой `dating_redis` | свой `dating_redis`, база по номеру (`/1`) |
| phpMyAdmin | свой `dating_phpmyadmin` (`:9637`) | свой же, но порт на петле — доходят ssh-туннелем |
| адрес соседа | `http://uvicorn:8000` — имя контейнера | `https://92.5.17.195.sslip.io` — публичный HTTPS |
| общая сеть с соседом | нужна: адрес соседа — имя контейнера | не нужна и не подключается |
| `BASE_PATH` | пусто | пусто — у панели своё имя |
| порт наружу | `8021` на всех адресах | петля и шлюз `docker0` — снаружи только через Caddy |

Своя веб-морда к базе теперь нужна с обеих сторон: `dating` живёт в отдельном
контейнере и там, и там, и phpMyAdmin соседа до неё не дотягивается.

**Различий осталось два, и оба про связь, а не про состав:** каким адресом панель
зовёт соседа и нужна ли для этого его сеть. Прод ходит по публичному HTTPS и в
чужой сети не состоит вовсе; локально в `RHAPSODY_URL` стоит имя контейнера, и
накладка подключает `rhapsodyai_os-net` — без неё имя не резолвится, а без
поднятого соседа установка и не стартует (`quickstart.md`, §1).

### Какой файл что описывает

**`docker-compose.yml` — это прод.** Разница локальной установки вынесена в
накладку `docker-compose.override.yml`, которую compose подхватывает **сам**, без
`-f`. Отсюда одна и та же команда на обеих сторонах:

```bash
docker compose up -d     # локально — свои движки; на сервере — прод
```

Прод стоит базой, а не накладкой, намеренно: то, что применяется по умолчанию,
должно быть тем, что должно работать. Забыть флаг легко, и цена забытого флага —
«панель поднялась не той стороной».

Накладки **на сервере нет и быть не должно**: в репозитории лежит только образец
`docker-compose.override.yml.dist`, рабочая копия под ignore, `deploy.sh`
исключает её из архива, а обе выкладки сносят файл на сервере перед подъёмом.
Попади она туда — compose прочитал бы её молча, и прод поднялся бы со своим
пустым MySQL вместо базы соседа.

Обратная сторона: на машине разработчика копию надо один раз сделать (`cp
docker-compose.override.yml.dist docker-compose.override.yml`, см. `quickstart.md`).
Без неё локальный запуск пойдёт по прод-файлу и упрётся в чужую базу с
прод-паролем — заметно сразу, тихой порчи данных не будет.

## 3. Как выложить

```bash
./deploy.sh              # архив → сервер → сборка → перезапуск → проверка панели
./deploy.sh --no-build   # только код, без пересборки образа (быстро)
```

Скрипт делает четыре шага, **дожидается ответа панели** (до десяти попыток) и
**поднимает смену держателя сокетов**. Без первого «выложил» и «работает» — разные
события; без второго живой чат молчит до следующего перезапуска, о чём ниже.

Что он исключает из архива и почему: `.env.prod` (на сервере он свой — с паролем
базы, токеном соседа и ключом сессии; перезаписать его отсюда значит уронить прод),
`.git`, `py_modules/.git`, логи и `__pycache__`.

Адреса переопределяются переменными: `DEPLOY_HOST`, `DEPLOY_DIR`, `DEPLOY_PANEL_URL`.

## 3.1 Автовыкладка по пушу

`.github/workflows/deploy.yml` — выкладка на каждый пуш в `master`. Секреты
репозитория: `HOST`, `USERNAME`, `SSH_KEY` и `ENV_FILE` (содержимое `.env.prod`
целиком — пароль базы, токен соседа, ключ сессии).

Blue-Green здесь нет: панель не держит долгих запросов, и перерыв в пару секунд на
перезапуск незаметен. У соседа он есть потому, что там workflow-прогоны идут
минутами и обрывать их нельзя.

**Ручная выкладка остаётся рабочей.** `./deploy.sh` делает то же самое с машины
разработчика — она нужна, когда правку надо проверить, не выкладывая её в `master`.

⚠️ Для пуша файлов в `.github/workflows/` токену GitHub нужно право `workflow`:
`gh auth refresh -h github.com -s workflow`. Без него пуш отклоняется целиком, и
понять это по сообщению не сразу выходит.

Схема накатывается сама при старте (`mysql_migration_up`), первый пользователь —
из `ADMIN_USERNAME` / `ADMIN_PASSWORD` в `.env.prod`, если таблица пуста.

`.env.prod` в репозиторий не попадает: там пароль базы, токен соседа и ключ сессии.
На сервер он кладётся вручную, один раз.

## 4. Маршрут в Caddy

Прокси у RhapsodyAi, конфиг — `docker/caddy/Caddyfile` **в его репозитории**.
Два блока: своё имя и редирект со старого пути.

```
dating.92.5.17.195.sslip.io {
    reverse_proxy 172.17.0.1:8021 {
        lb_try_duration 90s
        lb_try_interval 2s
    }
}
```

**Адрес, а не имя контейнера, — и это развязка, а не мелочь.** По имени
`dating_uvicorn` Caddy ходил через общую сеть, и DatingAi приходилось в неё
включать; этой строкой сеть и держалась последней. `172.17.0.1:8021` — шлюз
`docker0`, тот самый порт, который панель на нём публикует. Не `0.0.0.0`: панель
не должна висеть на всех интерфейсах машины вторым, неохраняемым входом.

Ретраи не для красоты: при выкладке контейнер пересоздаётся и с полминуты не
отвечает — без них человек получил бы 502 вместо ожидания.

Внутри блока админки остался редирект со старого адреса:

```
handle_path /dating* {
    redir https://dating.92.5.17.195.sslip.io{uri} permanent
}
```

`handle_path`, а не `handle`: префикс **срезается до подстановки**, и `{uri}`
приходит уже без него. С `handle` префикс приклеился бы второй раз —
`dating.…/dating/admin/dating`.

⚠️ **Править надо файл в репозитории RhapsodyAi, а не на сервере.** Его выкладка
копирует каталог целиком и затирает серверные правки вместе с резервными копиями
рядом. На этом уже наступались, когда так же переезжал BlogAi.

Общая сеть для этого больше не нужна: на проде наши контейнеры в
`rhapsodyai_os-net` не состоят вовсе. Локально — состоят, но по другой причине и
только накладкой (§2).

## 5. Грабли, на которые уже наступили

**Bind-mount одного файла ломается при замене.** Caddyfile смонтирован файлом, а не
каталогом. Если файл на хосте **заменить** (`cat >`, `sed -i`, копирование), меняется
inode — и контейнер продолжает видеть старое содержимое. `caddy reload` при этом
честно отвечает «config is unchanged». Лечится перезапуском контейнера:
`docker restart caddy`.

**Backend в репозитории — не тот, что на сервере.** `bluegreen.sh` переписывает
`reverse_proxy` под активный слот (`uvicorn` ↔ `uvicorn_green`). Копировать Caddyfile
из репозитория поверх серверного нельзя: админка уедет на погашенный слот и повиснет
на 90 секунд ретраев. Править надо **точечно**, сохраняя текущую строку backend.

**`${REDIS_URL}` в `command` берётся не из `env_file`.** Compose подставляет
переменные из `.env` проекта, про `.env.prod` он не знает. Адрес должна разворачивать
оболочка внутри контейнера: `sh -c 'rq worker --url "$$REDIS_URL" dating'`.

**Выкладка теряет смену держателя сокетов.** Пересоздание контейнеров обрывает
текущее задание, но его ключ single-flight живёт ещё две с половиной минуты — и
`chat_worker_recover` на старте сервера, увидев занятый ключ, честно ничего не
делает. Задание к этому моменту уже мёртвое («AbandonedJobError»), новое никто не
ставит, и сокеты стоят: сообщения не приходят, отправка отклоняется как
«собеседник вне чата». Проверено на живом проде. Поэтому `deploy.sh` в конце ждёт
истечения ключа и ставит смену сам; повтор безобиден — single-flight отсечёт лишнее.

**`replicas: 0` не убирает зависимость.** Сервис гаснет, но `depends_on` на него
остаётся, и compose отказывается поднимать — «is missing dependency». Нужно снимать
и саму ссылку: `depends_on: !reset []`.
