# Изменение схемы

## 1. Правило

**Изменение схемы — новый файл в `migrations/`.** Применённые файлы не правят:
`yoyo` применяет каждый ровно один раз и помнит это в `_yoyo_migration`, поэтому
дописанный в старый файл `ALTER TABLE` не выполнится нигде, кроме установки с
нуля. Код новую колонку уже читает — и падает.

Накат идёт на старте сервера через `yoyo` (`mysql_migration_up`, общая
библиотека `py_modules`). Установка из чистого репозитория поднимается одной
командой — отдельного шага «накатить базу» не существует. Файлы применяются по
алфавиту имён, при каждом старте — только новые.

### Имя файла — метка времени

`YYYYMMDDHHMMSS_<что делаем>.sql`, например `20260101000000_initial_schema.sql`
(начальная схема) или `20260826135000_dating_profile_rename.sql`.

Почему так, а не `0001`, `0002`: миграции пишутся в ветках подзадач параллельно, и
номерами они столкнутся — две ветки заведут `0002.sql` с разным содержимым, и
слияние молча оставит одну. Метка времени уникальна сама по себе, а алфавитный
порядок имён совпадает с хронологическим — в нём `yoyo` их и применяет, ничего
дополнительно сортировать не нужно.

Тот же уклад в RhapsodyAi: движок там побайтно тот же, и два проекта незачем
разводить по укладу.

### Где посмотреть текущую схему

Не в одном файле. Текущая схема — **сумма файлов** в `migrations/` по порядку
имён; `20260101000000_initial_schema.sql` описывает только начало и заморожен.

Быстрый ответ даёт база: `SHOW CREATE TABLE dating_profile` — или phpMyAdmin
(«Инструменты»). Разменяли осознанно: цена — схема больше не читается одним
файлом, выгода — правка доезжает до прода сама, при старте, а не одноразовым
файлом по туннелю.

## 2. Как менять

1. Заводите `migrations/<метка времени>_<что делаем>.sql` с одним `ALTER TABLE`
   или `CREATE TABLE`. `DROP TABLE IF EXISTS` там не нужен и опасен: файл
   выполняется один раз, и «на всякий случай» здесь означает потерю данных.
2. Пересоздаёте контейнер: `docker compose up -d --force-recreate dating_uvicorn`.
3. В журнале старта обязано быть «Будет применено миграций: 1» и имя вашего файла.

Идемпотентным такой файл делать не надо — этим занимается `yoyo`. Требование
идемпотентности относится только к `data/migration_manual/` (§2.2), где файлы
гоняют руками.

## 2.1 Переименовать применённую миграцию — значит применить её заново

`yoyo` помнит применённое **по имени файла** (`_yoyo_migration.migration_id`), и
файл под новым именем для него новый. Для начальной схемы это `DROP TABLE` по
всей базе, то есть потеря всего.

Переименование обязано идти в паре с записью в журнал. Хеш там — sha256 **от
имени** миграции, а не от содержимого (`yoyo/migrations.py: get_migration_hash`),
поэтому запись считается точно и подделкой не является:

```python
hashlib.sha256('20260101000000_initial_schema'.encode()).hexdigest()
```

Проверить можно на живой базе: запись `0001` лежит там с хешем `888b19a43b15…`, и
это в точности `sha256('0001')`.

Пример — `migrations/20260826205700_yoyo_rename_initial_schema.sql` (сам он лежал
в `data/migration_manual/`, пока не переехал — см. §2.3). На проде такой файл
гонится **до** выкладки кода с переименованным файлом.

## 2.2 Живая база: ручной догон **данными**

`data/migration_manual/YYYY-MM-DD_<что>.sql` — про данные и про журнал самого
`yoyo`, а не про схему. Схему догоняет `yoyo` сам (§1), а вот перенос и починка
строк автоматически не случаются: seed применяется только к пустой базе, и на
проде он не доедет никогда.

Автоматически эти файлы не применяются — их гонят руками, локально и на проде.

Файл обязан быть идемпотентным: повторный прогон не должен ломать данные. В шапке
— зачем вручную, что меняется, что теряется и в каком порядке гнать относительно
выкладки кода.

**Каталога в репозитории сейчас нет, и это не отмена приёма.** Всё, что в нём
лежало, применено и записано, а пустых каталогов git не хранит — первый же новый
файл заводит его обратно. Отсутствие папки означает «ручных догонов на руках
нет», а не «так больше не делают».

## 2.3 Перенос ручных миграций в `migrations/` (30.08.2026)

Пять файлов из `data/migration_manual/` переехали в `migrations/` под именами с
меткой времени: колонки автовхода, индекс диалога, `user.role`, дописывание хоста
к фотографиям собеседниц и фиксация переименованной начальной схемы. Гоняли их
руками не по природе задачи, а по нужде: схему тогда держал один замороженный
`0001.sql`, и догнать живую базу было нечем. С метками времени эта нужда отпала.

**Перенести файл в `migrations/` — значит применить его заново**, ровно как
переименовать (§2.1): для `yoyo` имя новое. Поэтому порядок такой:

1. Убедиться, что изменение **уже стоит** на каждой живой установке. Смотреть
   базу, а не память: колонку — в `information_schema.COLUMNS`, индекс — в
   `STATISTICS`, правку данных — запросом, который считает битые строки.
2. Внести запись в `_yoyo_migration` руками, файлом из `data/migration_manual/`.
   Хеш — `sha256` от **имени** миграции (§2.1).
3. Только теперь выкладывать код с перенесённым файлом.

Сделано это файлом `data/migration_manual/2026-08-30_yoyo_move_manual.sql`. Сам
файл отработал на обеих установках и удалён (§2.2); что именно проверялось на
проде и с какими хешами вносились записи — в коммите `63f9b78` и ниже.

**Идемпотентность перенесённых файлов теперь не украшение, а второй рубеж.** На
установке с нуля они выполняются по-настоящему — и обязаны пройти вхолостую,
потому что всё, что они добавляют, уже есть в начальной схеме. Проверено чистой
базой: семь файлов подряд, ноль ошибок, второй старт применять нечего.

⚠ **Хеши для записи в журнал не считают на бумаге.** Правильный способ — поднять
чистую базу теми же файлами и снять хеши с журнала, который `yoyo` написал сам.
Совпадение с `sha256(имя)` тогда не предположение, а наблюдение.

## 3. Данные

Данные схемой не заводятся: в файле только структура. Учётки анкет заводятся
через панель или её API, пользователи — первым запуском (`auth_seed_first_user`).

Снять дамп перед накатом и залить его обратно можно **из самой панели**:
«Настройки → Backup» (`api.md`, §6). Оттуда же переносятся между установками
пользователи и учётки анкет — «Настройки → Seed SQL» (`api.md`, §5). Команды ниже делают то
же самое из терминала — они нужны, когда панель не поднимается.

Дамп рабочей базы:

```bash
docker exec dating_mysql mysqldump -udeveloper -ppassword \
  --default-character-set=utf8mb4 dating > dating_dump.sql
```

Восстановление:

```bash
docker exec -i dating_mysql mysql -udeveloper -ppassword \
  --default-character-set=utf8mb4 dating < dating_dump.sql
```

## 4. Грабли

**`--default-character-set=utf8mb4` обязателен.** Без него клиент MySQL показывает
`??????` вместо кириллицы — данные при этом целы, врёт только вывод.

**Для файлов из `data/migration_manual/` этот флаг не про вывод, а про то,
выполнятся ли они вообще.** Заголовки в них русские (`SELECT 'ДО' AS этап`), и без
флага клиент разбирает эти байты как испорченные — `ERROR 1064` на первой же строке,
а сам `ALTER TABLE` не выполняется. Ошибка уходит в stderr, поэтому прогон с
перенаправлением вывода выглядит успешным. Так уже терялся индекс: файл «прогнали»,
а в базе его не появилось. Правильно так:

```bash
docker exec -i dating_mysql mysql -udeveloper -ppassword \
  --default-character-set=utf8mb4 -t dating < data/migration_manual/<файл>.sql
```

После прогона — проверять глазами, а не по коду возврата: у каждого файла в конце
стоит `SELECT 'ПОСЛЕ'`, и он обязан показать то, что добавлялось.

**Порядок удаления таблиц важен.** Сначала зависимые (`dating_contact`,
`dating_log`, `dating_message`), потом таблица анкет. Иначе внешние ключи не дадут
уронить таблицу, и накат встанет на первом же `DROP`. Это про блок сносов в
начальном файле — в файлах изменений `DROP TABLE` не место (§2).

**В начальном файле таблица анкет называется `dating_girl`, и это не опечатка.**
Файл заморожен и описывает базу, какой она была на старте; в `dating_profile` её
переименовывает `20260826135000_dating_profile_rename.sql`. Установка с нуля
поэтому сначала создаёт `dating_girl`, а следующей же миграцией переименовывает —
так и работают миграции-довески.

То же и у четырёх файлов между ними (`202608180…`–`202608222…`): они писались до
переименования и говорят `dating_girl`, `girl_id`. Менять это в них нельзя —
по алфавиту имён они идут **перед** переименованием, и на установке с нуля
`dating_profile` в тот момент ещё не существует. Читать их надо по месту в
очереди, а не по нынешним именам таблиц.
