# Изменение схемы

## 1. Правило

Любое `CREATE TABLE` и `ALTER TABLE` — **только** в `migrations/0001.sql`.
Отдельных файлов миграций в проекте нет и заводить их не надо: файл описывает
базу целиком, и чтобы узнать её структуру, достаточно открыть один файл.

Накат идёт на старте сервера через `yoyo` (`mysql_migration_up`). Установка из
чистого репозитория поднимается одной командой — отдельного шага «накатить базу»
не существует.

## 2. Как менять

1. Правите `migrations/0001.sql` — там, где таблица создаётся.
2. Пересоздаёте контейнер: `docker compose up -d --force-recreate dating_uvicorn`.

Файл начинается с `DROP TABLE IF EXISTS` в порядке зависимостей и создаёт всё
заново. Это значит: **накат стирает данные**. На пустой установке это норма, на
рабочей — повод сначала снять дамп.

## 2.1 Живая база: ручной догон

`yoyo` применяет `0001.sql` **один раз** и запоминает это в `_yoyo_migration`.
Правка файла доезжает только до чистой установки: на локальной базе с данными и на
проде новых колонок от неё не появится, а код их уже читает — и падает.

Поэтому изменение существующей таблицы делается **дважды**: правка `0001.sql`
(источник схемы) и одноразовый файл `data/migration_manual/YYYY-MM-DD_<что>.sql`,
который догоняет живую базу. Автоматически такие файлы не применяются — их гонят
руками, локально и на проде.

Файл обязан быть идемпотентным: каждый шаг сверяется с `information_schema` и на
повторном прогоне ничего не делает. В шапке — что меняется и что теряется.

## 3. Данные

Данные схемой не заводятся: в файле только структура. Учётки анкет заводятся
через панель или её API, пользователи — первым запуском (`auth_seed_first_user`).

Дамп рабочей базы:

```bash
docker exec dating_mysql mysqldump -udeveloper -ppassword \
  --default-character-set=utf8mb4 dating > dating_dump.sql
```

Восстановление:

```bash
docker exec -i dating_mysql mysql -udeveloper -ppassword \
  --default-character-set=utf8mb4 dating < dating_dump.sql
```

## 4. Грабли

**`--default-character-set=utf8mb4` обязателен.** Без него клиент MySQL показывает
`??????` вместо кириллицы — данные при этом целы, врёт только вывод.

**Для файлов из `data/migration_manual/` этот флаг не про вывод, а про то,
выполнятся ли они вообще.** Заголовки в них русские (`SELECT 'ДО' AS этап`), и без
флага клиент разбирает эти байты как испорченные — `ERROR 1064` на первой же строке,
а сам `ALTER TABLE` не выполняется. Ошибка уходит в stderr, поэтому прогон с
перенаправлением вывода выглядит успешным. Так уже терялся индекс: файл «прогнали»,
а в базе его не появилось. Правильно так:

```bash
docker exec -i dating_mysql mysql -udeveloper -ppassword \
  --default-character-set=utf8mb4 -t dating < data/migration_manual/<файл>.sql
```

После прогона — проверять глазами, а не по коду возврата: у каждого файла в конце
стоит `SELECT 'ПОСЛЕ'`, и он обязан показать то, что добавлялось.

**Порядок удаления таблиц важен.** Сначала зависимые (`dating_contact`,
`dating_log`, `dating_message`), потом `dating_girl`. Иначе внешние ключи не дадут
уронить таблицу, и накат встанет на первом же `DROP`.
