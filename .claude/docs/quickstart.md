# Быстрый старт

## 1. Что нужно до запуска

Поднятый **RhapsodyAi**: без него панель откроется, но работать не сможет — вход
на сайт, ответы агента и адрес чат-сокета берутся оттуда. Проверить связь можно
после старта (см. раздел 4).

Общая сеть тоже его: `rhapsodyai_os-net` создаётся его `docker-compose`. Если
сеть не поднята, `docker compose up` здесь упадёт на её отсутствии — это не сбой
конфигурации, а честное «соседа нет».

## 2. Запуск

```bash
cp .env.dist .env                                              # заполнить RHAPSODY_TOKEN и SESSION_SECRET_KEY
cp docker-compose.override.yml.dist docker-compose.override.yml
docker compose up -d
```

Второй `cp` обязателен. `docker-compose.yml` описывает **прод** — движки там свои,
такие же, как здесь. Локальные особенности — публикация портов наружу, локальное
окружение вместо `.env.prod` и общая сеть с RhapsodyAi — лежат в накладке, которую
compose подхватывает сам. В репозитории от неё только образец:
под рабочим именем файл уезжал бы на сервер вместе с кодом, и прод поднимался бы
с пустой локальной базой. Без копии запуск пойдёт по прод-файлу и упрётся в чужую
базу — заметно сразу.

Машинные особенности правятся не в накладке. Пароли и адреса — в `.env.local`
(он читается поверх `.env` и в репозиторий не попадает), а **порты — в `.env`**:
их подставляет docker, который про `.env.local` не знает.

Схема накатывается на старте (`mysql_migration_up`): установка из чистого
репозитория поднимается одной командой, отдельного шага «накатить базу» нет.

Учётки заводятся тогда же — две, по числу ролей:

| Учётка | Откуда | Когда заводится | Что доступно |
|--------|--------|-----------------|--------------|
| администратор | `ADMIN_USERNAME` / `ADMIN_PASSWORD` | только если таблица пуста | всё: анкеты, seed, бэкапы, база |
| оператор | `DATING_USERNAME` / `DATING_PASSWORD` | если такого логина ещё нет | только анкеты |

Ни та, ни другая не «создать или обновить»: иначе правка пароля в `.env` молча
меняла бы его у живого пользователя, а забытый в образце `change-me` возвращался
бы после каждого перезапуска. Условия разные потому, что администратор — признак
свежей установки, а оператор появляется и на живой: роль добавили позже панели.

Про роли — `auth.md`.

Панель: `http://localhost:8021` (порт задаётся `UVICORN_PORT`).
phpMyAdmin к своей базе: `http://localhost:9637` (`PHPMYADMIN_PORT`), он же
открывается по ссылке в шапке панели («Инструменты»).

## 3. Переменные окружения

Полный список — в `.env.dist`, здесь только то, что нужно понимать.

| Ключ | Зачем |
|------|-------|
| `RHAPSODY_URL` | Адрес соседа: имя сервиса в общей сети, не `localhost` |
| `RHAPSODY_TOKEN` | `user_access_token` учётки `dating_service` в RhapsodyAi |
| `REDIS_URL` | **Именно URL.** Общая библиотека читает эту переменную и по умолчанию берёт `redis://redis:6379` — Redis соседа. Без явного значения смены держателя уходят в чужую очередь |
| `MYSQL_HOST` | `dating_mysql` — своя база, не соседа |
| `MYSQL_PORT` vs `MYSQL_PORT_HOST` | **Разные вещи.** Первый — порт, по которому к базе ходит приложение внутри сети (3306); второй — порт, который накладка публикует на хост. Подставленный вместо второго первый публикует 3306, то есть ровно тот порт, который на машине с чужими MySQL и занят |
| `SESSION_SECRET_KEY` | Подпись сессионной куки; на рабочей установке свой |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | Администратор: анкеты плюс seed, бэкапы и база |
| `DATING_USERNAME` / `DATING_PASSWORD` | Оператор анкет: только страница анкет и её ручки |
| `LOG_DIR` | Подкаталог `DATA_DIR` под `app.log`. **Пустое значение — не «по умолчанию»**: путь склеивается из двух ключей, и без него журнал ложится в корень `data` вперемешку с шаблонами и дампами |
| `PHPMYADMIN_PORT` | Порт своего контейнера с веб-мордой к базе (9634-9636 заняты чужими установками) |
| `PHPMYADMIN_URL` | Что открывает ссылка в шапке. Не выводится из порта: жмёт её человек в своём браузере, а порт на проде опубликован на петле — доходят ssh-туннелем (`deploy.md`, §2) |

Права токена в RhapsodyAi: `browser:view`, `browser:create` (водить браузер),
`agent:view`, `agent:create` (заводить агента анкеты). Больше не нужно.

### ⚠ Не всё настраивается окружением

Часть настроек живёт **в базе**, на странице «Настройки → Значения»
(`/admin/setting`, ручки — `api.md`, §6.2). Разделение простое: в `.env` то, без
чего процесс не поднимется (адрес базы, токен соседа, ключ шифрования); там — то,
что подкручивают на ходу.

**Первое, что стоит выставить после установки, — часовой пояс** (ключ `timezone`,
например `+3`). Умолчание — UTC, потому что в UTC живут и контейнеры, и база; пока
пояс не задан, панель показывает все времена в UTC, и человек видит их сдвинутыми
относительно своих часов. Это не поломка, а честное «показываем как есть».

## 4. Проверка после запуска

```bash
# сервисы
docker compose ps

# связь с соседом изнутри контейнера
docker exec dating_uvicorn python3 -c "
import asyncio
from src.rhapsody.rhapsody_api import rhapsody_api_site_list
print(asyncio.run(rhapsody_api_site_list()))"

# вход в панель
curl -s -c /tmp/c.txt -X POST http://localhost:8021/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<пароль>"}'

# список анкет
curl -s -b /tmp/c.txt http://localhost:8021/api/dating/profile
```

Смена держателя сокетов ставится сама при старте сервера. Проверить, что она
идёт:

```bash
docker exec dating_redis redis-cli get "chat_worker:flight"   # 1 — держатель работает
docker logs dating_worker --tail 20
```

## 5. Частые грабли

**«Сообщение не принимается: собеседник вышел из чата».** Присутствие в чате
держит воркер своим heartbeat. Если смена не идёт, сайт считает анкету вне чата и
отклоняет отправку. Смотреть `chat_worker:flight` и журнал воркера.

**Первое письмо не пришло.** Сообщение, отправленное до подключения сокета, лежит
в очереди сайта и забирается запросом истории по списку собеседников. У анкеты,
которой никто не писал, список пуст — поэтому он собирается и из `dating_contact`
(тех, кого сайт показал в чате), а не только из тех, кто уже писал.

**Изменения `.env` не подхватились.** `docker compose restart` сохраняет прежнее
окружение — нужен `docker compose up -d --force-recreate`.

**`docker compose up` падает с «port is already allocated».** На машине уже
что-то занимает порт из `.env`. Порты — машинная особенность: правятся в `.env`,
а не в накладке compose, которая одинакова у всех.

Именно в `.env`, а не в `.env.local`: подстановкой `${...}` в compose занимается
docker, и он читает только `.env` в корне проекта. `.env.local` знает питон, и на
порты, публикуемые контейнерами, он не влияет — проверено.
Занятость проверяется так:

```bash
docker ps --format '{{.Names}}\t{{.Ports}}' | grep <порт>
```

**Журнал лёг в корень `data`.** Значит `LOG_DIR` пуст: общая библиотека склеивает
путь из `DATA_DIR` и `LOG_DIR`, и пустой второй кусок даёт `data//app.log`.
Должно быть `LOG_DIR=logs` — журнал и ротация уходят в `data/logs/`.
