# Контракт с RhapsodyAi

## 1. Правило

Все обращения к соседу идут через `src/rhapsody/rhapsody_api.py` — и никак иначе.
Прямых `httpx.post` по коду быть не должно.

Причина не в аккуратности: адрес, токен, таймауты и разбор ошибок должны жить в
одном месте. Разбросанные вызовы означают, что половина кода ходит с одним
таймаутом, половина с другим, а при смене адреса чинить приходится в десяти
файлах.

## 2. Кем представляемся

Токеном служебной учётки `dating_service` (`RHAPSODY_TOKEN`), заголовком
`Authorization: Bearer`. Заголовки того, кто нажал кнопку в панели, наружу **не
пробрасываются**: пользователей этого проекта в RhapsodyAi нет, и представляться
там надо своей учёткой.

Права учётки в RhapsodyAi ровно под задачу:

| Право | Зачем |
|-------|-------|
| `browser:view` | читать закладки сайтов с их `presence`, список сессий |
| `browser:create` | гонять сценарии, заводить и гасить сессии, снимать адрес сокета |
| `agent:create` | заводить агента анкеты |
| `agent:view` | находить его потом по имени |

Токен не задан — функции бросают `RhapsodyError('не задан RHAPSODY_TOKEN')`, а не
падают в середине работы с непонятным следом.

## 3. Что спрашиваем

| Функция | Ручка соседа | Когда зовётся |
|---------|--------------|---------------|
| `rhapsody_api_site_get` | `GET /api/browser/site/{id}` | каждый раз, когда нужна настройка `presence` |
| `rhapsody_api_site_list` | `GET /api/browser/site?tag=dating` | селект сайтов на странице |
| `rhapsody_api_scenario_login_find` | `GET /api/browser/scenario` + детали | вход на сайт |
| `rhapsody_api_scenario_find` | `GET /api/browser/scenario` | анкета, диалоги, выход — по имени из `presence` |
| `rhapsody_api_scenario_find_by_id` | `GET /api/browser/scenario/{id}` | подстановки известного сценария перед прогоном |
| `rhapsody_api_scenario_run` | `POST /api/browser/scenario/{id}/run` | сам прогон в браузере |
| `rhapsody_api_session_open/close/list/state` | `/api/browser/session…` | жизнь вкладки |
| `rhapsody_api_ws_capture` | `POST /api/browser/ws/capture` | снять адрес чат-сокета |
| `rhapsody_api_agent_create` | `POST /agent/create` | завести агента анкеты |
| `rhapsody_api_agent_find` | `GET /agent/name/{name}` | найти его номер |
| `rhapsody_api_chat_ask` | `POST /chat/ask` | получить ответ в чате |
| `rhapsody_api_error_write` | `POST /api/browser/error` | строка во вкладку «Ошибки» соседа |

## 4. Четыре места, где контракт неочевиден

**Сценарий входа ищется по подстановкам, а не по имени.** Имя у каждого сайта
своё («вход (общий)», «login»), а вход всегда узнаётся по паре «логин + пароль» в
подстановках `{{...}}`. Список подстановок RhapsodyAi наружу не отдаёт, поэтому
каждый сценарий сайта читается целиком и подстановки считаются по шагам
(`rhapsody_api_scenario_keys`). Сценариев у сайта единицы, и делается это раз за
вход.

**Агент ищется точечной ручкой, а не списком.** `GET /agent/list` для
неполноправной роли отдаёт только агентов её узлов — служебной учётке приходит
пустой массив, и «агента нет» получалось на ровном месте. `GET /agent/name/{name}`
отвечает про одного агента, про которого имя известно. 404 от неё — это законное
«агента нет», а не сбой связи, и клиент превращает его в пустой словарь.

**Сайты спрашиваются с меткой `dating`.** В закладках соседа лежат не только сайты
знакомств: там же его собственная админка и рабочие стенды, и в селекте анкеты они
только мешали — завести учётку на админке нельзя. У закладки есть поле `tags`
(метки через запятую), запрос идёт с `?tag=dating`, и отбор делает сосед. Правило
«что считать сайтом знакомств» живёт там, где заводят закладки: новый сайт получает
метку в его админке и появляется здесь сам, без правки кода. Метка — константа
`RHAPSODY_API_SITE_TAG`, а не настройка: она обязана совпасть буквально с тем, что
лежит в чужой базе, и двум местам разъезжаться нельзя. Закладка без меток не попадёт
в список никогда — это осознанно, так «забыл пометить» видно сразу.

**`presence` берётся детальной ручкой.** В списке сайтов её нет: это простыня —
адреса ручек сайта, заготовки GWT-запросов, имена сценариев по ролям. Возить её в
каждой строке селекта незачем, поэтому `GET /api/browser/site/{id}` отдельно.

## 5. Ошибки

Всё, что не 2xx, и любой обрыв связи превращаются в `RhapsodyError` с текстом,
пригодным для журнала анкеты: «RhapsodyAi недоступен: …», «`/agent/create` → 409:
…». Код ответа сохраняется в тексте намеренно — 401 значит «протух токен», 404 —
«нет такой сессии», и это разные поводы для звонка.

Ручки проекта переводят такую ошибку в **502**: сосед не ответил — это не наша
внутренняя поломка и не вина того, кто нажал кнопку.

Исключение — `rhapsody_api_error_write`: она не бросает никогда. Сбой журнала не
должен ронять работу с анкетой; это то же правило, что и у остальных журналов —
упавшая запись хуже всего тем, что уносит с собой то, ради чего её писали.

## 6. Что делать, когда сосед меняется

Если в RhapsodyAi переименуют ручку или поменяют формат ответа, ломается **один**
файл — `rhapsody_api.py`. Это и есть цена, за которую держится правило из первого
раздела.

Появилась нужда в новой ручке соседа — сначала функция здесь, потом её вызов в
коде. Не наоборот: вызов, обходящий клиент, живёт до первой правки контракта.
