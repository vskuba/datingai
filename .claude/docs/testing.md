# Тесты

## 1. Как устроены

Сюита ходит **по HTTP в запущенную панель**, а не поднимает приложение в памяти.
Причина: половина того, что стоит проверять, живёт не в коде — сессия в куке, срез
префикса прокси, права на странице. Тест против объекта `app` их не увидит.

Значит перед прогоном панель должна работать:

```bash
docker compose up -d

# локально
ADMIN_PASSWORD=<пароль> .venv/bin/pytest tests/ -q

# против прода — у панели своё имя, префикса нет, `BASE_PATH` пуст как локально
ADMIN_USERNAME=admin ADMIN_PASSWORD=<пароль> \
  BASE_URL=https://dating.92.5.17.195.sslip.io .venv/bin/pytest tests/ -q
```

## 1.0 Группы: гоняем то, что задето правкой

Полная сюита идёт **три минуты**. Платить их после каждой правки в одном углу
проекта — верный способ проверять реже, чем следует, поэтому тесты разбиты на пять
групп по подсистемам. Маркеры объявлены в `pyproject.toml`, ключ `markers`.

| Группа | Что покрывает | Тестов | Время |
|--------|---------------|--------|-------|
| `mail` | почта: рассылка, входящие, ответы, шаблоны, переменные, избранные, собеседники | 578 | ~1:35 |
| `profile` | анкета: CRUD, вход и восстановление, расписание, присутствие, списки людей | 376 | ~22 с |
| `core` | общее: доступ, пользователи, настройки, сайты, дверь к соседу | 232 | ~34 с |
| `chat` | чат: сокет, кадры, диалоги, инвайты, импорт из панели, автоответ | 215 | ~30 с |
| `page` | страницы панели: вёрстка вкладок, шаблон работы, журналы, пейджер, время | 122 | ~14 с |

```bash
.venv/bin/pytest -m chat -q              # одна группа — полминуты вместо трёх
.venv/bin/pytest -m "chat or page" -q    # две сразу
.venv/bin/pytest tests/test_invite.py -q # один файл
.venv/bin/pytest tests/ -q               # всё, ~3 минуты
```

### ⚠ Почему было девять минут, а стало три

Сюита ходит по HTTP против поднятого приложения, и каждому тесту нужна сессия.
Брал он её **заново**: фикстура `auth_client` делала `POST /auth/login` перед
каждым тестом.

Замер объяснил всё: вход идёт **309 мс**, обычный запрос — **10 мс**. Разница не в
сети, а в `bcrypt`: пароль проверяется намеренно медленным хешем, и это правильно
для прода. Полторы тысячи тестов — полторы тысячи таких проверок, то есть почти
весь прогон уходил на проверку одного и того же пароля.

Теперь сессия открывается **один раз на прогон** и переиспользуется (`_СЕССИИ` в
`conftest.py`): кука подписанная, живёт час, а прогон идёт минуты. Клиент при этом
остаётся свой у каждого теста — у него свой пул соединений.

⚠ **Куку проверяем перед использованием** дешёвым запросом: длинный прогон мог её
пережить. Без проверки сюита падала бы `401`-ми на последних файлах, и причину
искали бы в правках, а не в часе жизни куки.

⚠ **Деление по предмету, а не по слою.** «Письма» — это и ручки, и круги воркера,
и агент у соседа: правят их вместе, значит и гонять надо вместе. Деление по слоям
(«роутеры», «воркер», «домен») заставляло бы гонять три группы на одну правку.

⚠ **`mail` вчетверо тяжелее прочих**, и это не перекос разметки: почта — самая
большая подсистема панели (семь кругов из пятнадцати, три пула, шесть таблиц).
Правишь только рассылку — есть `tests/test_mailing*.py`; правишь почту целиком —
полторы минуты честнее трёх.

### Когда группы мало

* **правка в общем месте** — `py_modules/`, `conftest.py`, схема БД, `auth`: задето
  может быть что угодно, гони всё;
* **не уверен, какую задел** — гони всё. Три минуты дешевле сорванной выкладки;
* **перед коммитом с выкладкой на прод** — полная сюита обязательна, как бы мала
  ни была правка. Группа экономит время внутри круга, а не заменяет проверку на
  выходе.

### Как размечать новые тесты

Группа ставится **файлу целиком**, строкой после импортов:

```python
import pytest

pytestmark = pytest.mark.mail
```

⚠ **После импортов, а не под докстрингом.** `pytestmark` ссылается на `pytest`, и
строка выше его импорта роняет сборку файла `NameError`. Многострочный импорт —
отдельная ловушка: строка, вставленная между его скобок, даёт `SyntaxError`, и
падает тогда **вся сюита**, а не один файл.

**Файл принадлежит ровно одной группе.** Тест на стыке подсистем идёт в ту, чей
контракт он стережёт: `test_favorite_mail.py` проверяет, кому и как часто писать, —
это про почту, хотя список людей берётся из избранных.

Новый файл без маркера не запустится **ни в одной** группе — молча. Проверить, что
таких нет:

```bash
.venv/bin/pytest -q --collect-only \
  -m "not mail and not chat and not profile and not page and not core"
```

Ответ `no tests collected` — все размечены.

### ⚠ Имя теста — латиницей, и это не вкусовщина

Правило общее (`docs-common/code_rules.md`, §«Имена — только латиницей») и на тесты
распространяется наравне с кодом: `pytest -k` по кириллическому имени требует
переключать раскладку посреди команды, а привычный отбор по латинской подстроке
такое имя не найдёт вовсе. Транслитерация запрет не обходит — **имя переводится
словами**, а префикс берётся от проверяемого модуля:

```
test_сайт_с_забором_попадает_в_круг  ->  test_mail_in_round_takes_site_with_check_on
test_пустой_обход_молчит             ->  test_mail_in_round_empty_pass_writes_nothing
```

Именно здесь долг и набегает: 48 кириллических имён из 53 по всему проекту жили в
`tests/`. Проверка — та же, что в общем файле, вывод обязан быть пустым:

```bash
grep -rnP "^\s*(async\s+)?def\s+\w*[а-яА-ЯёЁ]|^\s*class\s+\w*[а-яА-ЯёЁ]" \
  --include=*.py . | grep -v "\.venv\|__pycache__"
```

⚠ Она смотрит только `def` и `class`. Локальные переменные и **имена параметров
`parametrize`** (`@pytest.mark.parametrize('час, в_сети', …)`) она не ловит, а
правило на них распространяется тоже — argnames лежат строкой, и переименование
функции их не тронет.

## 1.1 Окружение: `.venv`, а не системный питон

Сюита гоняется **из `.venv`**. Причина в юнит-тестах: они импортируют `src/` и
`py_modules/` напрямую, а значит требуют тех же пакетов, что и приложение —
`python-json-logger` тянется через `logging_`, `websockets` через чат. Системный
питон этой машины закрыт для установки (PEP 668), и складывать в него пакеты
проекта незачем.

```bash
uv pip install -r docker/uvicorn/requirements.txt -r requirements-dev.txt
```

Два файла, а не один: `docker/uvicorn/requirements.txt` едет в образ панели, и
pytest в проде не нужен никому. Тестовое живёт в `requirements-dev.txt`.

⚠ Без этого юнит-тесты **не собираются**, и `pytest tests/` падает целиком — не
одним файлом, а сборкой всей сюиты. Так и было: тогдашний `test_contact_photo.py` месяцами
не запускался, потому что на хосте не оказалось одного пакета.

| Переменная | Зачем |
|------------|-------|
| `BASE_URL` | куда стучаться; префикс, если он есть, уже внутри адреса |
| `BASE_PATH` | что должно быть **написано в разметке**. Сейчас пусто и локально, и на проде: панель везде живёт в корне. Задавать его надо, только если панель снова выставят под префиксом |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | учётка администратора; пароль в репозиторий не кладём |
| `DATING_USERNAME` / `DATING_PASSWORD` | учётка оператора — ею проверяется, что админское закрыто |

Разделение `BASE_URL` и `BASE_PATH` не педантизм: первый отвечает за «куда идти»,
второй — за «что ожидать в ссылках». Спутать их легко, и тест статики на этом уже
спотыкался, прося `/dating/dating/static/...`.

⚠ **Сюита ходит под теми же учётками, что и человек** — вопреки общему правилу
(`docs-common/testing_rules.md`, §3: отдельная полноправная учётка, не админская).
Причина в том, что заводить её было бы неоткуда: третьей роли нет, а вторая
полноправная учётка — это ровно то, чего не даёт здешняя модель ролей
(`auth.md`, §7). Цена известна и принята: по журналу не отличить прогон сюиты от
работы человека. Появится третья роль — заведётся и учётка сюиты.

Отсюда же требование к самим тестам: **они убирают за собой**. Учётки анкет
заводятся со случайным логином и удаляются в конце; проверки по посеянным данным
пропускаются, если посева нет. Сюиту гоняют и по проду, где чужого следа
оставаться не должно.

## 1.2 ⚠⚠ Наружу сюита не ходит вовсе — и живого HTTP в ней не бывает

> **Правило без исключений: в тестах используется только поддельный HTTP.**
> Настоящий клиент не создаётся и настоящий запрос не уходит — ни к соседу, ни к
> сайту знакомств, ни куда бы то ни было ещё, кроме самой панели. Нужен внешний
> вызов — значит нужна заглушка; заглушки нет — значит тест писать нельзя.

Разрешена ровно одна живая дверь: **сама панель** (`BASE_URL`). Через неё сюита и
работает — часть тестов ходит в неё по HTTP, это документировано в §1. Всё
остальное обязано идти через подделку.

**Ни один тест не зависит ни от одной внешней системы.** Ни от соседнего проекта,
ни от сайта знакомств, ни от чего-либо ещё за пределами этой установки. Правило без
исключений, и держится оно на трёх причинах:

* **тест против чужой системы проверяет не нас.** Он краснеет от чужого
  перезапуска, от занятого пула вкладок, от переименованного сайта — и молчит про
  то, ради чего написан;
* **он пишет в чужую систему.** Прогон сценария занимает вкладку в пуле соседа,
  общем с его задачами; вход в API сайта знакомств — действие под живой анкетой, а
  частые заходы сайт считает подозрением и отвечает блокировкой. Блокировка стоит
  анкеты, а не запроса;
* **важное им не проверить.** Занятый браузер, протухший токен, оборванная связь,
  «сайт просит подождать» — ждать этого в нужную секунду нельзя, а с заглушкой это
  строка в тесте.

Так и было: `test_rhapsody_link.py` утверждал `assert sites, 'сосед недоступен?'`,
`test_work_template.py` брал номера сайтов из его списка, а `test_import_api.py`
опирался на то, что у сайта №19 «сценария импорта заведомо нет» — то есть покраснел
бы в день, когда сценарий там заведут. За один прогон сюита слала соседу **47
запросов**.

Теперь наружу ведут две двери, и у каждой своя заглушка:

| Что за дверью | Модуль | Заглушка | Фикстура |
|---------------|--------|----------|----------|
| RhapsodyAi: сайты, сценарии, агенты | `src/rhapsody/rhapsody_api.py` | `tests/rhapsody_fake.py` | `rhapsody` |
| API сайта знакомств: вход, списки, письма | `src/dating/dating_site_api.py` | `tests/site_api_fake.py` | `site_api` |

Появится третья — заглушка пишется тем же приёмом и по тем же правилам.

⚠ **Заглушка сайта подменяет транспортный модуль, а не того, кто зовёт ручку.** За
дверью сайта теперь двое: списки собеседников (`dating_people_api.py`) и отправка
писем (`dating_mail_send.py`), а вход и токен у них общие — в `dating_site_api.py`.
Подмени заглушка одного из вызывающих, второй ходил бы на живой сайт.

### ⚠⚠ Отправка писем: наружу не уходит ни одно

`POST /messages/send` — действие **необратимое**: письмо получает живой человек,
отменить его нечем. Это самый дорогой внешний вызов в проекте, дороже входа
браузером: тот стоит блокировки учётки, этот — полусотни писем незнакомым людям от
имени агентства.

Поэтому весь разговор об отправке (`test_mail_send.py`) идёт через заглушку, и
проверяется в нём то, что и ломается: **порядок двух шагов** (`CheckId` живёт десять
секунд), что уезжает в теле запроса, что ложится в базу и что неудача не сжигает
письмо.

Живой отправки в сюите нет и быть не должно. Её проверяет человек — точечно, кнопкой
на карточке письма.

Заглушка при этом **проверяет разрешение**, как живой сайт: письмо с чужим `CheckId`
она отвергает. Без этого тест «сперва спросили разрешение, потом отправили» проходил
бы и на выдуманном значении, то есть не значил бы ничего.

### Приём один на обе: подменяется HTTP, а не функции

Заглушка встаёт на **транспорт httpx внутри самого модуля** (`httpx.MockTransport`),
подменяя в нём имя `httpx`. Две причины, и обе существенные:

* **модуль остаётся под проверкой целиком** — как строится путь, как уезжает метка
  и токен и, главное, как код отказа превращается во фразу («409 → браузер соседа
  занят», «403 → сайт просит подождать»). Подмени мы `rhapsody_api_site_list` или
  `dating_people_api_rows`, всё это осталось бы непроверенным ровно там, где живут
  отказы;
* **точка подмены одна.** Функции двери к соседу разошлись по десятку модулей и
  импортированы по имени, так что подменять пришлось бы в каждом импортёре — и
  первый забытый молча пошёл бы к живому.

Глобально `httpx.AsyncClient` подменять нельзя: сломался бы сам тестовый клиент,
который ходит в панель.

### Что заглушки дают

Готовые положения — методами: у соседа `refuse(409, …)`, `offline()`,
`forget_scenarios()`; у сайта `refuse(403, …)`, `offline()`, `expire_token()`. Что
у них лежит — полями (`sites`, `scenarios`, `run`; `users`, `password`). Что у них
спросили — `calls`: по нему проверяется «вошли один раз, а не на каждый список».

### Три рода тестов и что каждому нужно

| Род | Что нужно поднять | Кто так написан |
|-----|-------------------|-----------------|
| по HTTP в панель | панель и база | вход, права, страницы, отказы до входа в обработчик |
| обработчик в процессе | база (порт из `MYSQL_PORT_HOST`) | всё, что ходило бы наружу: анкеты, настройки сайта, снимок списка, списки собеседников |
| чистый юнит | ничего | разбор кадров, правила автовхода, сборка SQL, разбор карточек |

Файл может смешивать роды — и обычно смешивает: `test_profile_crud.py` заводит
анкеты в процессе, а «закрыто без входа» проверяет по HTTP. Это не небрежность:
каждую проверку ставят туда, где она **проверяет то, что назвала**.

### Правило для новых тестов

**Ручку, которая ходит наружу — к соседу или на сайт знакомств, — по HTTP не
дёргают.** Панель живёт в контейнере, и подменить в ней что-либо снаружи нельзя,
поэтому такие ручки зовутся **в процессе**, с фикстурой `rhapsody` или `site_api`.
По HTTP у них проверяется только то, что решается до входа в обработчик: вход и
права.

⚠ **Это расхождение с общим правилом** (`docs-common/testing_rules.md`: сюита
интеграционная, по HTTP, против поднятого приложения), и принято оно осознанно.
Общее правило исходит из того, что неподменяемых внешних зависимостей у приложения
нет; здесь их две, и обе — чужие рабочие системы. Выбор был между «тест ходит в
чужой проект» и «тест зовёт обработчик в процессе»; второе честнее.

Пересмотреть стоит, если у сюиты появится своя установка панели с поддельным
соседом рядом: тогда всё вернётся на HTTP без потери изоляции.

Проверять это глазами не надо: заглушка отвечает 404 на всякий путь, которого не
знает, — тест, ушедший не туда, узнает об этом сразу.

### ⚠ Правило без исключений: внешний вызов обязан иметь заглушку

**Любое обращение за пределы своей установки подменяется — всегда.** Сосед, сайт
знакомств, чей угодно API, любой адрес в интернете: если код тестируемого пути
куда-то идёт, у этого пути должна быть заглушка. Не «желательно», не «где
возможно» — всегда.

Появился новый внешний вызов — сперва заглушка, потом тест. Не наоборот: тест,
написанный без неё, проходит и молча ходит наружу.

### ⚠⚠ Круг в тесте обязан быть сужен до своей строки

Заглушки внешних вызовов мало. **Круг перебирает базу сам**, и база у сюиты одна с
людьми: `_rows` берёт все анкеты с включённым расписанием, `_sites` — все сайты.
Подменённое действие (вход, набор, зачистка) применится к каждой найденной строке,
и живая пострадает наравне с пробной.

Ошибка стоила данных **дважды**, и оба раза выглядела безобидно:

| Что случилось | Чем чинили |
|---------------|------------|
| круг шаблонов снёс пять написанных руками писем на живом сайте | `_sites` сужен до выдуманного |
| круг расписания записал живой анкете поддельный `ws_url` — та потеряла сессию и **перестала входить вовсе**: настоящий круг видел «уже в сети» и не трогал её | `_rows` сужен до пробной |
| круг забора писем обошёл тринадцать живых анкет Ladadate: `mail_check_on` включён у сайтов **по умолчанию**, и выдуманный сайт от живого ничем не отличался | `_sites` сужен до выдуманного |

⚠ Третий случай стоит помнить отдельно: там подмена действия сработала, наружу не
ушло ничего — но проверка «круг этот сайт не взял» считала чужие строки, то есть
отвечала не на свой вопрос. **Выключатель, включённый по умолчанию, делает это
правило обязательным**: пока новая колонка стоит в нуле, забывчивость незаметна.

Оба первых раза тест при этом **зеленел**. Второй же вдобавок начал падать, но не сразу и
не из-за поломки кода: человек включил расписание живой анкете, и та попала в счёт
`checked` — то есть о беде сообщила случайность, а не проверка.

**Правило:** тест, зовущий круг, подменяет его **отбор**, а не только действие.
Сужай там, где круг решает «кого брать» (`_rows`, `_sites`), и тогда чужого он не
увидит физически. Подмена одного лишь действия оставляет перебор нетронутым — и
это ровно тот случай, когда заглушка есть, а беда всё равно происходит.

Проверяется просто: прогони файл трижды подряд и посмотри на живую строку до и
после. Не изменилась — сужение на месте.

#### ⚠⚠ Сужать — значит **задать** отбор, а не отфильтровать живой

Фикстура, которая зовёт настоящий `_sites()` и оставляет из ответа свой номер,
выглядит сужением, но им не является: она по-прежнему зависит от строки сайта в
базе. А строку правит **фоновая сверка снимка** (`dating_site_sync`) — она
спрашивает у соседа список с меткой `dating`, выдуманного номера там не находит и
честно метит его `is_gone = 1`. Заводится сверка от любого показа списка сайтов,
не чаще раза в полминуты, — за трёхминутный прогон срабатывает несколько раз.

Фикстура сайта метку снимает, но **один раз, при подготовке**. Попади сверка в
промежуток между ней и вызовом круга — круг не увидит сайта вовсе, и тест упадёт
на «анкета не попала в круг», хотя круг отработал верно.

Так и вышло: `test_mail_in_round_ignores_schedule` падал раз на шесть полных
прогонов и был зелёным в одиночку. Причина проверена прямо: после
`dating_site_sync_now()` настоящий `_sites()` перестаёт возвращать стенд.

```python
async def ours():
    return [{'site_id': SITE}]        # ✅ задали

    return [row for row in await original() if row['site_id'] == SITE]   # ❌ отфильтровали
```

⚠ **Тесты про сам отбор такую фикстуру не берут.** «Снятый выключатель», «ушедший
сайт» — это вопросы к `_sites()`, и спрашивать их надо у него, а не гонять круг с
подменённым списком: подмена отвечала бы на «взял ли круг то, что мы ему дали».
Рядом с парой «не берёт» держите «берёт»: без неё обе зеленели бы и у отбора,
который не берёт никого вовсе.

### ⚠⚠ Тест не спрашивает, который час

Прогон в 23:50 обязан давать то же, что прогон в полдень. Иначе сюита **лжёт**:
зелёная днём и красная вечером, она перестаёт быть ответом на вопрос «сломал ли я
что-нибудь» — а именно этот вопрос ей и задают перед выкладкой.

Поймано живьём, и дорого: двадцать три теста в четырёх файлах покраснели разом в
23:47. Причина — одна строка, повторённая копипастой:

```python
ALWAYS = [{'from': '00:00', 'to': '23:45'}]   # ⚠ «во все сутки», кроме 15 минут
```

Смену задумывали круглосуточной, «чтобы проверка не зависела от часа прогона», — и
оставили дыру ровно перед полуночью. Полчаса ушло на поиск причины **в своих
правках**, которых там не было.

Правильных приёмов два, и оба дешёвые:

| Приём | Когда | Пример |
|-------|-------|--------|
| **подменить часы** | круг читает время сам | `monkeypatch.setattr(rnd, '_minutes_now', lambda offset: 9 * 60)` |
| **считать от «сейчас»** | подменять нечего | `hour = (time.gmtime().tm_hour + 6) % 24` — заведомо чужой час |

⚠ **Постоянное время в тесте — всегда ошибка**, даже когда «оно точно не наступит»:
оно наступит. Если смена должна быть круглосуточной — это `00:00–24:00`, а не
«почти»: правая граница строгая (`from <= minutes < to`), и 1440 включает последнюю
минуту суток.

### ⚠⚠ Общий счётчик стенда — источник плавающих отказов

Тест, зовущий круг, зависит не только от своих строк. `send_max_day` считает **все**
письма стенда, ушедшие сегодня, — включая оставленные другими файлами сюиты: они
бегут раньше по алфавиту и убирают за собой только своё. Наберётся сорок, и круг
молча перестаёт отправлять.

Выглядит это как загадка: полный прогон краснеет раз из трёх, файл поодиночке
зеленеет всегда, а сообщение — голое `assert 0 == 1`.

Правило: **тест, которому нужна работа круга, снимает общий предел** (подменяет
`_max_day` в фикстуре), а тест **про сам предел** задаёт его себе обратно, точечно
и на виду.

⚠ Проверять такую правку надо **набивкой счётчика**, а не повторным прогоном:
зелёный прогон ничего не доказывает, если условие не воспроизведено. Здесь это 45
строк «ушло сегодня» — с ними прежний файл валился тремя тестами, поправленный
проходит целиком.

### Три сторожа в `conftest.py`, и все три обязательны

Обещание здесь не работает: заглушку забывают, а **забытая заглушка не видна** —
тест зеленеет, просто идёт к чужой системе и делает там работу. Поэтому проверяют
не глаза, а код.

#### ⚠⚠ Сторож HTTP (`no_outside_http`) — главный

Подменяет **транспорт httpx** (асинхронный и синхронный) и `websockets.connect` на
весь прогон и падает на попытке уйти куда-либо, кроме панели.

Две особенности, и обе выстраданы:

**Ставится на HTTP, а не на сокет.** Сокет — слишком низко: туда ведут разные пути
(httpx, вебсокеты, свои клиенты), и каждый новый надо вспомнить. Транспорт httpx —
одна дверь на все клиенты процесса.

**Ставится на весь прогон (`scope='session'`), а не на тест.** Часть работы уходит
в **фоновые задачи**, которых тест не ждёт: ручка списков собеседников не ждёт
прогона никогда (`dating_people._refresh_start`). Такая задача доживает до
следующего теста или до конца прогона — когда сторож, снятый вместе со своим
тестом, уже не стоит. Именно так сюита и ходила наружу.

⚠ **Это не теория.** Журнал запросов (§3.4.1 в `api.md`) показал поимённо: за один
прогон сюиты **четыре настоящих `POST /auth/login`** на ladadate.com под живыми
анкетами — 851, 855, 857, 861, — каждый со своим кодом отказа от самого сайта и с
настоящей задержкой в сотни миллисекунд. Сокетный сторож их не увидел, тесты были
зелёными, а счётчик неудачных входов на стороне сайта рос с каждым прогоном — тот
самый, из-за которого сайт закрыл нам адрес целиком.

#### Заглушки включены всегда, а не по запросу

`rhapsody` и `site_api` — **`autouse`**. Пока их просили по имени, забывший тест
шёл к живой системе, и это было не видно. Теперь заглушка стоит всегда, а тест лишь
настраивает её под себя; просящим её по имени достаётся тот же объект.

#### Сторож сети (`no_outside_calls`)

Стоит на `socket.connect` — вторым рубежом, под сторожем HTTP. Разрешено ровно три
вещи, и все три — своя установка: панель по `BASE_URL`, своя MySQL, свой Redis.

Проверено на излом: тест, идущий к соседу на `:8011`, тест, идущий на
`ladadate.com`, и голый `socket.connect` — все три падают; работа через заглушку
проходит. Сам сторож HTTP тоже проверен на излом — `tests/test_request_log.py`,
`TestNothingGoesOutside`: живой httpx, синхронный клиент и вебсокет отвергаются,
панель проходит.

#### Сторож живых данных (`no_live_writes`)

 сверяет после каждого теста, не
появилось ли в `dating_message` строк у анкет, которые были в базе до прогона.
Своим анкетам — заведённым тестом — писать можно.

⚠ Он завёлся не на пустом месте. Тест «строка без колонки `enabled` читается как
ведём» подменял прогон сценария, но **не запись отправленного**: каждый прогон
сюиты добавлял в переписку живой анкеты ещё одно «привет». К десятому прогону
человек увидел десять приветов в диалоге и принял это за поломку автоответа —
искали в коде автоответа, а виноваты были тесты.

Отсюда правило для тестов отправки: **успешная отправка обязана подменять и запись**
(фикстура `saved` в `test_profile_enabled.py`), а номер анкеты берётся выдуманный, а
не живой. Первого мало — строка легла бы с чужим номером и просто мусорила; второго
мало — подмену легко забыть.

Проверено замером: за прогон всей сюиты панель шлёт соседу **столько же запросов,
сколько за то же время простоя**, то есть ни одного своего. Фон — это её собственный
воркер: он опрашивает присутствие анкет сам по себе, и к тестам отношения не имеет.

## 2.1 Кадры чата: фиксация протокола перед переносом

`test_chat_frames.py` и `test_send_frames.py` — юнит-тесты **без сети и базы**;
кадры лежат строками в `tests/frames/` (см. `readme.md` рядом с ними).

Написаны они не «чтобы было покрытие», а под конкретную задачу: протокол чата был
зашит в `dating_chat.py` и `dating_send.py` константами под Goldenbride, и его
предстояло вынести в драйверы сайтов (`dating.md`, §5.0). Тесты зафиксировали
**сегодняшнее** поведение, чтобы перенос было чем проверить: до них правильность
разбора доказывалась только живым сайтом.

**Перенос состоялся, и они переехали на драйверы без единой правки ожиданий** —
сменились только адреса функций (`_message_parse` → `site.incoming_parse`,
`dating_send_uid` → `site.message_uid`). Это и было доказательством
эквивалентности; после переезда мутации прогнали заново, уже по драйверам.

Отсюда два правила, которые легко нарушить по невнимательности:

**Ожидания пишутся литералами, а не импортом констант модуля.** Константа,
взятая из проверяемого кода, переименуется вместе с ним, и тест останется
зелёным на изменившемся проводе. Это не рассуждение — проверено мутацией:
переименование `confirmFromClient` первая версия теста не заметила.

**Тесты не правятся заодно с кодом.** Их задача — доказать, что перенос ничего не
изменил; правка ожиданий под новый код лишает их всякого смысла. Если поведение
надо поменять — это отдельный шаг, отдельным обоснованием.

Проверены мутациями: снятый подпротокол `chat`, выкинутая прелюдия, пустой
`content` в запросе истории, ожидание эха вместо подтверждения сервера,
переименованные методы, укороченный ULID, пропущенное приветствие, снятый
эхо-фильтр, снятая обрезка текста — каждая поймана. Мутация, которую сюита не
ловит, означает не «код хорош», а «тест ничего не проверяет».

Одна мутация оказалась **эквивалентной**: убери из списка приветствий
`reconnectFromServer` — ничего не изменится, потому что приветствие узнаётся
вхождением подстроки, а `connectFromServer` входит в него целиком. Тест не
пропустил изменение — изменения не было. В драйвере это записано, чтобы совпадение
не приняли за намерение.

`test_contacts_sort.py` требует посеянных данных (`scripts/dating_seed.py`): порядок
и потолок выборки видны только там, где собеседниц сотни. Без посева тесты
**пропускаются**, а не падают — сюиту гоняют и по проду, где тестовых анкет нет и
быть не должно; в пропуске написано, что запустить.

`test_revive_*`, `test_profile_card.py`, `test_site_driver.py`, `test_people_parse.py`,
`test_people_cache.py`, `test_people_api.py`, `test_rhapsody_fail.py`,
`test_scenario_log.py` и оба `*_frames.py` — юнит-тесты без сети, без базы и без
запущенной панели. С автовосстановлением это вышло
само: база, сосед и сам вход подтягиваются импортами внутри функций, а не в шапке
модуля, и арифметику можно проверить в изоляции. После дробления это стало
устройством, а не удачей: правила лежат в `dating_revive.py` вовсе без импортов
проекта, а круг зовёт соседей по именам своего модуля — их и подменяет
`test_revive_round.py`. С разбором ответа сайта —
намеренно: правила вынесены в чистый драйвер (`src/dating/site/site_profile.py`),
потому что цена ошибки в них молчаливая (битые данные у всех собеседниц разом), а
по HTTP такое видно только глазами на странице.

Ручки, которые водят браузер соседа (`/login`, `/check`, `/dialog`), сюита **не
трогает**: они идут минутами и требуют живого сайта знакомств с рабочим паролем.
Их проверяют руками — порядок в `dating.md`. Настоящий вход, которым чинит себя
автовосстановление, сюита по той же причине не трогает тоже.

### Сборка SQL проверяется без базы

`test_log_feed.py` — половина юнит-тестов на `_query`, чистую функцию сборки
запроса ленты. Не потому, что «так проще»: именно там живут решения, которые легко
испортить незаметно — какие колонки попадают в обе половины `UNION`, как отбирается
сайт у каждой, что делать с уровнем, которого у прогонов не бывает. Ошибка здесь не
падает, а тихо показывает не то.

⚠ **Своих `INSERT` сюита не пишет.** Строки заводятся тем же кодом, что и в бою, —
ручкой; тест, кладущий их в таблицу руками, проверял бы свой SQL вместо рабочего и
разошёлся бы с ним в первой же миграции.

Соединение с базой у сюиты при этом **есть**: часть ручек зовётся в процессе (§1.2),
и работают они с настоящей базой. Адрес правит `conftest.py`: `MYSQL_HOST` в `.env`
— имя в сети compose, с хоста оно не резолвится, и наружу база выходит
опубликованным портом (`MYSQL_PORT_HOST`). Правится до всякого импорта: `mysql_`
читает адрес на уровне модуля.

⚠ **Пул соединений закрывается после каждого теста** (фикстура `db_pool`). Он живёт
глобальной переменной и привязан к циклу событий, а цикл у каждого теста свой:
второй же тест получал бы соединения от цикла, которого больше нет, и падал с
«Event loop is closed» на ровном месте.

### Прогон сценария подменяется, а не ждётся

`test_people_cache.py` проверяет ручку собеседников целиком — с кэшем, фоновым
обновлением и отказами, — но **сам прогон сценария подменён**. Иначе дождаться
нужного случая невозможно: пул вкладок у соседа общий, и «браузер занят» (409)
приходит не по расписанию, а прогон, который не кончается, там подменяется вечным
ожиданием — живой такого не покажет никогда.

Redis тоже поддельный (`_FakeRedis` в том же файле): сюите не нужен поднятый
Redis, а срок годности снимка проверяется временем внутри самого снимка. Настройка
сайта (срок хранения) подменяется полем фикстуры — она лежит в MySQL, а юнит-тест
не должен требовать поднятой базы.

⚠ **Форму почти каждого теста задаёт то, что ручка не ждёт прогона.** Ответ уходит
сразу — со снимком или пустым, — а снимок кладёт фоновая задача. Поэтому «снять
список» в тесте это три шага: спросить, дождаться задачи, спросить снова (`_fill`).
Ровно то же делает страница. Тест, написанный «спросил — проверил», проверял бы
пустоту: так и было при переходе на неблокирующую ручку, шестнадцать тестов разом.

⚠ Фикстура там **асинхронная**, и это не украшение: уборка гасит фоновые задачи, а
сделать это можно только пока жив цикл событий. У синхронной фикстуры уборка идёт
после него, и отмена падает с «Event loop is closed» — так и было.

## 3. Что сюита уже нашла

Не гипотетически — при первом же прогоне:

**Повторный выход отвечал 401.** `/auth/logout` не был в списке открытых путей, и
middleware отбивал запрос до самой ручки. Выход обязан работать всегда: без сессии
он просто ничего не делает, а 401 на «выйди» — шум, из-за которого клиент начинает
разбирать, был ли он вообще внутри.

**Неизвестный сайт давал 502 вместо 422.** Сосед на несуществующий номер отвечает
404, клиент превращал это в `RhapsodyError`, а ручка — в «шлюз не отвечает». Но
опечатка в номере сайта это ошибка запроса, а не сбой связи. Теперь 404 от соседа
отделён от обрыва: пустой ответ → 422, обрыв → 502.

Обе поломки жили в коде, который «работал», и обе видны только снаружи — изнутри
приложения такой тест их не показал бы.

**Кнопка «обновить» молча ничего не делала.** Выдержку между фоновыми попытками
(пять минут) она не обходила: минуту назад прошёл удачный прогон, человек видит
список полуторной минуты, нажимает «⟳» — и ничего, ни вращения, ни новых имён.
Поймано щелчком по живой странице, а не тестом; тест написан следом
(`test_people_cache.py`).

**Сюита вставала намертво, без единого сообщения.** Ручки заводят фоновую работу и
не ждут её — в этом весь смысл, — а брошенная задача держит соединение из пула.
Пул же закрывается после каждого теста и ждёт возврата вечно. Теперь `conftest.py`
гасит фоновые задачи **до** закрытия пула (§1).

**Страница молча показывала пустоту при полном ответе ручки.** «Письма» не
показывали ни шаблонов, ни переменных: код брал `result.mails`, а ручка отдаёт
`result` списком. Ни ошибки в консоли, ни отказа — `undefined || []` законен.

⚠ **Сюита этого не ловила и не поймает:** она проверяет ручки, а сломана была
страница. Нашлось при открытии браузером (Playwright есть в соседнем проекте):
скрипт входит по HTTP, открывает страницу и сверяет **увиденное на экране** с
ответом ручки. Стоит того, когда правка касается разметки и JS: там пустая
консоль ничего не доказывает.

**В карточку собеседника попала аватарка нашей девушки.** Запасной селектор фото
(«первое `img` из `/content/photos/`») на странице под входом захватил шапку
кабинета, где стоит фото вошедшей анкеты. ⚠ Ни один тест такого не поймает: ответ
сценария правдоподобен, поле заполнено, ссылка настоящая. Поймал человек — увидел у
мужчины лицо нашей анкеты. Правило: **широкий селектор на странице под входом
хватает и то, что принадлежит вошедшему**.

**Сюита стирала живой пул писем.** Проверка очистки звала `DELETE ?site_id=343` —
номер живого сайта, потому что письму нужна настоящая анкета (внешний ключ), а
завести её можно только там. Ручка же не разбирает, чьё письмо тестовое, и одним
прогоном унесла полсотни писем, набранных руками.

⚠ Разводится это просто: **анкета живёт на живом сайте, а письма кладутся на
выдуманный** — `site_id` у письма просто число, внешнего ключа на нём нет. Правило
общее: сюита не должна трогать то, с чем работают люди, и «мне нужен настоящий
объект» относится ровно к тому полю, где он нужен.

⚠ Попутно проверка «пул одного сайта не виден у другого» перестала что-либо
проверять: после переезда она искала письмо там же, куда его и положили. Такие
проверки не падают — они молча одобряют.

**Сюита копила мусор в живой базе.** `test_companion.py` не удалял карточки, а
стирал у них поля — «ручки удаления нет, их накапливают». За день прогонов
накопилось **269 строк**, три из них на живом сайте: они попали человеку на глаза
во вкладку «Собеседники». Теперь фикстура убирает строку целиком, прямо из базы —
как это делает `test_mailing.py` с письмами. Правило: **что завела, то и убрала**;
пустая тестовая строка ничем не лучше заполненной, если она видна в панели.

**Плавающий тест жил четверть часа из каждого часа.** `test_outside_the_shift_is_skipped`
собирал время арифметикой над частями и на 45-й минуте выдавал «19:60»: ручка
такое отклоняла, расписание оставалось круглосуточным, тест падал. Отдельным
прогоном не воспроизводился — только в полной сюите, если та доходила до него в
неудачную четверть часа. Плавающий тест хуже отсутствующего: он учит не верить
сюите.

**Ручки налезали друг на друга, даже упираясь.** Упор по значению оставлял между
ними шаг ленты — четверть часа, то есть пять пикселей при кружке в тринадцать: два
кружка сливались в один, и взять нужный было нельзя. Теперь между ручками держится
зазор в ширину кружка (45 минут). Измерено браузером: просвет 16.3 px при ручке 13.

**Ручки ползунка проходили друг сквозь друга.** Значения пары сортировались —
меньшее становилось началом, — и, перетащив начало за конец, человек получал смену
наизнанку; соседние смены налезали одна на другую. Теперь ручки упираются, и
расписание годно по построению.

⚠ Отсюда же новый род проверок в сюите: **правила, живущие в JS, проверяются
запуском самого модуля через `node`** (`test_schedule_band.py`). Прежде их
приходилось либо пересказывать на Python — и пересказ врал бы после первой правки,
— либо поднимать браузер ради арифметики над четырьмя числами. Проверено, что тест
ловит поломку: со снятым упором он падает с двумя внятными строками.

**Смена пропадала, когда ползунок доводили до конца суток.** 1440 минут
сворачивались по модулю в `00:00` — начало тех же суток; смена становилась
отрицательной длины и уезжала в начало ленты. Теперь конец суток это `24:00`, и его
принимают обе стороны. ⚠ Проверки на границу были только на «внутренние» значения —
7:00, 23:00; крайнее значение шкалы никто не пробовал, хотя дотянуть до него человек
пробует первым делом.

**Сохранённое расписание рассылки не показывалось никогда.** В базе смена, на
экране «Смен: 0 из 4», переоткрытие вкладки не помогает. Причина — черновик,
заведённый пустым при первой отрисовке, до ответа сервера: пришедшее сохранённое
он потом заслонял (`dashboard_frontend.md`, §3.5.1.1). ⚠ Найдено браузером и
только им: ручка отвечала правильно, сюита её и проверяла.

**Ползунки не совпадали с полосой смены.** Нативная ручка вписывается в дорожку
целиком, поэтому её центр ходит от полуширины до ширины минус полуширина, а
заливка стоит в честных процентах: на краях расхождение доходило до шести
пикселей. Измерено в браузере — `getBoundingClientRect` у заливок и расчёт центра
ручки; после правки расхождение ноль по всем шести ручкам.

**Расписание теряло смены после первого сохранения.** Человек двигал ползунки,
видел «сохранено» — и смены пропадали. Причина: черновик снимался после удачной
отправки, а обработчики ползунков держат свою смену **по ссылке** на объект в нём.
Следующее движение начинало правку с пустого списка, лента пустела, и через
полсекунды пустое расписание уезжало на сервер (`dashboard_frontend.md`, §3.5.1.1).

⚠ **Тестом это не ловилось и не ловится:** ошибка живёт в связке «обработчик
ползунка — черновик страницы», а сюита ходит по HTTP. Воспроизведена она была
моделью алгоритма на Node — двадцать строк, повторяющих черновик, сохранение и
правку по ссылке. Разница видна сразу: было `лента: []`, стало
`лента: ['10:00-15:00']`.

**Тесты держались за список, который вырос.** Две проверки писем сравнивали
целиком реестр переменных и ответ настроек сайта — и сломались, когда в реестр
добавились `girl_name` с `companion_name`, а к расписанию рассылки прибавилось
поле `mailing_send_on`. Ни одна не проверяла того, ради чего написана. Правило,
которое из этого следует: **сверяй своё, а не всё** — свои `tst…`-имена и нужные
поля по одному.

**Сюита не собиралась целиком из-за одного пакета.** Тогдашний
`test_contact_photo.py` (теперь его работу делает `test_profile_card.py`)
импортирует `src/`, оттуда тянется `logging_`, а на хосте не было
`python-json-logger` — и `pytest tests/` падал на сборке, не дойдя ни до одного
теста. Прогоняли с `--ignore`, то есть четыре проверки разбора ответа сайта не
работали вовсе. Отсюда `.venv` и `requirements-dev.txt` (§1.1).

**Форма ответа отправки была неровной.** `offline` клали только ветка «нет в
чате» и `_fail`, а отказ сайта, молчание и удача — нет. Ошибкой это не стало
только потому, что единственный читатель (`dating_answer.py`) берёт ключ через
`.get()`; второй, спросивший `result['offline']`, получил бы `KeyError` на ровном
месте.

Найдено при написании `test_send_frames.py` и сначала зафиксировано **как есть** —
выравнивать заодно с переносом протокола было нельзя, иначе «тесты зелёные»
перестало бы что-либо значить. Исправлено следующим шагом, когда эквивалентность
переноса была доказана: теперь у ответа пять ключей во всех исходах и на обоих
путях отправки (сокет и HTTP), а тест перебирает все пять исходов и сверяет
множество ключей целиком.
