# План: уклад миграций, переименование `girl` → `profile`, страница «Экспорт анкет»

Дата: 2026-08-26. Три этапа, строго по порядку. Каждый заканчивается работающей
панелью, прогнанной сюитой и отдельным коммитом: этап 2 трогает 40 файлов, и
смешивать его с чем-то ещё в одном коммите — значит лишиться возможности откатить
что-то одно.

Почему такой порядок. Переименование таблицы — это `ALTER`, а живую базу правкой
`0001.sql` не догнать (`migration.md` §2.1). Сегодня такая правка требует
одноразового файла в `data/migration_manual/`, который гоняют руками и на локальной,
и на проде. После этапа 1 она становится обычной миграцией, которую yoyo
накатывает сам при старте. Поэтому уклад — первым, а переименование — уже по
новому укладу и служит ему первой проверкой.

## Этап 1 — уклад миграций как в RhapsodyAi

### 1.0 Что берём и что не берём

Движок трогать не надо: `py_modules/mysql_/migration/mysql_migration_up.py` в
обоих проектах побайтно одинаков (проверено `diff -q`). yoyo уже умеет применять
несколько файлов по алфавиту и помнит применённое в `_yoyo_migration`. Меняется
только уклад — как называем файлы и куда кладём изменения.

**Не берём** (решение пользователя): таблицу `migration_manual_log` и модуль
`src/mysql_/migration/migration_file.py` (326 строк). У соседа они обслуживают его
вкладку «Миграции» рядом с diff задачи и прогон в базе-песочнице; здесь такой
панели нет, и таблица без неё была бы журналом, который никто не пишет и не читает.

### 1.1 Переименовать начальную схему

```bash
git mv migrations/0001.sql migrations/20260101000000_initial_schema.sql
```

Имя ровно то же, что у соседа, — намеренно: два проекта, один уклад, и хеш для
шага 1.3 совпадает с уже посчитанным.

Почему метка времени, а не `0001`, `0002`: миграции пишутся в ветках параллельно, и
номерами они столкнутся — две ветки заведут `0002.sql` с разным содержимым, и
слияние молча оставит одну. Метка уникальна сама по себе, а алфавитный порядок
имён совпадает с хронологическим — именно в нём yoyo и применяет файлы.

### 1.2 Вычистить `USE` и поправить шапку

В `migrations/20260101000000_initial_schema.sql`:

- **удалить строку 12 `USE \`dating\`;`**. Имя базы задаёт подключение: yoyo берёт
  его из `MYSQL_DATABASE`, ручной прогон — аргументом `mysql`. С `USE` внутри файла
  прогон «в тестовую базу на проверку» молча переключается на рабочую и выполняет
  по ней `DROP TABLE` из строк 18–23. У соседа эту строку убрали ровно поэтому.
- **шапку переписать**. Сейчас она заявляет: «Единственный источник правды по
  структуре базы: любые CREATE TABLE и ALTER TABLE — только здесь». С этого этапа
  это неправда, и оставить фразу — значит заложить будущую потерю данных: кто-то
  поверит и допишет `ALTER` в применённый файл, откуда он никогда не выполнится.
  Новый текст: это **начальная** схема, она заморожена как история; изменения — в
  новых файлах рядом.

**Осознанное следствие.** Структура базы перестаёт читаться из одного файла:
она — сумма файлов в `migrations/`. Это цена уклада, и сосед её платит (его
`project_task_metric` и `migration_manual_log` в начальной схеме отсутствуют —
проверено `grep -c`, оба дают 0). Взамен изменение схемы доезжает до прода само,
а не руками по туннелю.

### 1.3 Одноразовый файл: зафиксировать переименование в журнале yoyo

Новый файл `data/migration_manual/2026-08-26_yoyo_rename_initial_schema.sql`.

**Это самый опасный шаг всего плана.** yoyo помнит применённое по **имени файла**
(`_yoyo_migration.migration_id`), и переименованный файл для него новый. Стартовать
приложение с новым именем и без записи в журнале — значит выполнить начальную
схему заново, а в ней `DROP TABLE` по всем таблицам. Прод теряет всё.

Хеш в журнале — sha256 **от имени** миграции, а не от содержимого
(`yoyo/migrations.py: get_migration_hash`). Значит запись считается
детерминированно и не является подделкой: она ровно та, что yoyo записал бы сам.
Посчитано:

```
sha256('20260101000000_initial_schema')
  = f8d6516fa90f6235e7dbf15d69bdaf83a28debf5372e250d50be66c0096cae49
```

Тело файла (старую запись `0001` не удаляем — она след того, что схема
применялась, и никому не мешает):

```sql
INSERT INTO `_yoyo_migration` (`migration_hash`, `migration_id`, `applied_at_utc`)
SELECT 'f8d6516fa90f6235e7dbf15d69bdaf83a28debf5372e250d50be66c0096cae49',
       '20260101000000_initial_schema',
       COALESCE(MAX(`applied_at_utc`), UTC_TIMESTAMP())
  FROM `_yoyo_migration`
 WHERE `migration_id` = '0001'
ON DUPLICATE KEY UPDATE `applied_at_utc` = VALUES(`applied_at_utc`);
```

В шапке файла — зачем вручную, что проверено, и порядок: **на проде он гонится ДО
выкладки кода с переименованным файлом**.

Подводный камень `INSERT ... SELECT`: если записи `0001` в журнале нет (база
поднималась с нуля уже после переименования), `SELECT` вернёт ноль строк и вставки
не будет — что верно, там уже стоит новое имя.

#### Универсальное правило против нового уклада

`.claude/docs-common/database_rules.md` §1 сегодня гласит: «Все `CREATE TABLE` /
`ALTER TABLE` / `CREATE INDEX` — **в одном файле миграции**. Второго файла со
схемой не существует, «временных» миграций рядом тоже», и объясняет почему: «как
только DDL размазан по десятку файлов, ответ на вопрос "какая сейчас схема"
требует их мысленного проигрывания в правильном порядке. Один файл читается
глазами».

Новый уклад это правило нарушает прямо. Оставить его — значит держать в проекте
документ, который запрещает то, что проект делает; такие документы перестают
читать целиком.

§1 переписывается: единственным остаётся источник **начальной** схемы, дальше —
файлы с меткой времени; «какая сейчас схема» спрашивается у базы
(`SHOW CREATE TABLE`) или читается как сумма файлов по порядку. Причина размена
называется вслух: цена — схема больше не читается одним файлом, выгода — изменение
доезжает до прода само, а не одноразовым файлом по туннелю.

Раздел «Идемпотентность» тоже правится: он описывает `DROP TABLE IF EXISTS` +
`CREATE` для одного файла. Для файлов-довесков это неверно и опасно — там `ALTER`,
и он выполняется ровно один раз.

> ⚠️ **У соседа эта же копия уже врёт.** RhapsodyAi перешёл на новый уклад, но свой
> `.claude/docs-common/database_rules.md` §1 не поправил (проверено: текст там
> дословно тот же). Файлы уже разошлись между проектами (`diff` непустой). Правку
> в RhapsodyAi этот план **не включает** — чужой репозиторий, отдельная задача, — но
> помнить о ней стоит: папка задумана переносимой.

## Этап 2 — `dating_girl` → `dating_profile`, целиком

Слова `girl` в проекте не остаётся. Заодно снимается коллизия имён: `dating_profile`
сегодня занят кэшем профилей, он уезжает в `dating_profile_cache`.

### 2.1 Миграция схемы

Новый файл `migrations/20260826HHMMSS_dating_profile_rename.sql` (метку времени
взять фактическую на момент написания). Начальную схему **не трогаем** — она
заморожена (см. 1.2).

MySQL 8.0 (`docker-compose.override.yml.dist:55`), значит `RENAME COLUMN` и
`RENAME INDEX` доступны.

Порядок обязателен: колонку под внешним ключом просто так не переименовать, поэтому
ключи сначала снимаются, потом ставятся заново уже с новыми именами.

```sql
ALTER TABLE `dating_message` DROP FOREIGN KEY `fk_dm_girl`;
ALTER TABLE `dating_log`     DROP FOREIGN KEY `fk_dl_girl`;
ALTER TABLE `dating_contact` DROP FOREIGN KEY `fk_dc_girl`;

RENAME TABLE `dating_girl` TO `dating_profile`;
ALTER TABLE `dating_profile`
    RENAME INDEX `uk_dating_girl_site_login` TO `uk_dating_profile_site_login`;

ALTER TABLE `dating_message`
    RENAME COLUMN `girl_id` TO `profile_id`,
    RENAME INDEX  `idx_dating_message_girl` TO `idx_dating_message_profile`;

ALTER TABLE `dating_log`
    RENAME COLUMN `girl_id` TO `profile_id`,
    RENAME INDEX  `idx_dating_log_girl` TO `idx_dating_log_profile`;

ALTER TABLE `dating_contact`
    RENAME COLUMN `girl_id` TO `profile_id`;

ALTER TABLE `dating_message`
    ADD CONSTRAINT `fk_dm_profile` FOREIGN KEY (`profile_id`)
        REFERENCES `dating_profile` (`id`) ON DELETE CASCADE;
ALTER TABLE `dating_log`
    ADD CONSTRAINT `fk_dl_profile` FOREIGN KEY (`profile_id`)
        REFERENCES `dating_profile` (`id`) ON DELETE CASCADE;
ALTER TABLE `dating_contact`
    ADD CONSTRAINT `fk_dc_profile` FOREIGN KEY (`profile_id`)
        REFERENCES `dating_profile` (`id`) ON DELETE CASCADE;
```

Имена составных ключей, где `girl` не встречается, не трогаем:
`uk_dating_message_uid`, `idx_dating_message_dialog`, `uk_dating_contact` — их
состав меняется вместе с колонкой сам.

Файл применяется yoyo при старте — идемпотентным его делать не нужно (в отличие от
`data/migration_manual/`, где это обязательно).

### 2.2 Переименование файлов

### 3.4 Сшивка `extract` в строки

Отдельная функция в `src/dating/dating_export.py` — чтобы её можно было проверить
без сети.

Сосед отдаёт `extract` — словарь `имя шага → текст`, где несколько совпадений
селектора склеены через `\n` (`browser_scenario_run.py:257-276`). То есть «список
профилей» приходит как несколько параллельных столбцов (имена, возраст, ссылки),
и сшивать их в строки надо здесь.

- Колонки — имена шагов в порядке сценария (`dict` его сохраняет).
- Строк — по самому длинному столбцу; недостающее — пустая строка. Обрезать по
  самому короткому нельзя: столбец, где сайт не отдал часть значений, молча съел бы
  хвост списка.
- Ответ: `{'result': {'status', 'columns', 'profiles', 'error', 'step_no'}}`.

### 3.5 Что в этап 3 не входит

- **Сам сценарий для ladadate.com** — заводится у соседа отдельной задачей
  (решение пользователя). До этого страница работает и отвечает «для сайта нет
  сценария»: это и есть проверка ветки 1 из 3.3.
- **Хранение выгруженного**. Схему не трогаем, таблиц не заводим: таблица живёт в
  памяти страницы, перезагрузка её гасит.

### 3.6 Проверка этапа 3

1. Пункт виден оператору и админу; подсветка на `/admin/dating/export` — одна.
2. Кнопка без выбранного сайта — «сначала выберите сайт».
3. Сайт без сценария — 422 с внятным текстом.
4. `.claude/docs/api.md` и `dashboard_frontend.md` пополнены (правило из `CLAUDE.md`:
   новая ручка → `api.md`, правка страницы → `dashboard_frontend.md`).

## Прод: порядок выкладки

Порядок здесь — не формальность, перепутать его значит потерять базу.

1. Свежий бэкап через «Настройки → Backup».
2. **Этап 1:** прогнать `data/migration_manual/2026-08-26_yoyo_rename_initial_schema.sql`
   по туннелю к прод-базе — **до** выкладки кода. Пароль переменной окружения, не
   аргументом.
3. Выложить код этапа 1. В журнале старта обязано быть «Новых миграций для
   применения нет».
4. **Этап 2:** выложить код. Здесь наоборот — руками ничего не гонится, yoyo
   применит `20260826HHMMSS_dating_profile_rename.sql` сам. В журнале —
   «Будет применено миграций: 1».
5. **Этап 3:** обычная выкладка, схемы не касается.

Между шагами 2 и 3 прод живёт со старым кодом и новой записью в журнале — это
безопасно: запись описывает уже применённую схему, а старый код читает `0001.sql`,
которого он для yoyo уже не увидит как неприменённый.
