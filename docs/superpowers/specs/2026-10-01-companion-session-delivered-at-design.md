# Доставка реплики как факт строки: `companion_session.delivered_at`

**Дата:** 2026-10-01
**Проекты:** DatingAi + RhapsodyAi (правка идёт в обоих)

## Задача

Агент видит в истории разговора свои реплики, которых собеседник **не получал**.
Из-за этого следующий ответ строится так, будто сказанное уже сказано.

Причина измерена, а не предположена. Шаг `dating_talk` «Разговор: записать
ответ» (id 743, позиция 29) пишет обмен в `companion_session` **внутри прогона**
— то есть до того, как ответ вернётся в DatingAi и панель попробует его
отправить. У панели строка в `message` появляется только при удачной отправке
(`send.py`, `result['ok']`), у соседа — всегда. Неудача отправки расходит две
истории: в переписке реплики нет, в памяти агента есть.

## Решение

Доставка становится **фактом строки**, а не следствием того, кто и когда её
записал. В `companion_session` появляется `delivered_at`; записывается строка
всегда, а в ленту для агента попадает только подтверждённое.

⚠⚠ **Дом у разговора остаётся один.** Рассматривался возврат к прежней схеме —
панель собирает ленту из своих пяти таблиц и шлёт переменными
`talk_history_chat` / `talk_history_mail`. Отвергнут: это вернуло бы два дома,
ради избавления от которых разговор и переехал к соседу 24–25.09, и сам по себе
не чинил бы ничего — он лишь прятал бы проблему за другим источником.

## Что меняется у соседа (RhapsodyAi)

### 1. Колонка

```sql
ALTER TABLE `companion_session`
  ADD COLUMN `delivered_at` DATETIME NULL DEFAULT NULL
  COMMENT 'Когда наш ответ дошёл до собеседника; NULL — не дошёл или ещё не ушёл';
```

⚠ **`NULL` и без умолчания.** Та же грабля, что у `favorite_mail.updated_at`:
заведённая `NOT NULL DEFAULT CURRENT_TIMESTAMP`, колонка получила бы от `ALTER`
время миграции всем накопленным строкам — и недоставленное выглядело бы
доставленным сию секунду.

`companion_session_add` колонку **не трогает**: умолчание и есть «не доставлено».

### 2. Бэкфилл накопленного

Той же миграцией:

```sql
UPDATE `companion_session`
   SET `delivered_at` = `answer_at`
 WHERE `answer_at` IS NOT NULL AND COALESCE(`answer`, '') <> '';
```

Решение принято явно. На 01.10.2026 в таблице 157 строк чата и 186 писем. Без
бэкфилла агент в день выкладки разом забывает переписку со всеми 1240
собеседниками и начинает разговоры с нуля. Цена известна и принята: среди
отмеченных есть неизвестное число реально не ушедших реплик — это ровно то
допущение, на котором система жила до сих пор.

### 3. Лента прячет недоставленное — половиной, а не строкой

`companion_session_history` отбирает **половину «ответ»** по
`delivered_at IS NOT NULL`. Половина «вопрос» показывается всегда.

⚠⚠ **Отбор именно половиной, а не строкой.** Доставка бывает только у нашей
реплики: его слова доставлены самим фактом прихода. Отбери мы строку целиком, из
истории вместе с недоставленным ответом пропали бы и его слова — в том числе 3
строки «тишины», где его реплика есть, а нашего ответа нет вовсе.

Строка, у которой после отбора не осталось ни одной половины, в ленту не идёт.

⚠ Отбор ставится **в `companion_session_rows`**, а не в `_lines_of`, — но не
потому, что `…_rows` читает кто-то ещё: вызывающий у неё сегодня ровно один,
`companion_session_history`. Причина в том, что отбор обязан попасть **в SQL**, и
только `…_rows` знает запрос. Отсев в `_lines_of` шёл бы уже по выбранным
строкам — см. следующий абзац.

⚠⚠ **Строка, которой нечего показать, отсекается в SQL — до `LIMIT`.** Условие
`WHERE question <> '' OR delivered_at IS NOT NULL`. Отсеки её после выборки, и
`LIMIT 20` считал бы двадцать строк, из которых видимых осталось три: лента
выходила бы короче предела тем сильнее, чем хуже доходили ответы, — то есть
ровно тогда, когда история агенту нужнее всего.

### 4. Номер строки уезжает наружу

Шагу 743 добавляется `outputs_map: {"id": "talk_message_id"}`. Движок и так
раскладывает результат инструмента по переменным
(`%companion_session_add_743_result_id%`), `outputs_map` даёт ему имя, под
которым его найдёт ручка.

`POST /chat/ask` начинает отвечать `{"result": …, "message_id": …}`.
`message_id` берётся из `framework_model.workflow_variables` после завершения
прогона: движок мутирует этот словарь на месте, поэтому финальные значения в нём
есть.

⚠ **Пустой `message_id` — законный исход**, а не отказ: агент промолчал, прогон
ушёл в «тишину» (шаг 744), доставлять нечего.

⚠ Шаг 744 «Разговор: записать тишину» не меняется вовсе: у него нет половины
«ответ», и доставке там не из чего взяться.

### 5. Новая ручка

```
POST /chat/message/delivered
{"message_id": 12345}
```

Ставит `delivered_at = NOW()` строке `companion_session`.

⚠ **Идемпотентна: уже проставленное время не переписывается**
(`WHERE delivered_at IS NULL`). Повтор отправки иначе сдвигал бы отметку вперёд,
и «когда это дошло» переставало бы отвечать на свой вопрос.

Неизвестный `message_id` — не ошибка сервера: отвечаем тем, что строк изменено
ноль. Паниковать здесь нечему, а 500-й на это заставил бы панель повторять.

## Что меняется у нас (DatingAi)

### 6. Клиент соседа

`src/rhapsody/rhapsody_api.py` — единственная дверь, и обе правки в ней:

* `rhapsody_api_chat_ask` отдаёт пару «текст + `message_id`» вместо строки;
* появляется `rhapsody_api_chat_delivered(message_id)`.

### 7. Три места зовут `dating_talk` — и все три помечают доставку

| Откуда | Когда известна доставка | Где зовём `delivered` |
|--------|------------------------|----------------------|
| `answer_run` — чат | сразу, в том же вызове | `answer.py`, после `send_message` при `result['ok']` |
| `answer_mail_reply` — ответ на письмо | часами позже, кругом отправки | `mail_send_mark(sent=True)` |
| `answer_mail_write` — письмо избранному | часами позже, кругом отправки | `mail_send_mark(sent=True)` |

⚠ **У писем точка одна на оба пула — `mail_send_mark`.** Через неё проходят и
круг отправки, и путь через панель (`mail_reply_panel.py`), и она уже знает, из
какой таблицы письмо (довод `table`). Две точки вместо одной разошлись бы ровно
так, как разошлись бы записи исхода, — а их там тоже свели в одно место и по той
же причине. Условие: `sent` и `table in ('mail_reply', 'favorite_mail')` и
непустой `message_id`; `mailing` сюда не попадает никогда.

⚠⚠ **Рассылка и инвайты сюда не входят.** Они идут своими workflow
(`mail_agent.py`) и `companion_session` не пишут вовсе — помечать там нечего.
Проверено запросом: `companion_session_add` стоит ровно в двух шагах, и оба в
`dating_talk`.

### 8. ⚠⚠ Пулам нужен номер в строке

Чат отправляет ответ сразу, и номер живёт в памяти вызова. Письма ложатся в пул и
ждут круга отправки, иногда часами, — номер между сочинением и отправкой теряется.

Поэтому **двум** пулам добавляется колонка:

```sql
ALTER TABLE `mail_reply`     ADD COLUMN `message_id` INT NULL DEFAULT NULL;
ALTER TABLE `favorite_mail`  ADD COLUMN `message_id` INT NULL DEFAULT NULL;
```

⚠ `NULL` значит «не знаем»: строка могла родиться до этой правки либо агент
промолчал. Круг отправки на таком не спотыкается — просто не зовёт `delivered`.

## Порядок выкладки — три шага

Решение принято явно.

1. **Сосед:** колонка, бэкфилл, ручка, `message_id` в ответе. Лента ещё **не**
   отбирает. Ничего не ломается: панель про новое поле не знает.
2. **Мы:** колонки пулов, клиент, три точки вызова `delivered`.
3. **Сосед:** включается отбор в `companion_session_rows`.

⚠⚠ **Склей шаги 2 и 3 в один, и отбор заработает раньше меток.** По всем новым
репликам агент увидел бы историю без собственных ответов — то есть ровно ту
поломку, от которой лечимся, только с другой стороны.

## Проверка

* **Сосед:** `delivered_at` у новой строки `NULL`; ручка ставит время; повтор
  время не меняет; лента без `delivered_at` не показывает «она», но показывает
  «он».
* **Мы:** удачная отправка зовёт `delivered`, неудачная — нет; письмо из пула
  зовёт её в момент отправки, а не сочинения; пустой `message_id` не роняет
  ничего. Живой HTTP в тестах запрещён — только заглушка `rhapsody_fake.py`
  (`testing.md`, §1.2).
* **На живых данных:** строка в `companion_session` без `delivered_at` при
  неудачной отправке — и её отсутствие в ленте следующего прогона.

## Чего эта работа не делает

* Не чинит **пустую половину «вопрос»** — 120 строк чата из 157 записаны без
  `prompt_user`. Это соседняя поломка той же области: агент не видит, на что
  отвечал. Лечится отдельно, иначе две правки в одних файлах перепутаются.
* Не трогает нашу таблицу `message` и правило «пишем только ушедшее».
* Не переносит сборку истории обратно в панель.
