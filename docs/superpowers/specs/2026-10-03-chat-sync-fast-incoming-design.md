# Входящее в чате за секунды: ответ удара присутствия перестаёт выбрасываться

**Дата:** 2026-10-03
**Проекты:** DatingAi + py_modules (правка общего слоя — одна функция)
**Сайт, на котором это работает:** Ladadate (343), 13 анкет, 11 в сети

## Задача

Входящее сообщение чата доезжает до нас за минуты. Нужно — за секунды.

Бюджет замерен на проде, а не предположен:

| Звено | Сколько |
|---|---|
| Обнаружение: круг импорта из панели | **0–120 с** (тик круга 60 с + срок сайта `chat_check_every` = 60 с) |
| Ожидание круга автоответа | 0–60 с |
| `POST /chat/ask` у соседа (LLM) | **81 с в среднем**, 55 % вызовов дольше минуты, максимум 240 с |
| Отправка `POST /chat-send` | 0,3 с |

Факт по 84 парам «его реплика → наш ответ» за 30 дней: в среднем **133 с**, 34
случая быстрее двух минут, 37 от двух до пяти, 13 дольше пяти.

⚠ **Забор из панели при этом почти бесплатный**, и минута — не цена, а просто
настройка: один GET на **весь сайт** (`AccountId=0`), 16 КБ, 9 строк за сутки,
437–1243 мс, разбор таблицы 5 мс. У сайта заполнен `admin_url`, поэтому забор
идёт ручкой по удерживаемой сессии, а не сценарием (`panel_fetch.py`).

## Находка: быстрый канал у нас уже есть, мы выбрасываем его ответ

Круг присутствия бьёт `POST /chat-sync` каждые 30 секунд по каждой анкете — 1424
запроса в час в журнале прода. Тело ответа движок ударов не возвращает
(`http_heartbeat_send_many` отдаёт `{ключ: дошло ли}`), и оно теряется. А в нём:

```json
{"IsSuccess":true,"Reason":"OK","Message":"OK",
 "ChatSessions":[],"ChatRequests":[],"Balance":0,"SelectedUser":null}
```

`ChatRequests` — это и есть **входящие сообщения девушке**. Прочитано в
`chat-app.js?v=16` самого сайта, а не выведено по догадке:

```js
function RequestMessage(accountId, name, age, isLiked, isContact, profilePhoto,
                        city, countryCode, messageId, body, isRead) { … }

$.each(response.ChatRequests, function (i, request) {
    if (IsSelectedUser(request.AccountId)) { isNeedLoadMessages = true; } else {
        AddChatRequest(request);
        if (IsLady() && isSoundOn) { PlayAcceptChat(); }
    }
    lastChatRequest = request;
});
…
if (lastChatRequest != null && IsLady()) { BlinkTitle('✉️*NEW MESSAGE*✉️ - LadaDate'); }
```

То есть запись несёт `MessageId`, `AccountId`, `Name`, `Age`, **`Body`** и
`IsRead`, а страница на эту ветку вешает звук и мигание заголовка — и только при
`userGender = 'lady'`, то есть ровно для наших анкет (проверено: страница `/chat`
под нашей сессией отдаёт `userGender = 'lady'`).

⚠ **Ритм сайта — 15 секунд**: на странице `syncTimeout = '15000'` и
`usersSyncTimeout = '15000'`. Наш удар ходит раз в 30 — мы вдвое медленнее живой
страницы, и это тоже часть сегодняшней задержки.

## Что проверено и отброшено

| Путь | Почему нет |
|---|---|
| `POST /chat-messages` | Отдаёт огрызок текущей сессии и `MessageId: 0`. Для пяти живых пар вернул `Messages: []` у четырёх и одну **нашу** реплику у пятой. Источником быть не может |
| `POST /chat-users` | Довод `userType` игнорирует (`contacts`, `all`, `favorites`, `dialogs` дают один и тот же ответ), признаков непрочитанного не несёт вовсе |
| Просто опрашивать панель раз в 10–15 с | Работает, но это запрос на сайт против нуля у `chat-sync`, и у панели остаётся **минутная** точность времени |
| Счётчик `unread` движка ударов | У Ladadate в настройке не заведён, и он про почту, а не про чат |

## Решение: `chat-sync` работает звонком, писатель остаётся один

**Непустой `ChatRequests` не пишет сообщение сам, а немедленно запускает забор из
панели и будит ответ.** Задержка от этого вырастает на один GET панели — 0,5
секунды против 15 секунд шага, — а взамен снимается главный риск.

⚠⚠ **Почему не писать напрямую — записано заранее, в `message_twin.py`:**

> ⚠ Допуск только у исходящих. У входящих близнецов на проде **нет ни одного** —
> сайт без сокета, и реплики собеседника приходят единственной дорогой. Зато
> входящие в одну секунду бывают настоящими: человек пишет очередью, до пяти
> реплик. Поэтому им оставлен прежний строгий ключ: показать лишнюю строку
> неприятно, а съесть чужую реплику — беда.
>
> Появится сайт с сокетом — входящие тоже станут приходить двумя дорогами, и это
> место придётся пересмотреть **вместе с замером**, а не по аналогии.

Это и есть наш случай: у входящих появляется вторая дорога. Пиши `chat-sync` в
`message` сам — и либо номера сойдутся с панельными (тогда `INSERT IGNORE`
схлопывает всё даром), либо нет, и тогда понадобится нечёткое правило близнеца на
входящих — то самое, которое, по замеру, рискует съесть настоящую реплику из
очереди. Звонок обходит развилку целиком: **в `message` по-прежнему пишет только
забор из панели**, со своими номерами, своими отметками времени и уже отлаженной
нормализацией текста (сущности `&#252;`, коды смайликов `#smile#`, воронка
`text_emoji_same`).

### Что меняется

**1. Общий слой: ответ удара можно забрать.**

```python
http_heartbeat_send_many(client, sessions, config, with_body=False)
#  with_body=False → {ключ: дошло ли}                     — как сегодня
#  with_body=True  → {ключ: {'ok': bool, 'status': int, 'body': str}}
```

Одна функция, а не вторая рядом: два пути удара разошлись бы на первой правке.
Умолчание сохраняет поведение всех прочих вызывающих.

⚠ Попутно закрывается оставленная в `heartbeat_round._note` заплатка «кода ответа
у пачки нет, ноль честнее выдуманного 200»: с `with_body=True` код ответа
настоящий.

**2. Настройка сайта описывает, где в ответе новости.** В `presence` — раздел
рядом с `send` и `heartbeat`:

```json
"chat_new": {"ok": "IsSuccess", "rows": "ChatRequests",
             "id": "MessageId", "uid": "AccountId"}
```

⚠ **Текста и имени в настройке нет намеренно**, хотя сайт их присылает (`Body`,
`Name`). Звонку они не нужны, а взять их значило бы завести второго писателя
`message` — то самое, от чего вся эта форма и уходит. Понадобятся они ровно
тогда, когда понадобится форма «пишет сам».

⚠ **Настройкой, а не кодом драйвера** — тем же способом, которым уже описаны
анкета девушки (`site_profile.py`), карточка собеседника (`site_about.py`) и
транспорт отправки (`site_base.py`): «имена полей по настройке». Нет `chat_new` у
сайта — всё ведёт себя в точности как сегодня, то есть сайт без этой настройки
правкой не затронут.

**3. Новый `src/dating/chat_sync.py`.** Своего HTTP не делает — только разбор и
решение:

* `chat_sync_rows(config, body)` — ответ удара в список `{uid, id}` по именам
  полей настройки. Не разобралось, `ok` ложный, раздела нет — пустой список, без
  исключений: зовут из круга, и упавший круг унёс бы присутствие.
* `chat_sync_ring(site_id, news)` — решает, звонить ли. Номера, по которым уже
  звонили, держим в памяти процесса со сроком в пять минут.

  ⚠ **Срок у памяти, а не «звонили навсегда».** Если панель в этот момент
  отстала и забор ничего не привёз, второй звонок случится через пять минут. Дыры
  тут нет: обычный круг импорта продолжает ходить **раз в минуту**, то есть
  худший исход такого случая — ровно сегодняшняя скорость, а не потерянное
  сообщение.

  ⚠ **Дедуп обязателен.** Мы никогда не «читаем» запрос на сайте (`/chat-select`
  не зовём), поэтому непрочитанный `ChatRequest` будет приезжать в **каждом**
  ответе удара. Без памяти о номерах звонок бил бы в панель каждые 15 секунд
  вечно.

  ⚠ Память в процессе, а не в Redis — тот же довод, что у `_beaten` в
  `heartbeat_round`: перезапуск смены это **лишний** заход в панель, а не
  пропущенный, и цена ошибки в эту сторону копеечная.

**4. Круг присутствия отдаёт ответ, а решает за него `chat_sync`.**
`heartbeat_round` зовёт удар с `with_body=True`, складывает новости всех анкет
сайта и звонит **один раз на сайт за тик**: забор из панели идёт по сайту целиком
(`AccountId=0`), и тринадцать звонков дали бы тринадцать одинаковых GET.

⚠ **Да, присутствие и чат здесь склеены — потому что это один запрос сайта.**
Общее правило проекта разделяет «в сети» и «в чате» (`heartbeat.md`), и оно
остаётся верным: у Ladadate `beat` и «опрос нового» — буквально один и тот же
`POST /chat-sync`, который шлёт страница. Второй круг с тем же запросом означал
бы удвоение стука на сайт ради чистоты схемы.

**5. Ответ просыпается по событию, а не по тику.** В смене держателя появляется
событие «есть новое входящее»; `_answer_loop` ждёт либо свои 60 секунд, либо его.
Оба круга — задачи одного процесса (`chat_hold_run`), поэтому хватает
`asyncio.Event`, без Redis.

⚠ **Событие пустое, без номера анкеты.** Круг автоответа и так перечитывает
список готовых анкет каждый заход (`_profiles_ready`) и обходит их все; передавать
ему, кого именно будить, значило бы завести второй порядок обхода рядом с
существующим.

⚠ Предел сайта «одно сообщение в минуту одному собеседнику» (`AUTO_PERIOD_SEC`)
побудка **не отменяет**: она ускоряет начало работы, а не частоту отправки. От
двух ответов на один повод защищает уже стоящий ключ `chat_reply.message_id`.

**6. Ритм 15 секунд.** `heartbeat_every` у Ladadate 30 → 15, ритм самой страницы.
Тик круга присутствия и так 15 секунд — менять его не нужно.

### Цена, названная числом

| Что | Было | Станет |
|---|---|---|
| `POST /chat-sync` наружу | 26/мин | 52/мин (ровно столько делает живая страница на анкету) |
| Строк в журнале запросов | ~37 тыс./сутки у присутствия, 52 тыс. всего | ~75 тыс. у присутствия; при трёхдневном хранении ~225 тыс. строк |
| GET панели | 60/час | 60/час + один на входящее (входящих ~3 в сутки) |

### Что остаётся как есть

**Забор из панели остаётся и остаётся на минуте.** Он авторитетен по номерам,
несёт историю, наши исходящие и то, что пришло, **пока анкета была вне смены**:
`chat-sync` бьётся только за анкеты в смене, поэтому страховка здесь обязательна,
а не «пока не убрали».

## Ожидаемый итог

| Звено | Было | Станет |
|---|---|---|
| Обнаружение | 0–120 с | **≤15 с** + 0,5 с на GET панели |
| Ожидание тика ответа | 0–60 с | нет |
| LLM у соседа | 81 с | 81 с |
| **Итого в среднем** | ~170 с | **~90 с** |

⚠ После этой правки **главным остатком становится `/chat/ask`** — 81 секунда в
среднем, 55 % дольше минуты, максимум 240. Это ~80 % итога и отдельная работа на
стороне соседа; в эту спецификацию она не входит, но без неё дальше секунд не
будет.

## Шаг 0: наблюдатель на проде (идёт)

Замысел держится на двух допущениях, и оба проверяются наблюдением, а не
рассуждением. На проде поднят наблюдатель (`/tmp/watch_chat_sync.py` в
`dating_uvicorn`, 14 часов, шаг 30 с, пишет `/tmp/chat_sync_watch.jsonl`,
только чтение). Он отвечает на три вопроса:

1. **Зажигается ли `ChatRequests`** при живом входящем. Если нет — замысел
   отменяется целиком, и остаётся вариант «опрашивать панель чаще».
2. **Мгновенна ли панель.** Сразу после находки наблюдатель спрашивает журнал
   панели: лежит ли там это сообщение уже. От этого зависит, годится ли звонок:
   если панель отстаёт на минуту, звонок бесполезен.
3. **Тот ли номер** `MessageId`, что `panel:59572496`. Для звонка это не нужно, но
   если панель окажется медленной, придётся писать напрямую — и тогда ответ на
   этот вопрос становится обязательным.

⚠ **Входящих на проде около трёх в сутки**, поэтому наблюдение занимает часы, а
не минуты. Работу по пунктам 1, 4 и 5 (общий слой, круг, побудка) это не
блокирует: они нужны при любом исходе.

### Если панель окажется медленной

Тогда форма меняется на «`chat-sync` пишет сам», и к ней добавляется то, чего
звонок не требует: значение `sync` в перечислении `message.source` (миграция),
нормализация текста теми же воронками, `is_read = 0` против `1` у импорта, и —
главное — правило близнеца на входящих **вместе с замером**, как велит
`message_twin.py`. Это существенно больший объём, и браться за него без замера
нельзя.

## Тесты

Живой HTTP в сюите запрещён (`testing.md`, §1.2) — только заглушка.

* разбор `ChatRequests` по настройке: полный ответ, пустой список, ложный
  `IsSuccess`, отсутствующий раздел, мусор вместо JSON;
* сайт **без** `chat_new` ведёт себя как сегодня — звонка нет, ответ удара не
  толкуется;
* тот же `MessageId` второй раз звонка **не** даёт (память о номерах);
* новости тринадцати анкет дают **один** звонок на сайт, а не тринадцать;
* побудка ответа срабатывает, и на один повод уходит один ответ;
* `with_body=False` в общем слое отдаёт в точности прежнюю форму `{ключ: bool}`.
