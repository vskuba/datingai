# Параметры анкеты девушки: вторая колонка окна и полное био для чата

**Дата:** 2026-10-12
**Проект:** DatingAi (правок у соседа нет)

## Задача

Агент, который говорит за девушку, знает о ней четыре вещи: имя, возраст, город и
рассказ «о себе». Это всё, что лежит в карточке `profile.profile`, и всё, что
уезжает переменной `girl_bio` — и при заведении агента (`dating_girl_create`
добывает из неё факты), и на **каждом** ответе в чате (`answer.py:581`).

Собеседник спрашивает о другом. Какого цвета волосы, какой рост, курит ли, есть ли
дети, кем работает, чем увлекается, кого ищет. Ответов на это у агента нет вовсе, и
он их **придумывает** — иначе ответить нечем.

При этом ответы существуют. Анкета девушки заполнена целиком, лежит в
админ-панели агентства, и панель мы уже читаем по удерживаемой сессии за доли
секунды (`panel_fetch.py`). Полтора десятка полей просто никуда не едут.

Нужно: снять их с панели, сложить в карточку под общим каркасом, показать и дать
править в окне «Персональные данные анкеты» второй колонкой, и дописать в `girl_bio`.

## Что уже есть

| Что | Где | Чем полезно |
|---|---|---|
| карточка анкеты | `profile.profile`, JSON: `id, name, age, city, about, photo` | сюда ложится новый ключ |
| отметки правки руками | колонка `profile_edited`, список имён полей | механизм готов, нужны составные имена |
| единственная дверь правки | `profile_card.py`: `profile_card_save`, `profile_card_keep`, `profile_card_forget` | правило «сайт не трогает правленое» живёт одной функцией |
| чтение страниц панели | `panel_fetch_html(site_id, path)` — GET по cookie, которые держит `panel_round` | 0,2–0,4 с против 40 у сценария |
| разбор таблицы панели | `panel_fetch_table(html)` на `html.parser` | образец для разбора формы |
| драйверы сайта | `site_registry.py`, три таблицы: чат, анкета, разбор страницы собеседника | образец для четвёртой |
| био собеседника | `companion_bio.py` + подписи `companion_about.py` | **тот же приём с другого конца** |
| сборка био девушки | `agent.agent_bio(card)` | сюда дописываются строки |
| заглушка панели в сюите | `tests/panel_fake.py` (подменяет транспорт внутри `panel_fetch`) | живого HTTP в тестах нет никогда |

## Разметка панели: снято с живой страницы

Страница `…/partner/agency/userprofile/edit/643694` снята **один раз** с прода
читающим GET по удерживаемой сессии (53 120 знаков). Это обычная серверная форма с
машинными именами полей:

```
input     AccountId      hidden   643694
input     Name           text     Diana
input     City           text     Kyiv
input     Occupation     text     choreographer
input     AgeFrom        number   35
input     AgeTo          number   65
select    CountryId      → option selected value="208"  «Ukraine»
select    EducationId    → «University»        EnglishId      → «Good»
select    EyesColorId    → «Hazel»             HairColorId    → «Red»
select    HairStyleId    → «Medium»            MaritalStateId → «Never been Married»
select    ReligionId     → «Christian»         EthnicityId    → «White/European»
select    BodyTypeId     → «Slim»              DrinkId        → «Rarely»
select    SmokeId        → «No»                ChildrenId     → «None»
select    HeightId       → «5'8" - 172 cm»     WeightId       → «112 lb - 51 kg»
select    BirthdayDay    → «21»   BirthdayMonth → «Jan»   BirthdayYear → «1990»
textarea  AboutMyself    Interest   AboutPartner
```

Отсюда два вывода, определяющие устройство:

**⚠ Разбираем по именам полей, а не по подписям.** У собеседника-мужчины
(`companion_about.py`) выбора не было: сценарий снимал весь текст блока одной
строкой, и подписи («Occupation», «Marital Status») были единственными ориентирами.
Здесь ориентир лучше: `name="HeightId"` — машинное имя, оно переживёт перевёрстку, а
подпись «HEIGHT» нарисована рядом и может стать «Tall» при первом же переводе
интерфейса.

**⚠ Чтение формы — свойство HTML, а не сайта.** Значение `input` лежит в `value`,
значение `select` — в тексте `option` с `selected`, значение `textarea` — в его теле.
Это семантика формы, одинаковая у любой панели. Значит она ложится рядом с
`panel_fetch_table`, а сайту остаётся только карта имён.

## Решение

### 1. Данные: вложенный ключ `parameters` с постоянным каркасом

```
profile.profile (JSON)
├── id, name, age, city, about, photo    ← как сейчас, не трогаем
├── parameters                           ← новое: ВСЕГДА все 21 ключ
└── parameters_at                        ← когда снято, UTC ISO
```

**Все 21 ключ лежат всегда**, неизвестное — пустой строкой. Это и есть требование
«каркас ключей одинаковый для всех профилей»: окно рисует одни и те же строки в
одном порядке у любой анкеты, а «ключа нет» и «ключ пуст» перестают быть двумя
состояниями, которые пришлось бы различать в четырёх местах — в показе, в сборке
био, в сравнении при правке и в отсеве пустых.

⚠ `parameters_at` — **не параметр**, и в реестр не входит: это отметка о чтении.
Лежит рядом, а не внутри, чтобы каркас оставался ровно из 21 ключа.

### 2. Реестр — `src/dating/profile_param.py`

Один источник на всё: подписи окна, подписи био, порядок, вид поля.

```python
# Ключ, подпись окна, подпись био (англ.), вид поля.
#
# ⚠ Порядок — порядок показа и порядок строк био разом: два порядка на один
# список разошлись бы на первой вставке.
PROFILE_PARAMS = (
    ('birthday',      'Дата рождения',      'Birthday',          'text'),
    ('country',       'Страна',             'Country',           'text'),
    ('occupation',    'Занятие',            'Occupation',        'text'),
    ('education',     'Образование',        'Education',         'text'),
    ('english',       'Английский',         'English',           'text'),
    ('marital_state', 'Семейное положение', 'Marital status',    'text'),
    ('children',      'Дети',               'Children',          'text'),
    ('religion',      'Религия',            'Religion',          'text'),
    ('ethnicity',     'Происхождение',      'Ethnicity',         'text'),
    ('body',          'Телосложение',       'Body',              'text'),
    ('height',        'Рост',               'Height',            'text'),
    ('weight',        'Вес',                'Weight',            'text'),
    ('hair',          'Волосы',             'Hair',              'text'),
    ('hair_style',    'Причёска',           'Hair style',        'text'),
    ('eyes',          'Глаза',              'Eyes',              'text'),
    ('smoke',         'Курит',              'Smoke',             'text'),
    ('drink',         'Алкоголь',           'Drink',             'text'),
    ('age_from',      'Ищет: возраст от',   'Partner age from',  'text'),
    ('age_to',        'Ищет: возраст до',   'Partner age to',    'text'),

```

Три функции, все чистые — базы и HTTP не касаются:

```python
def profile_param_frame(values) -> dict      # каркас: 21 ключ в порядке реестра,
                                             # чужие выброшены, недостающие пусты
def profile_param_fields() -> list[dict]     # реестр странице: key, title, kind
def profile_param_bio(params) -> list[str]   # строки «Label: value», пустые опущены
```

⚠ Подписи и вид поля страница берёт **с сервера**, ответом `GET /card`. Своя копия
списка на странице разошлась бы с кодом молча — грабля словаря тегов галереи
(`gallery_vision`), где это уже закрыто ручкой `/api/dating/gallery/tags`.

### 3. Чтение формы — `panel_fetch_form(html)` в `panel_fetch.py`

Сосед `panel_fetch_table`, тот же `html.parser` из стандартной библиотеки (в образе
нет ни `bs4`, ни `lxml`, и тянуть их ради одной формы незачем).

```python
def panel_fetch_form(html: str) -> dict:
    """Значения формы панели: имя поля → то, что в нём стоит."""
```

- `input` → атрибут `value` (поля без `name` пропускаются);
- `select` → текст `option` с `selected`; выбранного нет — пустая строка;
- `textarea` → тело тега.

⚠ У `select` берётся **текст**, а не `value`: `value="172"` — внутренний номер
сайта, человеку и модели он не говорит ничего, а текст `5'8" - 172 cm` говорит.

### 4. Драйвер панели — `src/dating/site/site_panel.py`, 4-я таблица `site_registry`

```python
class DatingSitePanel:
    name = 'base'
    path = ''        # путь страницы анкеты от корня панели; пусто — читать нечем
    FIELDS = {}      # имя поля формы → наш ключ, один к одному
    BUILT = ()       # ключи, которые драйвер собирает сам из нескольких полей

class DatingSitePanelLadadate(DatingSitePanel):
    name = 'ladadate'
    path = 'userprofile/edit/{uid}'
    BUILT = ('birthday',)   # из BirthdayDay + BirthdayMonth + BirthdayYear
    FIELDS = {'CountryId': 'country', 'Occupation': 'occupation',
              'EducationId': 'education', 'EnglishId': 'english',
              'MaritalStateId': 'marital_state', 'ChildrenId': 'children',
              'ReligionId': 'religion', 'EthnicityId': 'ethnicity',
              'BodyTypeId': 'body', 'HeightId': 'height', 'WeightId': 'weight',
              'HairColorId': 'hair', 'HairStyleId': 'hair_style',
              'EyesColorId': 'eyes', 'SmokeId': 'smoke', 'DrinkId': 'drink',
              'AgeFrom': 'age_from', 'AgeTo': 'age_to',
              'Interest': 'hobby', 'AboutPartner': 'about_partner'}
```

⚠ `BUILT` объявлен не ради красоты: `birthday` собирается из **трёх** полей формы и
в `FIELDS` попасть не может, а сторож согласия (проверка 5) обязан знать, что это
не потерянный ключ. Условие сторожа — `set(FIELDS.values()) | set(BUILT)` против
`PROFILE_PARAM_KEYS`, в обе стороны.

Плюс метод `params(form) -> dict`, который возвращает каркас из 21 ключа и делает
**нормализацию** — она тоже знание о конкретной панели:

| Что отдаёт панель | Что кладём | Почему |
|---|---|---|
| `HeightId` = `5'8" - 172 cm` | `height` = `172 cm` | дюймы в био не нужны, и склейка двух систем мер читается как мусор |
| `WeightId` = `112 lb - 51 kg` | `weight` = `51 kg` | то же |
| `BirthdayDay/Month/Year` = `21`/`Jan`/`1990` | `birthday` = `1990-01-21` | три поля формы — один факт |
| неизвестный месяц, неполная тройка | `birthday` = `''` | половина даты хуже её отсутствия |

⚠ Нормализация в **драйвере**, а не в сборщике био: вид `5'8" - 172 cm` — свойство
Ladadate, и в общем коде он стал бы миной для второго сайта. Та же причина, по
которой заведён `site_about.py` («вёрстка у каждого сайта своя»).

Четвёртая таблица в `site_registry.py` — `DATING_SITE_PANEL_DRIVERS`, выбор по тому
же `presence.driver`, что три прежние, и `site_registry_panel(presence)` рядом с
`site_registry_about`. Умолчание — базовый класс с пустым `path`: сайт без своего
драйвера панели читать нечем, и ручка говорит это словами.

⚠ **Четыре поля формы совпадают с полями карточки, и три из них мы не трогаем.**
`Occupation` берётся в параметры — в карточке его нет. `Name`, `City` и
`AboutMyself` имеют своих писателей (импорт, страница кабинета, кэш анкеты) и свои
отметки правки; сделать панель четвёртым их источником — отдельное решение с
отдельной ценой. Признак пересмотреть: если окажется, что панель свежее всех трёх.

### 5. Запись: две двери, и обе названные

**Проблема.** Кнопка «обновить с сайта» приносит данные **от сайта**. Писать их
через `profile_card_save` нельзя: та метит всякое изменение как ручную правку, и
первое же обновление заморозило бы все 21 поле навсегда.

Путь «сайт принёс карточку» в проекте уже есть — **дважды, слово в слово**:

```
profile_page._profile_save         SELECT profile, profile_edited
profile_cache._profile_save_card   {**before, **profile_card_keep(fresh, edited)}
                                   UPDATE profile SET profile = …
```

Они отличаются только фразой в журнале, и в докстринге прямо написано, что их
«правят парой». Третья копия ради панели — ровно та грабля проекта, которая уже
стоила пропущенного третьего писателя карточки («план закрыл двух из трёх, нашло
финальное ревью»).

**Поэтому близнец переезжает в `profile_card.py`:**

```python
async def profile_card_merge(profile_id: int, fresh: dict, note: str) -> dict:
    """Положить пришедшее с сайта, не затирая правленого руками."""
```

Оба прежних писателя становятся однострочными вызовами (`note` даёт им их прежние
фразы в журнале — «анкета не записалась» / «кэш анкеты не записался»), читатель
панели — третьим. Дверей записи карточки остаётся **две**:

| Дверь | Кто ходит | Что делает с отметками |
|---|---|---|
| `profile_card_save` | человек из окна | **ставит** их на изменённое, сверяет снимок (`_card_claim`) |
| `profile_card_merge` | сайт: страница кабинета, кэш анкеты, панель | **уважает** их: `profile_card_keep` роняет помеченное |

⚠ **Импорт анкет сюда не входит, и это не упущение.** У него решение и запись
разведены намеренно: `import_.import_match` — чистая функция, она только
*планирует* карточку (`{**before, **fresh}`, уже с `profile_card_keep`), а
`UPDATE` делает роутер импорта (`_profile_update`). Отметки он уважает своим
путём, а `parameters` переживают его потому, что `before` — прежняя карточка
целиком. Единственное, что здесь нужно, — **проверка**, что это так и остаётся.

⚠ Сверки снимка у `merge` нет — её нет и у обоих близнецов сегодня. Это
сохраняется как есть: заводить её значило бы расширить задачу. Но предупреждение об
этом после переезда будет стоять в **одном** месте вместо двух.

#### ⚠⚠ Слияние `parameters` — глубокое, и это не придирка

У близнецов слияние **плоское**: `{**before, **kept}`. С вложенным ключом оно
молча стирает данные, и вот как. `profile_card_keep` выбрасывает из пришедшего
помеченные подключи — значит у анкеты, где человек правил руками **все** 21 поле,
она вернёт `{'parameters': {}}`. Плоское слияние положит этот пустой словарь
поверх полного, и правленое руками исчезнет целиком — ровно у той анкеты, которую
человек заполнял дольше всех.

Поэтому `profile_card_merge` сливает `parameters` отдельной строкой:

```python
card = {**before, **kept}
if 'parameters' in kept:
    card['parameters'] = {**before.get('parameters', {}), **kept['parameters']}
```

⚠ Это **единственное** место с глубоким слиянием, и держится оно на том, что
вложенный ключ в карточке один. Появится второй — правило придётся обобщать, а не
копировать строкой ниже.

### 6. Отметки правки: составные имена

```
profile_edited = ["about", "parameters.height", "parameters.hobby"]
```

`PROFILE_CARD_FIELDS` = прежние пять + 21 имя `parameters.*`, собранные из реестра
(`PROFILE_PARAM_PREFIX + key`). Дальше почти всё работает без правок:
`profile_card_edited` фильтрует по списку, `profile_card_forget('parameters.height')`
сверяется с ним же, ручка `DELETE /card/{field}` — тоже.

Меняются две функции:

- **`profile_card_keep`** учится ронять вложенные ключи: если в пришедшем есть
  `parameters`, помеченные подключи выбрасываются из него, а сам ключ остаётся;
- **`_card_apply`** сравнивает `values['parameters']` **поключево** и метит только
  разошедшееся — то же правило «метится изменённое, а не присланное», ради которого
  «открыл поглядеть и сохранил» не замораживает поля. Ключа `parameters` в
  присланном нет вовсе — не трогаем ничего, как и у прочих полей; прежние значения
  переживают правку одной почты.

⚠ `PROFILE_CARD_EMPTY` для параметров расширять не нужно: пусто у всех — пустая
строка. В `_same` появляется `PROFILE_CARD_EMPTY.get(field, '')`.

⚠ **Три прежних писателя ключа `parameters` не присылают вовсе**, и
`{**before, **fresh}` сохраняет его нетронутым. Записать это явно обязательно:
иначе первый же читатель заподозрит потерю там, где её нет.

### 7. Био

`agent_bio(card)` получает второй абзац: строки из `profile_param_bio`, в порядке
реестра, только непустые.

```
My name is Diana. I am 36 years old. I live in Kyiv. Red-haired woman and that
says a lot! I have a sunny warm ginger and light character, I love laughter…

Birthday: 1990-01-21
Country: Ukraine
Occupation: choreographer
Education: University
English: Good
Marital status: Never been Married
Children: None
Religion: Christian
Ethnicity: White/European
Body: Slim
Height: 172 cm
Weight: 51 kg
Hair: Red
Hair style: Medium
Eyes: Hazel
Smoke: No
Drink: Rarely
Partner age from: 35
Partner age to: 65
Hobby: No sport, no life, that's my motto! Swimming, gym, Jiu Jitsu…
Looking for: A happy union is possible when two are self-sufficient…
```

⚠ **Пустое не называется вовсе.** То же правило, что у `companion_bio`: строка
«Hair: —» читается моделью как факт («цвет волос неизвестен»), и она может об этом
заговорить. Молчание честнее.

⚠ **`age_from`/`age_to` — две строки, а не одна «35–65».** Склейка была бы
единственным исключением из «ключ → строка», а первое исключение разрешает второе.
Признак пересмотреть: живое био покажет, что две строки читаются плохо.

⚠ **Куда уезжает — не меняется.** `girl_bio` остаётся одной переменной: и при
заведении агента, и на каждом ответе в чате. Правок у соседа нет вовсе.

⚠ **Предел 4000 знаков, по границе строки.** `girl_bio` уезжает на каждую реплику, а
`Hobby` и `About Partner` человек на панели пишет без ограничений. Режем **по
границе строки**, а не по знаку: оборванное на полуслове выглядит как сбой и
провоцирует модель это «досочинить».

⚠⚠ Ровно такое же правило уже стоит у `companion_bio` (1200 знаков) **своим куском
кода**. Это второй случай, значит обрезка переезжает в общий слой одной функцией
`py_modules/text_/text_trim_lines.py`, и `companion_bio` начинает звать её. Два
правила «как резать текст» разошлись бы так же, как разошлись три копии процентов
(`percent.py`): две клампили сами, третья соблюдала границы реестра.

⚠ Условие «биографии нет» **не трогаем**: `agent_bio` по-прежнему возвращает
пустоту, когда нет ни описания, ни города, ни возраста, и заведение агента говорит
«сначала прочитайте анкету». Параметры в это условие не входят.

### 8. Окно

`dating-modal-box` для карточки анкеты расширяется и делится сеткой на две колонки;
на узком экране колонки встают друг под друга (`grid-template-columns: 1fr` в
медиазапросе). Ширина задаётся **своим классом** у этого окна, как это уже сделано
у окна описания снимка (`.gallery-card { width: min(860px, 94vw) }`), а не правкой
общего `.dating-modal-box`: его делят трое.

```
┌─ Персональные данные анкеты ──────────────────────────────────────────────┐
│ Почта          [bogiladiana9021@bigmir.net]  │ Параметры с сайта          │
│ ID на сайте    [643694]                      │ Дата рождения [1990-01-21] │
│ Имя            [Diana]                       │ Страна        [Ukraine]    │
│ Возраст        [36]                          │ Занятие       [choreogr…]  │
│ Город          [Kyiv]                        │ …                          │
│ Описание       [……………]                       │ Увлечения     [textarea]   │
│                                              │ О партнёре    [textarea]   │
│                                              │ [Обновить с сайта]         │
│                                              │ снято 12.10 в 16:32        │
│                       [Отмена]  [Сохранить]  │                            │
└───────────────────────────────────────────────────────────────────────────┘
```

- Вид поля — из реестра: `hobby` и `about_partner` текстовой областью, остальные
  однострочным полем.
- Отметка «правлено руками · вернуть сайту» — у каждой строки, тем же кодом, что у
  пяти прежних полей (функция `label(key, text)` уже написана и принимает имя поля).
- Время снятия берётся из `parameters_at` и сдвигается в часовой пояс настройки
  через `time.js`: с сервера всё приходит в UTC.
- Сохранение остаётся **одним** нажатием на всё окно: 27 полей, одна ручка. Отказ —
  в подвале окна, набранное остаётся в полях.

⚠ **Наружу мы не пишем ничего.** Кнопка только читает панель; правка в окне меняет
нашу карточку и больше ничего. Это говорится подсказкой в шапке второй колонки —
иначе человек решит, что правит анкету на сайте, и удивится, не увидев там правки.

### 9. Ручки

| Ручка | Что делает |
|---|---|
| `GET /api/dating/profile/{id}/card` | **дополняется**: в ответ добавляются `parameters` (каркас), `parameters_at` и `parameter_fields` — реестр подписей и видов |
| `PUT /api/dating/profile/{id}/card` | **дополняется**: тело получает `parameters: dict[str, str]`; модель `DatingProfileCard` отсеивает ключи вне реестра и режет значения по длине вида: `text` — 190 знаков, `area` — `IMPORT_ABOUT_MAX` (2000), теми же постоянными, что у прочих полей карточки |
| `DELETE /api/dating/profile/{id}/card/{field}` | без правок — имя `parameters.height` уже сверяется с `PROFILE_CARD_FIELDS` |
| `POST /api/dating/profile/{id}/card/parameters` | **новая**: снять с панели и записать |

Новая ручка живёт в `src/uvicorn/routers/dating/profile_action.py` — «всё, что ходит
к сайту и к соседу». Домен — `src/dating/profile_panel.py`, ~70 строк: взять номер
анкеты из карточки, спросить драйвер о пути, `panel_fetch_html`, `panel_fetch_form`,
`драйвер.params`, `profile_card_merge`.

⚠ `parameters_at` проставляет **`profile_panel.py`**, а не `profile_card_merge`: это
отметка «панель прочитана», и у прочих писателей карточки её быть не должно.
Уезжает она в том же `fresh`, что и сами параметры, то есть одним `UPDATE` с ними —
разойтись отметке со значениями нечем.

### 10. Отказы

| Что случилось | Ответ |
|---|---|
| у сайта пуст `admin_url` | 422 «у сайта нет админ-панели» |
| у сайта базовый драйвер панели (пустой `path`) | 422 «панель этого сайта читать нечем» |
| у анкеты пуст номер на сайте | 422 «у анкеты нет номера на сайте» |
| панель увела на вход | 502 «панель увела на вход: сессия не признана» |
| панель ответила кодом ошибки | 502 с её кодом |
| **форма не дала ни одного известного поля** | 502 «на странице панели не нашлось ни одного поля — похоже, разметка сменилась», **и не записывается ничего** |

⚠⚠ Последняя строка — главная в этом разделе. Без неё смена разметки у сайта
обнулила бы параметры у всех сорока анкет молча, по одному нажатию кнопки. **Пустой
разбор — это отказ, а не пустой результат.** Порог «ни одного» (а не «меньше
половины») выбран намеренно: сайт вправе убрать одно поле, и половинчатый порог
начал бы отказывать на законных изменениях.

Поход в панель и так ложится строкой в «Журналы → Запросы» — это делает транспорт
внутри `panel_fetch`. Исход дополнительно пишется в журнал анкеты (`log_write`), как
у прочих действий с анкетой: человек открывает журнал, а не вкладку запросов.

### 11. Проверки

Живого HTTP в сюите нет никогда: панель подменяется `tests/panel_fake.py` (он
подменяет транспорт внутри `panel_fetch`, а не его функции).

1. **каркас** — `profile_param_frame` всегда даёт 21 ключ в порядке реестра; чужие
   ключи выбрасывает; недостающие кладёт пустыми;
2. **био** — пустые поля не названы; подписи и порядок из реестра; предел 4000 режет
   по границе строки, а не по знаку;
3. **чтение формы** — на настоящем образце разметки: `input[value]`, выбранный
   `option`, тело `textarea`, поле без `name` пропущено, `select` без `selected` даёт
   пустоту;
4. **нормализация драйвера** — `5'8" - 172 cm` → `172 cm`; `112 lb - 51 kg` →
   `51 kg`; `21`/`Jan`/`1990` → `1990-01-21`; неизвестный месяц и неполная тройка →
   пусто;
5. **сторож согласия** — карта драйвера и реестр совпадают ключ в ключ: ни лишнего
   имени, ни потерянного. Роль та же, что у `TestTheyAgree` в `initiative_explain`:
   два списка про одно и то же расходятся молча;
6. **отметки** — `profile_card_keep` роняет `parameters.height` и не трогает
   соседние; `_card_apply` метит только изменённый параметр, совпавший не метит;
6a. **все 21 правлены руками** — `profile_card_merge` не стирает ни одного:
   пришедшее даёт пустой `parameters`, и глубокое слияние обязано это пережить.
   Тест пишется **до** правки `merge` и обязан падать на плоском слиянии;
7. **`parameters` переживают прочих писателей карточки**: чтение страницы кабинета
   и кэш анкеты — через `profile_card_merge`, импорт — своим путём (`{**before,
   **fresh}` в `import_match`), и у него это проверяется отдельно: ключа
   `parameters` он не присылает, и прежний обязан уцелеть;
8. **ручка** — образец → параметры легли и `parameters_at` проставлен; **пустая
   форма → отказ словами и прежние значения на месте**; нет номера анкеты → 422;
9. **`text_trim_lines`** — своим тестом в сюите `py_modules`.

Образец разметки — `tests/frames/ladadate_lady_edit.html`: форма целиком, списки
`option` укорочены до трёх с сохранением выбранного.

⚠ **Значения в образце обезличены.** Файл лежит в репозитории, и правило для этой
папки уже записано в её `readme.md`: «номера собеседников и тексты безличны
намеренно». Разметка и имена полей остаются настоящими — в них весь смысл образца;
номер, имя, город и три текстовых блока заменяются короткими нейтральными.

## Чего в этой задаче нет

- **Круга, который обходит анкеты сам.** Решено: обновление только кнопкой. Признак
  пересмотреть — если окажется, что параметры у половины анкет не снимали ни разу.
- **Записи на сайт.** Мы только читаем; правка в окне остаётся нашей.
- **Переноса `Name`/`City`/`AboutMyself` с панели в карточку** — у них три своих
  писателя, и четвёртый это отдельное решение.
- **Расширения условия «биографии нет»** в `agent_bio`.
- **Сверки снимка (`_card_claim`) у `profile_card_merge`** — её нет и сегодня у обоих
  близнецов; переезд её не добавляет и не убирает.
- **Параметров у мужских анкет.** Роль `man` своего агента не имеет вовсе
  (`AGENT_WORKFLOW_CREATE` знает только `lady`), и ставить ей вторую колонку не для
  чего.
