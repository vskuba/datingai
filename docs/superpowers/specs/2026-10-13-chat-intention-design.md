# Намерения разговора: таблица `chat_intention` (2026-10-13)

## Зачем

Агент `dating_talk` по ходу разговора принимает решения, которых нет в тексте
ответа: «она обещала прислать фото», «он просил не писать до вечера». Сосед уже
умеет такое помечать — инструмент `chat_intention_add` кладёт **метку словом**
(`she_promised_send_photo`, не длиннее 100 знаков) и отдаёт их списком в ключе
`intentions` ответа `/chat/ask`.

Панель этот ключ **выбрасывает**: `rhapsody_api_chat_talk` читает из ответа
только `result` и `message_id`. То есть обещания девушки сегодня не живут
нигде, и исполнить их нечему.

Таблица `chat_intention` — место, где обещание ждёт исполнения.

⚠ У соседа есть своя `companion_intention`, и она решает **другую** задачу:
отметкой времени режет историю надвое, чтобы одно обещание не приезжало на
каждом следующем ответе. Это дедупликация внутри разговора, а не очередь
работы, и подменить одно другим нельзя.

## Что решено

| Вопрос | Решение |
|---|---|
| Кто ставит «выполнено» | **код** — занятие-исполнитель, которого ещё нет. Таблица = очередь работы |
| Повтор той же метки той же паре | **одна открытая** на пару + метку; выполненная ключ отпускает |
| Связь с собеседником | `site_id` + `uid`, как у всех пяти пулов и `companion_gallery_file` |
| Когда заводится строка | **сразу по ответу прогона**, до отправки реплики |
| Откуда пишется | `_agent_ask` — одна точка на три канала |
| Объём работы | таблица + запись из прогона; показа в панели пока нет |

## Границы работы

Входит: миграция, доменный модуль, подхват `intentions` в двери к соседу, вызов
из `_agent_ask`, тесты, документация.

**Не входит и это решение, а не недоделка:**

- **Исполнителя нет.** Круга, который берёт открытые намерения и делает дело,
  в этой работе не будет. Таблица заводится раньше работы намеренно — тем же
  доводом, что `companion_gallery_file`: память нужна в тот же миг, когда
  исполнение появится, а завести её потом значит иметь первые сотни обещаний
  без следа.
- **Показа в панели нет.** Пока некому исполнять, показывать нечего.
- **Словаря меток нет.** Какие метки бывает, задаёт workflow у соседа, и правки
  workflow живут только в его прод-базе — списка в коде не существует ни на
  одной стороне. Метка хранится как приехала.

## Схема

Файл `migrations/20261013150000_chat_intention.sql`. Имя без приставки
`dating_` — так называют новые таблицы (`chat_initiative`, `chat_reply`).

```sql
CREATE TABLE IF NOT EXISTS `chat_intention` (
    `id`         INT NOT NULL AUTO_INCREMENT,
    `site_id`    INT NOT NULL
        COMMENT 'Сайт собеседника: номер человека уникален в его пределах',
    `profile_id` INT NOT NULL
        COMMENT 'Чьё намерение: от чьего имени шёл разговор',
    `uid`  VARCHAR(32) NOT NULL
        COMMENT 'Кому обещано: номер собеседника на сайте',

    `intention` VARCHAR(100) NOT NULL
        COMMENT 'Метка словом: she_promised_send_photo',

    `status`  ENUM('open','done') NOT NULL DEFAULT 'open',
    `done_at` DATETIME NULL DEFAULT NULL
        COMMENT 'Когда исполнили. NULL — ещё открыто',
    `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
        COMMENT 'Когда намерение приехало от соседа',

    `open_intention` VARCHAR(100) GENERATED ALWAYS AS
        (IF(`status` = 'open', `intention`, NULL)) STORED
        COMMENT 'Метка, пока намерение открыто. NULL у выполненных',

    PRIMARY KEY (`id`),
    UNIQUE KEY `uq_chat_intention_open`
        (`site_id`, `uid`, `profile_id`, `open_intention`),
    KEY `idx_chat_intention_open` (`status`, `site_id`, `id`),
    KEY `fk_chat_intention_profile` (`profile_id`),
    CONSTRAINT `fk_chat_intention_profile` FOREIGN KEY (`profile_id`)
        REFERENCES `profile` (`id`) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='Намерения разговора: что агент пообещал и исполнено ли это';
```

Почему именно так:

- **`VARCHAR(100)`** — ровно предел соседа (`CHAT_INTENTION_LENGTH_MAX`).
  Длиннее у него не принимается, значит приехать не может.
- **Ключ держат только открытые.** `open_intention` гаснет в `NULL` у
  выполненной, а `NULL` в MySQL уникальности не нарушает. История обещаний
  остаётся, повтор открытой строки не заводится. Простой
  `UNIQUE (site_id, uid, profile_id, intention)` запретил бы **второе**
  обещание фото когда бы то ни было — а второе обещание законно и ожидаемо
  («oh no… I didn't get any photo» → «i can send it again if you want»).
- **`profile_id` входит в ключ, но не в вычисление**, и это не стиль. MySQL
  запрещает `ON DELETE CASCADE` у внешнего ключа, если от его столбца зависит
  генерируемый (`Cannot add foreign key constraint`, 1215) — таблица не
  создалась бы вовсе. Тем же приёмом живут `chat_initiative` и `invite`.
- **Регистр метки сравнивать не нужно**: при `utf8mb4_unicode_ci` ключ считает
  `Promised_Photo` и `promised_photo` одним. Дописывать нечего.
- **`site_id` хранится, хотя выводится из анкеты** — как в
  `companion_gallery_file` и `chat_initiative`: отбор идёт по сайту, и `JOIN`
  ради него в каждом запросе не нужен.
- **Два состояния, не три.** `failed` добавит миграцией тот, кто заведёт
  исполнителя: сегодня падать нечему.
- **Каскад по анкете** закрывает уборку сюиты: сторож `test_suite_sweep.py`
  сверяется со **схемой**, а не со списком имён, и таблица с
  `ON DELETE CASCADE` в ручную чистку не попадает сама собой.

Миграция пишется по общему правилу: разделы «ДО» и «ПОСЛЕ» со счётчиками,
`CREATE TABLE IF NOT EXISTS` ради идемпотентности. Перед накатом — репетиция
`mysql_rehearse` из общего слоя.

## Поток данных

```
dating_talk у соседа
  └─ шаг зовёт chat_intention_add('she_promised_send_photo', …)
       ├─ накопитель прогона  → ответ /chat/ask, ключ `intentions`
       └─ companion_intention у соседа (его дедупликация, нас не касается)

панель
  rhapsody_api_chat_talk   → {'text', 'message_id', 'intentions'}
    └─ _agent_ask          → chat_intention_put(profile_id, site_id, uid, …)
         └─ chat_intention: открытые строки

позже (этой работой не делается)
  исполнитель → chat_intention_open(...) → дело → chat_intention_done(id)
```

## Единицы

### `src/dating/chat_intention.py` — единственная дверь к таблице

| Функция | Что делает | Отдаёт |
|---|---|---|
| `chat_intention_put(profile_id, site_id, uid, intentions)` | заводит открытые строки пачкой, `INSERT IGNORE` | сколько новых легло |
| `chat_intention_open(site_id, profile_id=0, uid='', limit=0)` | что ещё не выполнено | список строк |
| `chat_intention_done(id)` | закрывает намерение | легла ли **наша** отметка |

- **Повтор открытой строки — обычный исход, а не ошибка.** Ключ отвергает
  вставку сам, вызывающему достаточно числа новых. Поведение и формулировка те
  же, что у `companion_gallery_sent`.
- **Отметка ставится условным `UPDATE`** (`WHERE id = %s AND status = 'open'`),
  а не вопросом «ещё открыта?» отдельным запросом: два исполнителя могут взять
  строку одновременно, и между вопросом и записью они разошлись бы. `rowcount`
  отвечает, наша ли это отметка. Тем же приёмом живёт `invite_send`.
- **Предел в 100 знаков проверяет модуль, а не дверь**: столбец принадлежит
  ему. Метка длиннее — пересказ разговора, сопоставить его не с чем, и такая
  метка отбрасывается молча. Сосед её и сам не принимает, но полагаться на
  чужой предел нельзя.
- **Пустой `uid` или пустой список — ничего не пишем**: намерению не к кому
  принадлежать.

Зависит от: `mysql_.mysql_`, `logging_.logging_`. Больше ни от чего — модуль
знает про таблицу и не знает ни про соседа, ни про каналы.

### `src/rhapsody/rhapsody_api.py` — третий ключ ответа

`rhapsody_api_chat_talk` начинает отдавать `intentions` списком строк:

```python
return {'text': str(data.get('result') or ''), 'message_id': number,
        'intentions': _intentions(data)}
```

- **Ключ отдаётся всегда**, пустым списком в том числе — по той же причине, по
  какой его всегда отдаёт сосед: принимающая сторона сворачивает «пусто» и
  «ключа нет» в одно, и пропажа стала бы неотличима от штатной тишины. Ровно
  так поломка `message_id` прожила шесть дней незамеченной.
- Разбор не доверяет чужой форме: что приехало не списком — пустой список;
  элементы приводятся к строкам и обрезаются по краям; пустые выбрасываются.
  Повторы внутри одной пачки не схлопываются здесь — это дело ключа базы.
- Дверь **не** ходит в нашу базу и не знает ни про анкеты, ни про
  собеседников. Это единственная дверь к соседу, и ею она остаётся.

`rhapsody_api_chat_ask` (тонкая обёртка для почтовых агентов и галереи) не
меняется: ей нужен только текст.

### `src/dating/answer.py` — точка записи

В `_agent_ask`, прямо перед `return`:

```python
await chat_intention_put(int(profile['id']),
                         int(profile.get('site_id') or 0),
                         uid, got.get('intentions') or [])
```

- **Подпись `_agent_ask` не меняется** — он по-прежнему отдаёт
  `(текст, ошибка, номер обмена)`. Четыре вызывающих (чат, инициатива, письмо
  первым, ответ на письмо) не трогаются вовсе.
- **Одна точка на три канала.** Отдай мы намерения наверх четвёртым значением,
  правило «запиши намерения» встало бы тремя копиями — ровно грабля
  `delivered_at`, где дорог оказалось пять и четвёртую забыли.
- **Отказ записи не роняет ответ.** Реплика к этому моменту сочинена и сейчас
  уйдёт человеку; уронить её из-за ненаписавшейся отметки значит отменить
  дорогую работу ради дешёвой. `try/except` + `logger_info` — тот же довод, по
  которому не бросает `rhapsody_api_chat_delivered`.
- **Строки в `log` анкеты не пишем**: запись в таблице и есть след.

## Известный размен

Строка заводится **по ответу прогона**, то есть до отправки. Значит возможна
открытая строка от обещания, которого собеседник не читал: агент промолчал,
отправка не удалась, а у писем между сочинением и отправкой проходят **часы** —
их уносит круг отправки, и черновик может быть стёрт уборкой.

Это принято сознательно: честный вариант требует отмечать намерение там же, где
ставится отметка доставки, — а это пять дорог сквозь пулы, и четвёртая
забывается. Лечится позже столбцом `message_id` в строке и отметкой доставки по
нему; место под него в таблице есть, и исполнитель тогда берёт только
доставленные.

## Проверка

Живого HTTP нет нигде. Подменяется приватная `_request` того же модуля — так
устроен `test_rhapsody_chat_client.py`, и тело функции интересует именно разбор
ответа. Анкета берётся фикстурой `girl_make` из `tests/conftest.py`, своей не
заводим.

**`tests/test_rhapsody_chat_client.py`** (метка `core`):

- `intentions` доезжают из ответа соседа;
- ключа в ответе нет → пустой список;
- ключ приехал не списком → пустой список.

**`tests/test_chat_intention.py`**, новый (метка `chat`):

- первая метка ложится; повтор той же метки той же паре, пока первая открыта, —
  не ложится;
- **выполненная отпускает ключ**: после `chat_intention_done` та же метка
  ложится снова, и в таблице две строки;
- `chat_intention_open` отдаёт только открытые и отбирает по сайту и анкете;
- вторая отметка той же строки отвечает `False` — условный `UPDATE` работает;
- метка длиннее 100 знаков не пишется;
- пустой список и пустой `uid` не пишут ничего;
- запись из `_agent_ask` ложится (подменяется `rhapsody_api_chat_talk`), а её
  падение ответ не роняет.

Уборка за сюитой — каскадом по `profile_id`; `test_suite_sweep.py` подтвердит
это сам, потому что сверяется со схемой.

Прогон: `pytest -m "chat or core"`, полная сюита — перед выкладкой.

## Поправка от 13.10.2026 — `chat_intention_open` удалена

Спека заводила `chat_intention_open` как «дверь для исполнителя», а
`chat_intention_rows` (спека вкладки) — как чтение для показа, и обосновывала
разницу договоров. На ревью выяснилось: за всё время у `chat_intention_open` не
появилось **ни одного вызывающего в бою** — только тесты, — а отбор она
повторяла слово в слово.

Функция удалена. Открытые намерения читаются
`chat_intention_rows(site_id, status='open')` — им же возьмёт работу исполнитель,
когда появится. Разделять чтение заранее значило угадывать, чего исполнителю
хватит; угадали неверно, и три дня в модуле стояла вторая копия отбора.
