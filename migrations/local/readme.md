# Разовые загрузки данных — только для локальной базы

Файлы здесь **не миграции**, хотя выглядят ими. Это одноразовые переносы данных,
уже выполненные на локальной базе.

## ⚠⚠ Почему они в подпапке, а не рядом с миграциями

Потому что `yoyo` катает миграции **при старте приложения**
(`main_uvicorn.py` → `mysql_migration_up`) и подпапки не обходит — проверено
опытом, не предположением. То есть подпапка работает как предохранитель.

Без него первая же выкладка выполнила бы на проде `DELETE` по `message`,
`contact`, `favorite` и `mail_in` — то есть снесла бы **всю переписку прода**,
42 289 реплик, ради того чтобы положить на её место её же снимок.

⚠ В шапке файла написано «это не миграция». Написано — и не защищено ничем:
признак прода живёт в `APP_ENV`, а из SQL её не видно. Надпись не предохранитель,
подпапка — предохранитель.

## Что здесь лежит

| файл | что делал |
|------|-----------|
| `…000000_dialogs_from_prod` | заменил тестовый мусор сюиты снимком прод-диалогов: 42 289 реплик, 147 избранных, 47 писем |

## ⚠ Почему это вообще понадобилось

Локально «Чат → Диалоги» и «Фавориты → Диалоги» показывали 25 тысяч реплик,
сочинённых сюитой, и одну запись избранного. Проверять на них вид страницы нельзя:
ни длинных разговоров, ни переписки письмами, ни отказов там нет.

## ⚠⚠ Что при этом уцелело намеренно

Строки сюиты (`seed-%`) из удаления **исключены**. Первая версия файла их снесла
вместе с остальным, и шесть тестов покраснели: `seed-000-big@example.com` живёт на
сайте 19, том же, что и боевые анкеты. Восстанавливать пришлось из бэкапа — 680
записей и 25 490 реплик.

## Как прогнать здешнее руками

    docker exec -i dating_mysql mysql --default-character-set=utf8mb4 \
      -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" dating -t < migrations/local/<файл>

⚠ Отметки в `_yoyo_migration` при ручном прогоне не появится, и это правильно:
файл не в очереди, ему там нечего отмечать.
